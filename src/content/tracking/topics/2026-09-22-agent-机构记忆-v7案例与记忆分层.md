## 先回答问题

- **机构记忆解决什么问题**：模型会推理，但不「认识」你的公司——哪份基金报告是最新的、同一个公司在三个系统里叫什么名字，这些上下文散落在文档、数据室、表格、邮件和内部工具里，**对 agent 不可见**。每次新会话，agent 都要重新发现一遍（A；见条目 1）。
- **V7 的实现一句话**：把企业文件解析成一张**「实体 + 关系 + 引用证据」的图（Context Graph）**——agent 近期对话留在上下文窗口里，更旧的知识存进图里按需检索；图不够时还能回退到对原始文档的 RAG 检索（A 自报；见条目 2）。
- **效果**：自报口径——检索式系统在企业信息连接基准 HERB 上超官方基线 69%、对「不可回答问题」的幻觉减少 38%；客户案例称交易筛查快 21 倍（一天 → 15 分钟）。**全部自报，无第三方验证**（A 自报；见条目 3）。
- **与编码 agent 记忆的关系**：CLAUDE.md、记忆文件解决的是「记住偏好和教训」（个人级、短小）；V7 这类机构记忆解决的是「记住整个组织的知识与出处」（企业级、海量）——两者是同一问题的不同规模，分层逻辑相同（分析；见条目 4）。

## 详细解释与证据

### 1. 问题：为什么 agent 需要「机构记忆」

三个叠加的约束使「把公司文件全塞给 agent」不可行：

- **上下文窗口有限**：再大的窗口也装不下一家公司的全部文档、数据室、表格、邮件；
- **注意力稀释**：塞进去的内容越多，模型对每一段的注意力越弱（与 09-21 归档 Jev 专题讨论的「信息熵」问题同源）；
- **知识是分散且带版本的**：「哪份基金报告是当前的」「同一个实体在三个系统里的名字」——这类问题的答案不在任何单个文件里，而在文件**之间的关系**里。

V7 官方对问题的表述（客户故事原文）：「今天的模型能推理复杂任务，但不会自动理解任务背后的业务上下文——那些上下文活在文档、数据室、表格、邮件和内部工具里：分散、未解决、对 agent 不可见。」

来源：[How V7 gives AI agents institutional memory](https://openai.com/index/v7)｜OpenAI 客户故事（V7 为欧洲金融行业初创，2018 年由 Rizzoli 与 Edwardsson 创立）｜2026-09-21｜A

### 2. 实现：Context Graph——把文件解析成「实体 + 关系 + 引用证据」的图

V7 Go 的机制分四步（客户故事原文要点）：

1. **接入仓库**：连接 SharePoint、Google Drive 等企业存储；
2. **扫描与抽取**：识别文件中的公司、基金、人物等实体（按本体/ontology），以及事实、属性、指标；
3. **建图**：把每个事实连接到新或已有的记录，并**保留指向原始来源的引用证据**（cited evidence）；
4. **查询与兜底**：agent 直接查询这张图（官方称比长上下文方案便宜且快一个数量级）；图不够时，回退到对底层文档的 RAG 检索（检索增强生成——先检索相关片段、再基于片段生成回答）。

对长时运行的 agent，V7 Go 的记忆分层是：**近期对话留在模型的活动上下文里，更旧的材料存进图里按需检索**——这正是本稿要立的「记忆分层」：工作记忆在上下文里，长期记忆在可检索的图里，两者各司其职。

来源：[OpenAI 客户故事](https://openai.com/index/v7)｜A（机制描述为 V7 自述）

### 3. 效果数字与边界：全部自报，且「99.9%」需拆开看

V7 自报的效果：50–100 步工作流几分钟完成、99.9% 准确率、每步决策可审计（auditable trail）；基准 HERB（跨企业系统找信息并建立连接的基准）上，其纯检索系统超官方基线 69%、对不可回答问题的幻觉减 38%；客户案例：资产管理者筛交易快 21 倍（整天 → 15 分钟）、一个金融服务团队把审阅时间从 100+ 小时压到 10 小时以内（每任务省 \$12,000 专家成本）。

**边界三条**：①全部为 V7 自报——HERB 基准的官方基线是什么、任务分布如何，本稿未核；②「99.9% 准确率」未说明口径（是字段级抽取准确率还是任务成功率）；③权限模型（谁能查到哪份文件）未披露——对企业记忆系统而言，权限与审计和效果同等重要。

来源：[OpenAI 客户故事](https://openai.com/index/v7)｜A（自报数字）

### 4. 模型分工：Luna 提取、Sol/Terra 推理、Astra 攻最难查询

客户故事里的模型分工本身就是一份「按任务选模型」的示范：**GPT-5.6 Luna**（便宜档）做百万级文件的信息抽取（每文档成本降 78%、精度反升 11.6 个百分点）；**GPT-5.6 Terra 与 Sol** 做复杂多步指令的推理与工具调用；**GPT-6 Astra** 只用于最难的图查询（跨千份文档的金融分析，最难查询 89% 准确率）。这与 09-19 归档 Luna vs Astra 代码审查对比（条目 5）的结论互相印证：便宜模型管量、贵模型管难。

来源：[OpenAI 客户故事](https://openai.com/index/v7)｜A（自报）

### 5. 更广的图景：记忆的三个层次与既有形态

agent 的「记忆」实际分三层，V7 做的是第三层：

| 层次 | 内容 | 典型实现 | 生命周期 |
|---|---|---|---|
| 工作记忆 | 当前会话的上下文窗口 | 模型上下文本身 | 会话内 |
| 长期记忆 | 跨会话的偏好、教训、决定 | CLAUDE.md、ChatGPT 记忆、各 harness 的 memory 文件 | 长期、个人/项目级 |
| **机构记忆** | 整个组织的文件、实体、关系与出处 | V7 Context Graph 这类图/检索系统 | 长期、组织级 |

前两层在编码 agent 场景已有成熟形态；第三层（机构记忆）此前多见于 RAG/知识图谱产品，V7 的差异点是把图检索**做成了 agent 的原生记忆层**（agent 直接查询图，而不是人查询后粘贴给 agent）。背景提示：知识图谱 + 检索的组合在企业搜索领域并不新（ SharePoint/Graph 生态多年），新的是与 agent 执行循环的直连。

来源：产品形态对照为分析｜判断

### 适用域边界（读者问询引出的关键区分）：文档域成立，代码域是另一回事

V7 Go 处理的是**企业文档**（基金报告、CIM 交易文件、保险承保、邮件表格）——非结构化但语义自洽的文本，实体关系（哪家公司、哪支基金、哪个人）可以用本体枚举。**代码仓库是另一个问题**：代码的「语义」由调用关系、类型系统与执行行为定义，朴素分块+embedding 的 RAG 在代码上效果差是工程共识——证据：Greptile 的 Launch HN 标题自我限定为「RAG on codebases **that actually works**」（2024-03，253 分，暗示此前的代码库 RAG 不 work）；工具市场随后出现明确「去 RAG」定位的检索（grebmcp，2025-11）；以及 Semble 用改造的语义索引声称对 grep 省 98% token（2026-05，445 分）。结论分两层：①「朴素 RAG 对代码基本无效」有市场证据支持；②「改造后的语义检索（Semble）可以反超 grep 的 token 成本」也有实例——**两者不矛盾：对代码有效的检索全是改造过的专用工程**。若把 V7 的 Context Graph 搬到代码仓库，恰好落入需要这种专门工程的失效区——领域不匹配。

**Semble 的实现补充（09-22 核查其 README，MIT，6,123★，MinishLab 出品——即 model2vec 静态嵌入团队）**：三件技术——①结构感知分块（按函数/类边界，非字符切分）；②静态嵌入检索（预计算查表向量，**查询无需 transformer 推理**：约 1ms、纯 CPU、无 API key；质量口径 NDCG@10 0.854，官方称追平 137M 参数的代码专用 transformer 嵌入 CodeRankEmbed，索引快 380 倍、查询快 17 倍）；③标识符词干匹配（查 "parse config" 加权含 parseConfig/ConfigParser 的块）。**省 98% 的口径**：基线是「grep 匹配行 + agent 读整个命中文件」的完整工作流——同等 recall 下 grep+read 需约 100k token 到 85%，Semble 2k token 到 97%；节省公式公开为（命中文件全文字符 − 返回片段字符）/ 4。局限：NDCG@10 0.854 意味着 top-10 仍有约 15% 不理想；静态嵌入的多跳语义查询弱于 transformer；基准为自建（63 仓库 / 19 语言 / 1,250 查询）。生态已有 Rust 移植（semble_rs：BM25+语义+Tree-sitter，211★）与 Go/VS Code 集成。**但其全部文档与基准只测「块与查询的相似度」——代码检索的另一半「链路型查询」（改这里影响哪些调用方 / 这个值从哪来）需要调用图与 def-use 链，Semble 的评测零覆盖，实现里也只有一条单跳的「定义块加权」**。链路基础设施（LSP、Sourcegraph 的 SCIP/LSIF 索引）存在但未与检索原语整合——这是相似度检索与代码导航之间的真正空白。

## 对当前工作流的启示

- **本工作区就是手工作版的 Context Graph**：检索手册（规则+指针）+ 归档（事件+引用）+ 专题（实体+出处）——V7 把这套结构做成了产品，反向印证了「引用证据必须保留到原始出处」的原则（09-14 归档以来反复出现）。
- **机构记忆的第一风险是权限而非效果**：把全公司文件喂进一个 agent 可查询的池子，等于把权限模型压缩成一张图——谁能查到哪份文件、跨系统实体合并是否越权，这些问题在 ZCode 事件（09-19 归档条目 1）里已有前车之鉴。部署前权限模型必须先于效果验证。
- **观察项**：V7 Go 的 Context Graph 与 OpenAI 企业记忆功能的边界（会不会被官方吸收）；HERB 基准是否公开可复现；类似机构记忆产品在编码场景（跨仓库知识图）的出现。
