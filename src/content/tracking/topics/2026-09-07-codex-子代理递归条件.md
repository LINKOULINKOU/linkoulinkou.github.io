## 先回答问题

- **为什么能递归**：这是代理运行框架（harness，负责上下文与工具）层的多代理 V2 规则，不是模型特调。子代理是否保留创建子代理的工具，由模型目录（harness 内置的模型元数据清单）声明 `multi_agent_version: v2` 决定；V2 不设递归深度上限，只有并发上限（A；见条目 1）。
- **何时引入**：机制 2026-05-18 已进 CLI（#22514）；体感「更新点」是 2026-09-03 GPT-6-Astra 进内置模型目录时自带 v2 声明（#42607）——机制日期与能力授予日期是两个独立日期（A；见条目 3）。
- **是否 Astra 专属**：不是。目录无「astra ultra」变体，gpt-5.6-sol、gpt-5.6-terra、daybreak 系同为 v2，声明 v2 即可递归；「Ultra」更可能对应服务端套餐档位（tier），尚未核清（A；见条目 1）。
- **推理档位为何影响使用**：源码显示 Ultra 档绑定鼓励主动递归委派的 Proactive 模式，其余所有档位绑定「仅明示请求才创建」；绑定是官方设计，用户实测吻合但只是佐证（A/C；见条目 2）。
- **嵌套与隔离的意义**：嵌套是官方明示的设计，价值在递归分解加分级压缩、保护主代理上下文，代价是 token（模型处理文本的计量单位）放大——Anthropic 自报约 15 倍。隔离是「半隔离」：子代理默认携带父级全部对话历史（`fork_turns` 参数），隔离的是对话与 token，不隔离文件系统——所有代理共享同一目录（A/B；见条目 4、5）。
- **仍不清楚**：`fork_turns` 默认全历史未实测复核；sol/astra 创建频率差异未独立复现；Proactive 模式 token 放大倍率无官方数据（见条目 2、4）。

## 详细解释与证据

### 1. Codex 多代理工具注入规则：V1 受深度上限约束，V2 只看模型目录声明

机制：源码显示，子代理能否拿到创建子代理的工具（代码中的 `spawn_agent`，创建子代理）由 `collab_tools_enabled` 按 `multi_agent_version`（模型目录里声明该模型适用的多代理机制版本的代码字段）三态决定。**当前适用结论以本条 main 分支 2026-09-07 快照为准；历史演进见条目 3。**

| 模式 | 子代理是否保留 spawn 工具 | 深度限制 |
|---|---|---|
| Disabled | 无任何多代理工具 | — |
| V1 | 有，前提是下一个 spawn 深度 ≤ `config.agent_max_depth` | `DEFAULT_AGENT_MAX_DEPTH = 1`（config/mod.rs 常量）：根代理（深度 0）spawn 出深度 1 的子代理；子代理想再 spawn 时 next=2 > 1 被拒。V1 默认不递归，调大 `[agents] max_depth` 即可放开 |
| V2 | 根代理必有；子代理也有 ⇔ 该子代理所用模型在目录声明 `multi_agent_version: v2` | 不检查 `agent_max_depth`——已核实 `agent/control.rs`、`agent/control/execution.rs` 全文无深度校验，只有 `max_threads` 并发上限（registry 的 `reserve_spawn_slot`）；深度值在 V2 里只作追踪/遥测（analytics） |

版本解析优先级（config/mod.rs `multi_agent_version_for_model`）：用户/组织 feature 覆盖（`Feature::MultiAgentV2` 强制 V2；agents 整体关闭 → Disabled）＞ 模型目录声明 ＞ 默认（`Feature::Collab` 开 → V1，否则 Disabled）。

内置模型目录快照（models.json，共 11 个模型）：`gpt-6-astra`＝v2；`gpt-5.6-sol`、`gpt-5.6-terra`、`gpt-daybreak-blue/red-latest`＝v2；`gpt-5.6-luna`、`codex-auto-review`＝v1；`gpt-5.5`、`gpt-5.4`、`gpt-5.4-mini`、`gpt-5.2`＝None（完全没有多代理工具）。

官方提示明示有意递归。Proactive 模式注入的 developer message（官方注入给模型的开发者消息）原文："If at any point you can parallelize work by delegating tasks to another agent (**no matter if you are root or subagent**), you should do so using collaboration tools if it could save time or improve quality."（若任何时刻你能通过把任务委派给另一个代理来并行推进——无论你是根代理还是子代理——且这可能节省时间或提升质量，就应使用协作工具。）

配套机制：子代理所用模型可被 spawn 参数覆盖（`MAX_SPAWN_AGENT_MODEL_OVERRIDES` 上限）；fork 支持 full-history 模式（fork 语义详见条目 4）；V2 工具名为平铺的 `spawn_agent`/`wait_agent`/`send_message`/`list_agents`/`interrupt_agent`，V1 才有 `multi_agent_v1` 命名空间。（用户观察到的 "agentrun" 与 CLI 规范名 `spawn_agent` 不一致，已确认为观察方 harness 的命名差异，不是 Codex 的工具名，不再追。）

**判断与边界**：源码显示模型目录成了 harness 行为的分发介质——`multi_agent_version` 与上下文窗口（context window，模型单次能看到的全部输入）一样是模型元数据的一部分，递归能力按模型分级发放，而不是全局开关。这延续了 [2026-09-07-热点追踪](/tracking/2026-09-07) 条目 5（GPT-6 Astra 发布）的「harness 即产品」主线。V2 无深度硬闸是最大的警点：递归深度不受限，只靠并发上限与模型自觉；官方对成本的对策是记账而非硬闸——v0.151.0（8/29）的 #41183 "Counted nested subagent token usage toward root goal budgets"（嵌套子代理 token 用量计入根目标预算）属于「先放开、再用预算兜住」的思路（我的判断）。从源码推导（未实测）：想复现递归可用 sol/terra；gpt-5.4 系（目录声明 None）应完全没有 spawn 工具；想关闭，可在 feature 层关 MultiAgentV2（回落 V1，受 max_depth=1 管）或整体禁用 agents。待验证：用户提到的「astra ultra」更可能对应 ChatGPT 套餐/服务端 tier 概念（9/3 有 commit "Update GPT-6-Astra **Fast tier** speed description"，说明存在 tier 维度），而非目录内模型变体——尚未核清。

适用范围：以上源码行为均为 openai/codex main 开发分支 2026-09-07 快照，可能与用户本机安装版差数个版本；「具备该机制」不等于在任何部署环境中默认触发。

### 2. 推理档位如何影响子代理调用：Ultra 档绑定 Proactive 主动委派模式

机制（main 分支 2026-09-07 快照，源码显示）：`effective_multi_agent_mode` 仅在 V2 下生效（V1 恒为 None）。解析顺序：配置 hint（config 配置或模型目录条目的 `model_messages.multi_agent.mode` 字段，含空串）优先；没有配置时按推理档位（reasoning effort，控制模型推理投入的设置）二分——

- `ReasoningEffort::Ultra` → **Proactive**（主动委派模式，官方提示鼓励主动拆子任务），提示原文 "…no matter if you are root or subagent, you should do so…"（「无论你是根代理还是子代理，都应这样做」）；
- 其余一切档位 → **ExplicitRequestOnly**（仅明示请求模式），原文："Do not spawn sub-agents unless the user or applicable AGENTS.md/skill instructions explicitly ask for sub-agents, delegation, or parallel agent work."（除非用户或适用的 AGENTS.md/技能说明明确要求子代理、委派或并行代理工作，否则不要创建子代理。）

**Ultra 是「行为档」而非纯数值档**：`resolve_reasoning_effort` 显示，选中 Ultra 后实际发给 API 的 effort 按优先级解析——先取模型目录的 `multi_agent_reasoning_effort` 字段（astra 目录条目＝"xhigh"），否则取 supported 列表的 max 档，再否则取倒数第一个非 Ultra 档。即 astra 上选「Ultra」实际以 xhigh 发请求——Ultra 档真正激活的是 Proactive 行为集，数值上反而「降档」。档位表：astra 与 sol 的 supported levels 均为 low/medium/high/xhigh/max/ultra；sol 无 `multi_agent_reasoning_effort` 字段（其 Ultra 实际落到 max 档）；两者 default_reasoning_level 均为 low。

**用户实测佐证（C 级，未独立复现）**：默认档位下模型基本不主动 spawn；Ultra 档下 sol、astra 均积极开子代理（sol 当时的嵌套情况未留意）——与代码行为吻合。本条目由用户观察触发、代码证实。

**判断与边界**：这是副作用式设计（我的判断）——用户拉满 effort 的诉求是「想得更深」，实际顺带解锁了「递归委派」这一激进行为模式；且 `docs/config.md` 完全没有 `[agents]`/multi-agent 段（grep 无匹配），纯实验特性、公开文档缺位，行为只能靠读源码获知。对成本敏感的团队这是隐蔽的支出放大器：Ultra 档一次「自由发挥」＝更深推理加递归多代理 token 放大的双重叠加；官方显然把这套行为定位为「重火力模式」。sol 在 Ultra 下比 astra 更爱开子代理（用户观感，未复现）体现 prompt 敏感性：Proactive 文案的触发条件是 "could save time **or** improve quality"，模型对自身质量收益的自评差异直接转化为 spawn 频率差异。

适用范围：绑定关系为 main 分支 2026-09-07 快照的源码事实；spawn 频率差异为观察，未独立复现。

### 4. 官方嵌套与隔离设计：usage hints 明文告知递归、fork_turns 与共享目录

以下引文是注入给模型的使用提示（usage hints，源码常量 `DEFAULT_MULTI_AGENT_V2_*_USAGE_HINT_TEXT`），即官方设计意图的第一手表述（main 分支 2026-09-07 快照）：

- **给根代理（root hint）**："You can spawn sub-agents to handle subtasks, **and those sub-agents can spawn their own sub-agents**."（你可以创建子代理处理子任务，而这些子代理也能创建它们自己的子代理。）"**All agents in the team … are equally intelligent and capable**, and have access to the same set of tools."（团队中所有代理同等智能与能力，可用同一套工具。）"You can decide **how much context you want to propagate to your sub-agents with the `fork_turns` parameter**."（你可以用 `fork_turns` 参数决定向子代理传播多少上下文。）
- **给子代理（subagent hint）**：同样被告知「你也能开子代理，子代理也能再开」；其 final 通道输出立即回传父代理；消息走 analysis/final 双通道（MESSAGE | FINAL_ANSWER）。
- **共享约束（shared hint）**：① collaboration 工具不能从 `functions.exec` 内部调用（必须直接调用，防止 exec 包装绕过）；② "**All agents share the same directory**"——所有代理同容器、同工作目录，"edits made by one agent are immediately visible to all other agents"（一个代理的编辑对所有其他代理立即可见）。
- **fork 语义（model override hint）**："Full-history forks (`fork_turns` omitted or `\"all\"`) inherit the parent model and reasoning effort and do not accept overrides."（省略 `fork_turns` 或设为 "all" 即全历史 fork，继承父级模型与推理档位，不接受覆盖。）——**省略即全历史 fork**：Codex V2 子代理默认携带父级完整上下文，「子代理消息不全」的常规假设在这里默认不成立；想省 token 才显式设 `none` 或正整数。

**判断与边界**：官方的隔离方案是半隔离——隔离 token（各自上下文窗口）但不隔离世界（共享文件系统）（我的判断）。对编码任务这是合理的默认：代码库本身就是可共享状态，编辑互见兜住了「决策冲突」的最大来源，对话层隔离省下的才是纯 token；因此问题应反过来问——什么时候**不要**全历史 fork（独立调研类子任务，避免父上下文污染子代理，也省 token）。嵌套的价值由此是递归任务分解加分级压缩管道：每层代理只看到任务面而非全局面，探索噪声留在本层、结论浓缩后上行，根代理的上下文被保护，代价是 token 总量放大（定量数据见条目 5 的 Anthropic 自报数字）。「同等智能」声明是防级联退化的提示工程：避免模型默认「子代理是下级」而过度压缩任务描述。待复核：`fork_turns` 默认全历史在真实 spawn 中的行为未实测。

### 5. 多代理正反证据：Anthropic 的收益数据与 Cognition 的立场演化

**正方（Anthropic，2025-06-13，A 级来源；效果数字为自报评测）**：多代理研究系统中，子代理独立上下文＝并行＋压缩，原文 "Subagents facilitate compression by operating in parallel with their own context windows"（子代理以各自的上下文窗口并行工作，从而实现压缩）；lead 代理超 200K token 即截断，分解是刚需；多代理消耗约 15 倍 token（单代理约 4 倍），token 用量解释 80% 的性能方差，内部研究评测中 90.2% 优于单代理 Opus 4。其明确划定边界：不适合 "tasks requiring shared context or tight inter-agent dependencies (**e.g., most coding work**)"（需要共享上下文或代理间紧耦合依赖的任务，例如多数编码工作）。其 2026-04《Scaling Managed Agents》延续同一方向（90 天时效核查已做）。

**反方初版立场（Cognition，Walden Yan，2025-06-12，B）**："**Actions carry implicit decisions, and conflicting decisions carry bad results**"（行动隐含决策，冲突的决策带来糟糕结果；Flappy Bird 例子：两个子代理基于未言明的假设做出风格冲突的产物）；决策过于分散、上下文无法充分共享导致系统脆弱；主张单线程线性 agent＋压缩模型管长上下文。

**反方立场演化（按 AGENTS.md 90 天时效核查规则回查，2026-09-07 核查完成）**：Walden Yan 2026-04-22 发续篇《Multi-Agents: What's Actually Working》，10 个月后部分收回原立场：parallel-writer swarm（多个代理并行写同一产物）的警告维持不变，非结构化 agent 网络仍是 "mostly a distraction"；但承认三类「写保持单线程、其他 agent 注入智能」的模式已在生产可用：① code-review loop——干净上下文的 reviewer agent 审计 coder 输出，平均每 PR 抓 2 个 bug（58% 为严重级），且正因不共享上下文反而更强（短上下文避免「上下文腐化」（Context Rot，指上下文变长后模型表现下降））；② "Smart Friend" 能力路由——主模型遇难题外呼更强模型，跨厂商组合（Claude＋GPT）经生产验证，但弱主模型做路由会失败（SWE 1.5 教训：升级判断本身是训练问题）；③ manager delegation——manager Devin 经内部 MCP 把大任务分给子 Devin，是 map-reduce-and-manage（映射-归并-分管）形态而非自由协商。点题句："**The open problems are all communication problems.**"（悬而未决的问题全是沟通问题。）

**对 Codex 的映照（综合判断，指向条目 1、2、4）**：Codex Proactive 模式＋无深度硬闸放开的正是 parallel-writer 形态，至今仍是 Cognition 明确反对的唯一形态——这一分歧没有弥合。但 Codex 的三项工程设计各有落点：`fork_turns` 可控传播回应「消息不全」；共享文件系统回应 "communication problem"；根代理唯一持有用户目标回应「决策分散」。且 Walden 肯定的「干净上下文 reviewer 更强」恰与 `fork_turns=none` 场景互证：上下文不全在某些角色（审查、评审）里是资产不是缺陷。另：HN Algolia 检索未发现针对 Codex 递归 spawn 机制的直接讨论帖（C，检索性线索）。

## 对当前工作流的启示

- **可靠性与权限设计**：Codex 选了「递归自由＋经济闸门」路线（深度放开，控制点放在 token 预算记账与并发上限，见条目 1），Claude Code 的 Task 工具则是结构限制（子代理默认不可再嵌套）。结合 rogue agents 逃逸案例（见 [2026-09-07-热点追踪](/tracking/2026-09-07) 条目 4），结构限制在对抗性场景更硬，计量限制在成本场景更优雅——自建多代理工作流时建议两层都要。且共享工作目录的半隔离（条目 4）意味着一个被注入的子代理可以污染所有兄弟代理的工作区：失控影响范围（blast radius，失控操作的影响范围）不因上下文隔离而缩小，出站/敏感操作不能只靠上下文隔离（综合判断；见条目 1、4、5）。
- **成本**：嵌套是花 token 买覆盖面（Anthropic 自报约 15 倍、解释 80% 性能方差，见条目 5），而「拉满推理档位」在 Codex 里会同时解锁更深推理与递归委派的双重放大（见条目 2）。可迁移的做法：把「是否允许递归/并行子代理」当成显式决策而非默认，开子代理前先估 token 预算。
- **下一步验证什么**：① `fork_turns` 默认全历史在真实 spawn 中的行为复核（见条目 4）；② sol（Ultra 落 max 档）与 astra（落 xhigh）的子代理创建频率差异是否可复现——复现路径（源码推导，未实测）：用 sol/terra 应能复现同样递归，用 gpt-5.4 系应完全没有 spawn 工具（见条目 1、2）；③ Proactive 模式实际 token 放大倍率无官方数据，可自测一轮；④ 观察 Codex 的 `[agents]` 配置面（max_depth/default_subagent_model/interrupt_message）是否随企业化收权加组织级下发——趋势对照 managedMcpServers（见 [2026-09-07-热点追踪](/tracking/2026-09-07) 条目 6），并盯 Desktop/网页端 release notes 的多代理条目（见条目 3）。
