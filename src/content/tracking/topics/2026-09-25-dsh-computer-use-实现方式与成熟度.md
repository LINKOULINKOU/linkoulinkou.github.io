## 先回答问题

dsh 是 DeepSeek 的开源编码代理（命令行与桌面端）。computer use 指让模型直接看屏幕并操作本机图形界面——本工作区 [2026-09-21 专题](/tracking/2026-09-21-computer-use-它是什么与开源缺口) 把它定义为 agent 的第三条操作通道（区别于 API 与命令行），并指出沙箱与审批属于代理运行框架这一层、不属于通道本身。本篇查清的是：dsh 这一支怎么接进来的、默认能不能用、边界在哪。

- **能力全部来自外部，dsh 只做一层极薄的接入。** dsh 不实现驱动、不定义动作空间：它提供的共享服务只有一个「排他注册」动作，决策记录的原话是「这个服务不含提供方对象、共享操作类型、派发方法、会话锁或运行时选择器」。真正干活的是一套开源上游驱动（Cua Driver），dsh 通过两条路径接它：一条把它当外部子进程通过工具协议调用（驱动不在包内，需用户自行安装），另一条把它的软件开发包直接跑在 dsh 进程内（钉定版本）。
- **默认关，且没有专门的审批层。** 两套提供方式都必须显式启用：内置预设里没有任何 computer use 相关条目，工具目录里也没有它的工具。dsh 没有为它自建确认流程——唯一的确认语义来自上游驱动，而上游的默认模式是「不弹提示」，另一种模式需要显式危险开关、且在启动时固定。dsh 提示词里要求模型「优先后台投递、被拒绝不等于允许改用前台重试、一次已送达的点击不等于结果正确」，也就是把「做对没有」交给模型自己判断。
- **成熟度：实验性、无稳定版、无兼容性承诺。** 仓库至今没有稳定发布（全部为预发布），每次说明都标注实验性；官方明写的限制里包括「原生运行时崩溃可终止宿主进程」「取消不会回滚已投递的输入」「无驱动热切换、无专用权限界面、动作无抽象」「工具协议没有稳定性承诺」；唯一的平台注意事项都指向 macOS；仓库内没有 Windows/Linux 的实测证据。
- **成本细节值得单独记**：为适配 DeepSeek V4.1，图片缩放与 token 估算被改过，官方文档给了具体账——旧投影把 2000×2000 的截图按 800×800 送出、只算 422 个 token，而模型对完整网格要收 994 个；新规则按 16:9 保持 1708×966、单边上限 4096 像素、约 2 MiB 的目标。这条改动的时间（9 月 10 日）早于 computer use 首发（9 月 15 日），所以「专为它而改」是推断；但它直接决定大截图的保真度与计费，是这条通道能不能用得起的现实约束。

## 1. 它实际怎样工作：能力在外部，dsh 只做「排他注册」

一次调用的路径是：模型决定操作界面 → dsh 把请求交给当前注册的提供方 → 提供方调用上游驱动去点击、输入或截图 → 结果作为工具输出回到会话。截图不是白拿的：它需要会话侧有附件存储，还要求模型路由声明支持图片输入；文档里明确「没有驱动会默认激活」。

dsh 这一层的设计取向可以概括为「不持有能力」。上游（提供桌面动作的一侧）的实现被完整地留在上游：动作清单、坐标系、权限模式、平台支持，dsh 都不复制一份。它的文档甚至写明「这里没有额外的 dsh 动作目录」。好处是升级与适配都跟着上游走；代价是**可控点也在上游**——想知道「它能做什么、默认要不要确认」，答案不在 dsh 仓库里。

提示词里那几句约束值得单独看，因为它替代了硬校验的位置：优先后台投递；一次拒绝不授权改用前台重试；点击被成功投递不等于结果正确。换句话说，这套接入把「验证动作是否达到目的」当成模型的责任，而不是通道的保证。

## 2. 能力边界来自上游：Cua Driver 提供什么

dsh 钉定的上游是一套开源的后台驱动（trycua/cua 的驱动组件，钉定版本 0.28 系列）。它的自我定位是「给任何 agent 用的后台 computer-use 驱动：通过工具协议通信，操作原生应用而不抢焦点」——不抢焦点意味着它可以和用户并行用同一台机器，而不是接管屏幕。

- **平台**：上游声明支持 macOS、Windows、Linux 三平台，各有独立文档；需要留意的是 dsh 侧唯一的平台注意事项都指向 macOS（光标叠加层操作可能返回「设施不可用」；macOS 的光标叠加托管与桌面权限界面被推迟）。
- **动作**：上游提供十几个动作工具（点击、双击、右键、输入文本、按键、组合键、滚动、设值、调用菜单、设置窗口位置、列窗口、取窗口状态、验证状态），另有拖拽、缩放、启动应用、取桌面/浏览器状态、检查权限。
- **坐标系（决定成败的细节）**：坐标是「窗口内截图像素」，左上原点、y 轴向下；默认长边上限 1568 像素，模型看到的图与点击坐标系**同分辨率、无需换算**——这条设计把视觉定位误差压掉一层，是这套驱动比早期方案实用的地方。
- **权限模式**：默认的「标准」模式**不弹提示**；另一种不受限模式需要显式危险开关；模式在启动时固定、改动需重启；驱动自己**不渲染授权界面**。对无人值守场景，这三点合起来意味着「启用即默认放行」。

## 3. 默认状态与成熟度：实验性、默认关、没有稳定版

三处独立证据支持「默认不启用」：决策记录写明两套提供方式都不默认启用；四个内置预设配置里搜不到任何 computer use、浏览器操作或相关驱动的字段；工具目录里没有它的工具。

成熟度上，官方在四处独立位置标注实验性（发行说明、决策记录、包描述、包名本身），并给了七类自陈限制，其中对使用者影响最大的四条是：**原生运行时崩溃可以终止宿主进程**；**取消操作不会回滚已经投递的输入**（点错了就是点错了）；没有驱动热切换、没有专用权限界面、动作层面没有抽象；工具协议随上游版本走、**没有兼容性承诺**。此外「桌面是共享的，会话之间的动作不做串行化」——同一台机器上多开任务时，动作可能互相干扰。

平台证据的成色要分开看：上游台账里 Windows、macOS、Linux（X11/Sway）都有验收记录，但也存在成片「未验证」，Wayland 下的光标断言被标为不支持；而 dsh 仓库内**没有任何 Windows 或 Linux 的 computer use 实测证据**。顶层说明文件也完全不提这个功能（它显然不是门面能力），安全声明是一段全局免责：「沙箱、审批提示与权限控制能降低风险，但不保证隔离、也不阻止损害」。

## 4. 与 Qwen Code 的同类做法有何不同：分叉，还是钉版本

同一周里 Qwen Code 也发布了自己的驱动组件（比 dsh 的候选版早约三个半小时）。两者都直接集成同一上游，但路线不同：Qwen 把上游驱动**复制进自家仓库并改名**（基线是上游更早的 0.20 系列），加了自己的归一化坐标选项；dsh 不改上游，钉定 0.28 系列、要么调用用户自己装好的可执行文件。含义很直接：分叉便于深度定制与统一品牌，但会落后上游版本；钉版本跟进快、改动小，但把稳定性和平台支持完全押在上游身上。对使用者的实际差别是：Qwen 的坐标语义与上游不完全相同，迁移时要重新标定。

## 对当前工作流的启示

- **要试 computer use，先定判定器**：这套接入把「动作是否达到目的」交给模型提示去约束，没有硬校验（没有验证动作、没有回滚）。在真实机器上启用前，先想清楚谁判断「做对了」——这正好是本工作区反复出现的「先有判定器，再谈自动化」。
- **默认放行是首要风险**：驱动默认模式不弹提示、不渲染授权界面，而 dsh 没有为它加审批层；要跑就在隔离环境或专用账号上跑，不要把「有沙箱」当成默认前提（沙箱与审批属于运行框架层，这一支目前很薄）。
- **选型看控制点**：控制点全在上游驱动与模型路由声明上；要审计就得审上游的版本与权限模式，而不是只看 dsh 的说明。
- **未决问题**：dsh 是否把 computer use 移出实验状态；上游在 Wayland 与 Windows 上的光标断言何时补齐；dsh 是否补一层自己的确认或审计；上游版本的坐标系与 Qwen 分叉的差异带来的迁移成本。

## 实现资料（仅在需要接入或复现时）

用途说明：以下为实现级标识，供需要复现或审计的人核对；普通阅读不需要。

- 两条接入路径的包名：MCP 路径为 `@deepseek-ai/dsh-experimental-computer-use-cua-driver-mcp`（以子进程方式调用用户已安装的 `cua-driver`，配置字段为命令与参数，工具命名空间 `mcp__cua-driver-mcp__`）；原生路径为 `@deepseek-ai/dsh-experimental-computer-use-cua-driver-native`（进程内依赖钉定 `@trycua/cua-driver@0.28.0`，无配置字段，命名空间 `cua_driver_native__`）。
- 上游钉定版本与坐标：`cua-driver-rs-v0.28.0`；坐标语义为窗口局部截图像素（左上原点、y 向下），截图默认长边上限 1568 像素（`max_image_dimension`）；权限模式 `standard`（默认、无提示）与 `unrestricted`（需 `--dangerously-bypass-approvals`），启动时固定。
- Qwen 侧集成：驱动 vendored 在 `packages/cua-driver`（基于上游 `cua-driver-rs-v0.20.0`），改名 `qwen-cua-driver`，注册命令 `qwen mcp add cua-driver qwen-cua-driver mcp`，另有 `CUA_DRIVER_RS_COORDINATE_SPACE=1` 提供 0–1000 归一化坐标。
- 图片投影规则（V4.1 适配）：`.agents/notes/implemented/bug-fix/2026-09-10-deepseek-v41-request-image-projection.md`；旧投影 2000×2000 → 800×800、计 422 token（完整网格 994）；新规则 16:9 保持 1708×966、单边上限 4096、约 2 MiB。
