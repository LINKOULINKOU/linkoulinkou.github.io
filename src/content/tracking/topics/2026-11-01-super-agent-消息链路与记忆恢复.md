DeepSeek 的 Super-agent 接入群聊、Issue、PR 等已有工作场合，用讨论串保留消息归属，用工单组织持续推进的任务，再交给独立会话执行。Router 在内部判断新任务、建立关联和处理必要协调；后续讨论通过订阅继续送达执行者。

人可以在飞书里提出需求，到 GitHub 上继续评审；后台同时推进几项工作。系统维护讨论、任务和执行会话之间的联系，让工作沿这些关系持续进行。

下面先分清这几层关系，再跟着“增加字体设置”走一遍消息链路和历史回查。最后把它放回仓库、机器、权限和规范共同组成的工作现场，说明恢复机制怎样保存任务进展与过程经验。

## 1. 讨论、工单与执行会话怎样划分工作

一项工作在系统里有几种不同的身份：

| 层次 | 表达的内容 | 字体设置的例子 |
| --- | --- | --- |
| 接入来源（Source） | 监听范围、接入身份及读位点 | 接入编辑器仓库和相关飞书群 |
| 消息串（Thread） | 同一话题下按时间排列的事件 | 飞书里的字体讨论，或字体 PR 的讨论 |
| 工单（Ticket） | 已接下的任务、授权范围和持续状态 | 完成字体设置这项工作 |
| 执行会话（Worker） | 当前承担技术工作的执行者 | 在独立目录里调查、修改和验证 |

Thread 为消息提供讨论归属，Ticket 为工作提供长期身份。讨论可以先存在，系统在其中识别出任务后再建立工单。工单随后订阅有关的讨论串，持续接收新输入。

它们是多对多关系。一张工单可以同时连接原飞书话题和实现它的 GitHub PR；一个讨论串也可以关联多张工单。读取 Thread 时看到的工单列表，来自这些关联关系。

```text
飞书里的字体话题 ─┐
                  ├─ 字体设置工单 → Worker
GitHub 的字体 PR ─┘
```

这种组织保留了外部场合的线索：人在具体话题或 PR 下发言，消息随之带上所属 Thread。已订阅的后续消息可以按程序记录的关系送达。

Router 是内部调度层。用户仍可以在不同群、话题和 PR 中与系统交互；原型用一个常驻主会话实现调度，与用户面对哪些交互入口是两层安排。Router 主要在新工作出现、归属尚待确定或需要协调时作出判断。

依据：[消息串、工单与订阅的领域关系](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/001-domain.md#L25-L43)、[设计文章第 2 节：Router 与 Worker](https://www.chaincatcher.com/en/article/2300676)。

## 2. 一条飞书消息怎样走到代码修改

假设一位有发起工作权限的成员在飞书群里说：

> @助手，给编辑器增加字体设置。

以下消息和编号均为讲解用的假设，流程依据公开原型。

### 接入器把消息整理为事件

负责接入外部平台的适配器叫 **Source**。GitHub、飞书分别有自己的接入实现；具体配置决定监听范围、使用哪个 CLI 和账号、是否启用。

公开原型面向一个 GitHub 仓库，飞书配置可以包含多个群。一份 Source 实例就是一份这样的接入配置，里面维护账号身份和读位点。

接入器收到消息后，整理发送者、正文、时间、是否 @ 助手、所属话题和回复地址，生成一条不可变事件，叫 **Trigger**。同一话题下的事件按时间组成一个**消息串（Thread）**。GitHub 上的 Issue 或 PR 讨论也有相应的消息串。

Source 记住自己读到了哪里，并过滤自身账号发出的消息。这样，系统能持续接收外部事件，也能避免把自己的回复再次当作请求。

### 程序检查准入，Router 判断如何处理

新任务进入**评估流程（Eval）**后，先执行代码层的**准入检查（Gate）**。它检查来源和发送者，结合是否提及助手、接收表等配置，决定这条消息的处理强度。

通过准入的候选卡片进入**调度会话（Router）**。Router 里的模型读取卡片，判断要开新任务、附到已有任务、停止工作，还是忽略这段讨论。需要更多背景时，它会调用读取工具。

原型把两类输入分开处理：

- **明确请求（explicit）**：由 Router 理解后直接作路由决定。例子里的授权成员 @ 助手提出需求，属于这条路径。
- **推断候选（inferred）**：用于从环境讨论中识别工作机会。要接单时，Router 还需执行完整的模型研判（Assessment），检查主动规则和改动意图。

这次 Router 决定接下“增加字体设置”。系统保存一条**决定（Decision）**，同时创建三类记录：

| 记录 | 在这项工作里的作用 |
| --- | --- |
| 工单（Ticket） | 保存任务身份、输入、状态、关联讨论和执行记录 |
| 授权（Mandate） | 保存接单依据、允许范围、所用策略版本及命中规则 |
| 派工（Assignment） | 记录这一次由哪个执行器推进工单 |

一张工单可以经历多次派工，授权记录说明工作依据，派工记录说明当前执行关系。

### Worker 接手技术工作

系统为工单准备独立目录和**执行会话（Worker）**。Worker 读取原始需求，调查代码，选择实现方案，完成修改和验证。

技术拆解主要发生在这里。Router 的提示词要求保留原始请求和必要的路由信息，将实现方案留给 Worker。工单因此可以从“调查字体显示错误并修复”这样的目标开始，执行者再决定怎样定位和修改。

复杂任务还可以由 Worker 在内部调用子代理。外层仍然跟踪同一张工单。

### 报告和回复回到原对话

Worker 用报告提交进展、结果或需要人决定的问题。Router 通常收到工单卡片、状态和简短摘要，再按原始对话位置组织交接。普通进度留在内部，需要决策或有可交付结果时再通知人。

对外消息先进入**待发送队列（Outbox）**，保存发送状态，再由平台的写回适配器 **Channel** 发到飞书或 GitHub。发送失败可以重试，同一工单在同一对话中的消息按规则维持顺序。

整条新任务链路如下：

```text
Source 接收消息 → 整理为 Trigger → 归入 Thread
→ Gate 准入 → Router 判断与路由 → 保存 Decision
→ 创建工单、授权和派工 → Worker 修改与验证
→ Worker 报告 → Router 对外交接 → 队列发送 → 原平台收到回复
```

这条链路里，程序负责接入、记录和投递，Router 负责判断与协调，Worker 负责具体执行。

依据：[领域模型](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/001-domain.md#L5-L43)、[两类候选的处理](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/002-authorization.md#L83-L105)、[派工职责](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/prompts/dispatch.md#L5-L14)。

## 3. 后续讨论怎样接回正在进行的工作

Worker 开始修改后，群里又补了一句：

> 字号也要能调。

此时工单已经**订阅（Subscription）**了这个消息串。程序查到订阅关系，便把新消息直接送给该工单的 Worker：

```text
新消息 → 所属消息串 → 订阅它的工单 → 正在跟进的 Worker
```

这种订阅是持久记录。它连接工单和消息串，并支持多对多关系：一张工单可以跟进飞书话题和 PR，一个讨论串也可以被多张工单订阅。

对于已经归属工单的人类续话，Worker 直接判断怎样处理，Router 收到跟进提示。这样，补充要求、评审意见和澄清可以持续到达执行者，省去每句话都重新判断归属、再转发一次的步骤。

Worker 开出 PR 后，Source 可以把 PR 关联到这张工单。人再到 GitHub 评论“改成跟随系统字体”，消息就能沿 PR 的订阅关系到达原 Worker。跨平台的连续性主要来自这些工作对象之间的关联；原型分别管理各来源的身份。

订阅还承担上下文分发：机器人评论、CI 结果等可以直接送给正在工作的 Worker。它们也会独立经过新任务评估入口，由准入规则决定后续处理。

每张工单仍按原授权范围工作。Worker 遇到超出范围的新请求，会交回 Router 处理。另外，执行者可以只为了解背景而订阅相关讨论；这类“上下文订阅”只提供材料，不接管那里的人类请求。

依据：[订阅和续话规则](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/002-authorization.md#L18-L44)、[收件与投递实现](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/intake.ts#L30-L59)。

## 4. 沿工作关系，怎样一步步查回历史

字体工单同时关联飞书话题和 GitHub PR，系统因此有了一条从当前评审回到原需求的路径。工单还连接输入、报告和执行历史，需要背景时可以继续沿这些关系读取。

这就是**链式回查（Chain of Recall）**：模型从当前线索出发，每读到一个对象，再沿它返回的 ID 和读取入口取下一份材料。下面先看这些材料的存放位置，再实际走一遍从 PR 评论回到飞书决定的过程。

### 信息分别放在哪里

这套系统使用几类存储：

| 位置 | 保存的材料 |
| --- | --- |
| 工单数据库 | 事件、消息串、工单、授权、派工、输入、报告及其关联 |
| DSH 会话记录 | Worker 的消息和工具结果等执行历史 |
| 工作目录和 Git | 实际文件、修改和提交 |
| GitHub、飞书 | 可通过适配器读取的原平台记录 |

模型当前窗口只装入本轮需要的一部分。工具返回的对象会带摘要、ID 和后续读取入口，让模型逐步展开。

### 从 GitHub 评论查回飞书里的决定

继续使用字体设置的例子。假设 PR 已经关联到工单，工单也保留了原飞书话题。现在 Router 需要查清这项工作与早先讨论的关系。

这里用 `T3` 表示当前评论，用 `K17` 表示工单，都是讲解用编号。读取统一通过 `orchestrator_read` 工具，`resource` 参数指定要读的对象。

第一步可以读取 `trigger/T3`。返回里包含评论正文、所属消息串，以及已经投递到哪些工单等信息。拿到消息串标识后，再读取 `thread/<消息串标识>`。

完整展开过程如下：

| 步骤 | 读取对象 | 这一步得到什么 | 用什么进入下一步 |
| --- | --- | --- | --- |
| 1 | 当前 GitHub 评论 | 正文、所属 PR 消息串、投递去向 | PR 消息串标识，或已知工单 ID |
| 2 | PR 消息串 | 话题信息、关联工单卡片、消息列表 | 工单 `K17` 的 ID 和读取入口 |
| 3 | 工单 `K17` | 原请求 ID、允许范围、关联讨论串、输入和报告摘要、会话历史入口 | 原飞书话题标识 |
| 4 | 原飞书消息串 | 按页列出的消息 ID、发送者、时间和预览 | 当时讨论字体方案的那条消息 ID |
| 5 | 具体消息 | 保存的正文，以及适用的回复、邻近消息或原平台读取线索 | 信息足够时结束；长内容继续翻页 |

于是，一次跨平台回查可以走成：

```text
GitHub 评论 → PR 讨论串 → 工单 → 原飞书话题 → 当时的具体消息
```

每一步的下一跳来自上一步的工具结果。例如，工单页给出原消息 ID，模型便知道应该去读哪条消息；消息串页给出各条预览，模型再选择与当前问题有关的一条。

已有信息足够时可以少走几步：当前卡片直接带了工单 ID，就从工单开始；之前已经读过相关输入，就可以利用现有上下文。工单页提供的是原请求的 ID 和读取线索，完整正文按需另取。

底层是一个有分支的引用图。所谓“链”，就是模型这次为了回答问题，在图中实际走出的路径。

### Worker 怎样查自己试过的方案

执行者还可以沿工单进入自己的会话历史。例如，它需要回顾“之前为什么放弃另一种字体实现”，可以走：

```text
自己的工单 → 会话历史条目列表 → 某条助手消息或工具结果
```

原型提供两个具体入口：

- `ticket/<id>/transcript`：先给倒序的历史条目预览，并附单条读取地址。
- `ticket/<id>/message/<n>`：展开指定条目。测试失败的具体输出可以在这一步读取，长文本继续分页。

这份历史投影包含用户消息、助手消息和工具结果，过滤 reasoning 块。它让已经记录下来的过程证据可再次进入上下文。

Router 在工具层面也有读取这些历史的入口。它日常主要使用工单摘要和报告，提示词将技术调查和实现方案留给 Worker。两层会话因此采用不同的信息粒度：调度层看工作归属和结论，执行层按任务需要深入细节。

依据：[对象卡片携带的引用](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/cards.ts#L59-L76)、[消息串读取](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/resources.ts#L133-L148)、[工单与历史读取](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/resources.ts#L235-L291)、[历史事件投影](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/context.ts#L28-L32)。

### 上下文按预算装入，缺少的部分再读

文章把这种组织方式称为 **Inline & Spill**：常用材料直接放进当前输入，长内容放在窗口外，通过摘要和指针保留读取入口。

公开原型的预算很具体：

- 主动候选完整研判时，当前事件正文最多内联 4000 字符。讨论窗口包含最初五条、事件前后各五条；通常每条最多 400 字符，前后最近各两条放宽到 1200。其他已加载消息可以只留 50 字符预览。
- Worker 首次派工内联的任务描述最多 1500 字符。源事件和后续 Trigger 输入卡片的正文最多 600 字符；后续 Input 消息整体超过 1500 字符时，还会截断并给续读入口。
- Router 收到的 Worker 报告摘要最多 600 字符。
- 通用文本读取默认一页 4000、最多 8000 个 UTF-16 单元；列表默认 20 项、最多 50 项，通过返回的偏移量继续读。

所以，模型拿到的卡片通常长这样：一段能直接使用的内容，加上“这里还有多少内容、到哪里继续读”。模型根据当前问题决定是否展开，信息足够时停止。

这里有两条互补的信息流：**订阅负责把新消息推给已有任务，链式回查负责把过去的材料拉回当前上下文。**

回查依靠已保存的关系和可读取的内容。PR、工单、飞书话题之间的联系，需要在工作过程中建立；模型选择哪条分支、是否继续翻页，也影响最终拿到的信息。

读取范围按角色设置。Router 可以查看全局工单关联；Worker 的应用读取接口主要面向自己的工单及相关讨论，并隐藏其他工单的 ID。实际部署另外需要考虑执行环境隔离：当前原型的会话拥有操作系统用户权限和 shell 能力。

依据：[上下文预算与读取范围](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/007-architecture.md#L534-L593)、[输入投递的整体截断](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/dsh.ts#L329-L342)、[部署权限](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/006-deployment.md#L13-L19)。

## 5. 主动工作从哪些环境信号开始

事件入口让系统持续接触团队的工作环境。在此基础上，模型可以从讨论中识别已经形成的改动意图，按规则接单。

例如，有人说“这个按钮文字有点怪”，另一人接着说“就改成‘保存’吧”。讨论已经给出了具体目标，即使没有 @ 助手，也可能形成候选。

公开原型的主动范围主要是小型内部修改。默认规则包括文案和局部视觉修正；研判要求讨论表达实施意图、目标有明确依据，并且产品或设计方向已经确定。新行为、新交互和跨模块重设计留在明确派发的任务路径中。

Source 配置负责观察范围。GitHub 的 `repository` 指定仓库，`cli` 指定使用哪个已登录的 CLI，`pollSeconds` 控制轮询间隔。几个 `observe` 字段扩大采集范围：

| 字段 | 额外接收的事件 |
| --- | --- |
| `observeIssues` | 未 @ 助手的新 Issue |
| `observePulls` | 未 @ 助手的新 PR |
| `observeComments` | 未 @ 助手的评论和代码评论 |
| `observeCi` | 默认分支 CI 的失败和恢复 |

账号通知、已订阅讨论和工单关联 PR 的 CI，还有各自的采集路径。

事件进入后，主动接单由策略控制：

| 模式 | 处理方式 |
| --- | --- |
| `off` | 关闭推断候选处理 |
| `observe`，默认 | 研判并记录“本来会接”，供人观察策略效果 |
| `auto` | 研判通过后创建工单并派工 |

明确请求在三种模式下都可以处理。实际接起一项主动工作，需要观察范围、准入规则、模型研判和自动接单模式共同配合。

文章进一步探索了投机执行：系统在团队讨论期间先做一些后台尝试，在有用的结果出现后再交付。公开原型目前给这类工作设了较窄的范围，适合从小型、目标清楚的改动开始。

## 6. 把讨论和工单放回完整的工作现场

执行一项工程任务，还需要知道仓库在哪里、使用哪台机器、允许操作什么，以及遵守哪些规范。这里把这一组材料称为**工作上下文（Working Context）**，用它描述工作的完整现场。

可以按几个具体问题展开：

| 问题 | 需要的材料 |
| --- | --- |
| 在哪里做？ | 仓库、机器、目录、依赖和工具链 |
| 以什么身份做，能做什么？ | 接入账号、执行凭据、工具权限和任务授权范围 |
| 按什么规矩做？ | 仓库规范、评审要求、人工确认条件 |
| 当前以什么为准？ | 需求、已确认决定、进度、证据和已尝试方案 |
| 跟哪些人或执行者协作？ | 任务分工、讨论位置和交接关系 |

一个项目可以同时包含许多话题、PR 和工单，它们使用相同的一部分现场信息，并各自保留任务目标与过程记录。Thread 负责讨论归属，工单负责工作身份，工作上下文把这项工作所用的环境、规则和历史一起纳入视野。

例如，字体设置工单关联飞书和 PR，执行者在编辑器仓库的目录里修改代码，遵守仓库规范，以配置的账号提交。人打开 PR 讨论时能确定当前议题；系统还需按照工单和部署配置取得正确的执行现场。

原型已经分别用来源配置、执行环境、授权记录、提示词和历史对象表达其中的若干部分。“工作上下文”在这里是帮助理解整体关系的分析概念，相关信息仍分布在这些具体机制中。

群聊可以成为人选择工作现场的可见入口。项目群绑定仓库、文档和环境后，人在群里发言便提供了明确的项目线索；具体话题和工单再细分正在推进的工作。执行侧的权限由账号、工具和环境配置落实。交互位置、任务归属、执行边界因而可以分别管理，再通过显式关系连接起来。

更长期的状态维护也发生在这个层次。飞书先决定方案 A，PR 后来确认方案 B，回查能找回两次讨论。进一步管理多项并行工作时，还需要表达当前采用哪个决定，以及哪些任务需要收到变化。这可以作为现有引用与投递机制继续发展的方向。

依据：[部署中的仓库、账号与执行环境](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/006-deployment.md#L143-L157)、[授权与输入的领域关系](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/001-domain.md#L25-L43)。本节的整体划分及后续方向是基于这些机制的分析。

## 7. 执行中断以后，怎样继续这张工单

原型将任务状态保存在会话之外。数据库里记录了工单、授权、派工、输入、报告、订阅和待执行操作，系统重启后可以据此找到仍需推进的工作。

### 会话历史还在时，沿原现场恢复

正常重试会创建新的 Assignment，沿用原 Worker 会话、目录、分支和 PR。

宿主重启后，中断的派工会附恢复说明重新启动。说明要求 Worker 检查目录、Git 历史和 GitHub，再决定下一步，尤其注意已经发生的外部操作。系统还保存输入的接收记录，重投上轮未实际进入会话历史的输入。

因此，一次运行停止以后，后续执行可以继续利用原来的消息、工具结果和文件现场。模型重新读取这些材料，重建工作上下文。

### 会话被删除时，重新建立任务入口

源码也处理了会话缺失：找不到原会话时，会按原 ID 创建新会话。在后续派工启动时，如果发现最初的任务消息缺失，会补发原任务简报、源事件和最初批次。

单独的输入投递也能触发会话重建，这条分支继续投递当前输入；原任务简报的补发发生在派工启动分支。

重建后，执行者仍可以通过工单读取原需求和报告，通过目录检查已有修改。任务的身份、允许范围和当前现场由这些材料连接起来。

### 任务内经验怎样留下，目前还有待补全

执行过程会积累比进度摘要更细的信息：某个工具参数已经试过无效，方案 A 因兼容性问题被放弃，文件已修改但测试尚未运行，某项外部操作已执行而尚未汇报。这些都是任务内经验。

当前主要有三种载体：

- 会话历史保存消息和工具结果，可按需回读。
- 报告保存模型写出的进展、证据和阻碍。提示词要求报告已经尝试的补救措施；同一次 Assignment 的后续报告会替换其当前报告。
- 目录和 Git 保存文件状态与修改结果。

原型也使用底层 DSH 的上下文压缩和工具结果裁剪。模型通过摘要继续工作，需要时再展开仍然存在的历史。

若会话记录被彻底删除，任务简报和文件现场只能保留其中一部分经验。比如旧 Worker 试过 A，回退后改用 B，放弃 A 的理由只写在工具调用过程里；新会话可以看到 B 的文件，却可能重新尝试 A。

在已检查的实现范围中，还没有看到一套独立于原会话历史、持续保存并恢复这些重要过程事实的完整机制。后续可以围绕失败尝试、未完成操作、已发生的副作用和待执行验证，设计更明确的记录与恢复方式。

这也是链式回查与经验恢复的连接处：**回查负责沿引用取回现有材料；保住过程经验，还需要让重要材料先被记录、持续保留，并在恢复时重新读入。**

依据：[重试和重启](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/docs/003-execution.md#L118-L159)、[会话缺失时重建](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/app/sessions.ts#L137-L159)、[派工时补发任务](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/dsh.ts#L449-L468)、[输入投递时重建](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/executor/dsh.ts#L299-L342)、[阻碍报告要求](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/prompts/work.md#L21-L36)、[报告更新](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/src/core/assignments.ts#L110-L127)、[压缩配置](https://github.com/deepseek-ai/dsh-superagent-prototype/blob/6337fc823ce20251c8de8085948165c81aaa701e/cordis.patch.yml#L79-L95)。

## 8. 把它放回团队的工作方式里看

这套原型来自团队日常开发实践。它在 coding agent 之上固定了一种分工：外层接收环境事件、组织任务和对外交接，内层在独立会话里完成技术工作。

与常见 Agent Team 相比，它主要组织多项持续到来的工作。每项工作内部仍然可以使用团队或子代理。文章也承认，当一个 Team 的主会话只负责沟通和派发、成员各自推进任务时，两种组织形式会很接近。

这种分工适合工作自然发生在群聊、Issue、PR 和 CI 中，任务之间相对独立、结果容易验证的研发场景。讨论越能形成清楚的目标，系统越容易接住并推进。技术细节可以交给 Worker 调查；产品方向和验收判断仍由相应的人承担。

任务之间的依赖增多时，Router 需要理解更多跨任务信息。它的判断能力、工单卡片提供的信息，以及回查是否到位，都会影响调度质量。这是框架后续扩展的一条主线。

### 初步实验展示的是调度效果

作者使用约 300 条消息、约 20 个工作请求，每种配置运行 5 次，以耗时工具替代真实编码。Super-agent 的任务完成时间中位数（p50）和 95 分位（p95）为 12.4/15.7 分钟；单 Session 加子代理工具的中性提示基线，p95 为 29.5 分钟，5 次都没有实际调用子代理。

给单 Session 换成“优先委派”提示后，5 次中有 4 次使用子代理，完成表现明显改善，另一次自行执行形成长尾。这个对照说明，把分工固定在系统里，可以减少模型临场选择工作方式带来的波动。

订阅直通主要节省调度开销。去掉直通后，作者称完成时间基本一致，读缓存 token 从 2323 万增至 3177 万，约增 37%。多会话方案也消耗了更多读缓存 token，以额外开销换取并行组织能力。

这些是作者在合成负载和简化环境下的初步结果，测量范围集中在调度与协作。真实编码能力、生产交付效果还需要相应的实践材料。

### 公开版仍是一套继续发展的框架

文章讨论了计算、状态和执行环境分离，以及独立 Watchdog 检查任务进展。公开版目前主要按独立 DSH profile、本机进程和 tmux 部署，文档还提供了在另一个 profile 中创建定时巡检任务的方法。完整的云端计算、端侧 daemon 和跨设备 BYOM 属于更广的设计方向。

从使用体验看，人可以在已有工作场合提出要求，通过具体话题继续讨论，在需要决策时回来。Thread 保留讨论归属，工单维持工作身份，订阅投递后续消息，回查带回历史背景。执行会话承担技术工作，随任务推进而启动、等待或恢复。

这套探索已经给出了清楚的消息流和任务组织方式。后续的发展可以沿两条线继续：一条是把仓库、环境、权限和当前决定之间的关系表达得更清楚，另一条是让任务内经验在长时间运行和执行恢复中持续保留下来。
