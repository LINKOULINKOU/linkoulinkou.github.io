## 先回答问题

**Claude Managed Agents 是 Anthropic 平台上的一项托管服务**：把一个代理「跑起来」所需的整套运行环境——模型调用循环、代码沙箱、工具执行、会话存储、定时调度、持久记忆、凭据保管、花费封顶——都放在 Anthropic 的基础设施上。你只声明「代理长什么样、什么时候跑、能碰什么」，运行与治理由服务负责；本机不需要常开任何东西。它处于 beta（所有请求需带 `managed-agents-2026-04-01` 的 beta 请求头；4 月 8 日官方工程博客介绍了它的设计），面向长跑任务与异步工作。

10 月 8 日，官方开发者博客用它做了一个完整参考实现：每个工作日早上读指定的 Slack 频道与 GitHub 仓库，挑出「今天你会行动的事」，发一份短简报到一个频道。这篇文章值得展开，不是因为「定时」新鲜——主流编码代理基本都带上了自动化功能，连「跑在云端、本机不用开」也不再稀奇——而是因为它把定时代理真正的难点逐条写成了机制：**没人看着的时候怎么失败**。README 里有一句可以当全文主旨：大部分设计都是关于没有人看着的时候如何失败得好看。

把失败拆开看，是三类，各自对应一组机制：

| 失败 | 表现 | 对应机制 |
|---|---|---|
| 丢 | 消息漏报，且没人发现 | 每个来源一个游标（bookmark，记录上次读到哪条）；读不到 ≠ 没有新消息，如实上报 |
| 重 | 同一内容报两次 | 台账（ledger，已报条目的清单）；发布前按刊头查重 |
| 误记 | 没发出去却被记成发过，或反过来 | 只有平台明确确认才算发出；结果不确定时记「也许发过」，其余状态一律不动 |

整体取向是**宁重勿丢**：不确定的结果不猜、不抹，显式记进运行记录，把最坏情况压到「可发现的重」而不是「无人知的丢」。

**证据边界先说清**：本篇材料全部来自官方——服务文档、官方文章与示例代码、工程博客；我们没能实测（beta 需 API 账号），也没找到独立第三方复核。下面讲的是「官方文档承诺的行为」与「官方示例的写法」，不是经过验证的运行事实；官方没说明的地方，文中直接写不知道。

## 1. Claude Managed Agents 是什么

一句话：**你不再自己写代理循环、搭工具执行层，而是把「运行一个代理」交给平台**。官方把它和 Messages API（原始的模型调用接口）的对比收在一张小表里：Messages API 是「直接调模型」，适合自己写代理循环、要细粒度控制；Managed Agents 是「跑在托管基础设施里的、预构建、可配置的代理 harness」，适合长跑任务与异步工作。

它具体托管这些（官方文档口径）：

- **运行循环**：调用模型、把工具调用路由到对应基础设施，内置提示词缓存与上下文压缩等优化；
- **沙箱**：每次运行的隔离执行环境——默认在 Anthropic 云上，也支持跑在你自己基础设施上的自托管沙箱；代理在里面跑命令、改文件；
- **工具**：内置 shell、文件操作、网页搜索与抓取，以及接入外部工具服务（MCP，模型上下文协议）的能力；
- **会话**：一次运行在服务端有完整记录，事件历史持久、可完整取回，会话在暂停后可干净恢复；沙箱状态与产物同样存在服务端；
- **调度**：定时部署——用 cron 表达式加时区定义「什么时候跑」，到点平台自动启动会话；
- **记忆**：记忆存储，一组跨会话持久的文件目录，运行时挂进沙箱（挂载点、只读或读写都是声明出来的）；
- **凭据**：凭据库，真实密钥不进沙箱，出沙箱的请求由平台把占位符替换成真值；
- **花费**：预算，按公开列表价持续计费，达到上限就暂停。

**怎么用**：控制台、API/SDK，或官方命令行（`ant`）。命令行是声明式的——代理（模型、工具、指令）、环境、记忆、凭据、部署各写成一份文件，`ant apply` 一次创建全部资源并把 ID 记进一个锁文件；官方还配了一个 Claude Code 技能，在对话里说一句，它就读这套指南、生成这些文件并替你创建。

**为什么长这样**（来自 4 月 8 日的工程博客）：服务把代理拆成三个可独立替换的接口——**会话**（事件只追加的日志）、**运行循环**、**沙箱**（执行环境）——并把「大脑」（模型与循环）和「手」（沙箱、工具）解耦。官方称它是「元 harness」：对具体用什么运行框架不做预设，Claude Code 本身就是一种可以放进去运行的良好 harness。收益是结构性的：容器坏了，循环把失败当成一次工具调用错误交回模型，需要时按标准配方重建新容器（不再「养宠物」）；循环自己崩了也不重要——会话日志在它外面，从最后一个事件恢复即可；**凭据拿不进沙箱**（Git 凭据在初始化克隆时接好，MCP 调用由沙箱外的一个代理去凭据库取密钥），提示注入因此碰不到真实 token。

**要明确的限制**：整个服务处于 beta，行为可能调整；服务端有状态（会话与沙箱状态存 Anthropic 侧、可随时删除，但因此不适用「零数据保留」与 HIPAA 口径）；另有 Claude Platform on AWS 版本（功能可用性与会话行为有差异）；「自托管沙箱」可选；预算按「公开列表价」计，与真实账单的差异官方没有展开。

| 你声明（文件 / API） | 平台负责 |
|---|---|
| 代理：模型、工具、指令 | 运行循环、提示缓存与上下文压缩 |
| 环境：沙箱、网络白名单 | 起沙箱、执行工具、按白名单放行网络 |
| 记忆：挂载哪些存储、只读或读写 | 每次运行挂载、跨运行持久（写入生成版本记录） |
| 凭据：凭据库与可用于哪些主机 | 请求出沙箱时替换真实值 |
| 部署：cron、时区、预算、首条消息 | 到点启动新会话；超预算暂停而非失败 |

## 2. 和「普通定时」的区别

先把话说白：**「定时」本身没有稀缺性**。主流编码代理基本都带自动化——Codex 有 Automations，Claude Code 有 cron/loop 与 hooks 机制，DeepSeek 的 dsh 加了定时任务与提醒（可查运行记录、重启保留、最快每分钟一次），Trae 把自动化任务写进了合并后的平台能力清单；连「跑在云上、本机不用开」也在变成标配（OpenAI 的 Dots 自带云电脑常驻运行，Google 的工作代理以「关掉笔记本任务继续跑」为卖点）。所以这项服务卖的不是「会定时」，而是触发之后的三件事：

**其一，它是一个功能，还是一层服务。** 产品自带的自动化属于那个产品：在它的界面里开关，按它的方式执行。而这里的代理、环境、记忆、凭据、部署（含时间表）是**五种有 ID 的平台资源**，用声明文件或 API/SDK 管理，可以被别的程序创建——官方就提供了 Claude Code 技能来自动生成整套配置。差别在于：产品自动化回答「让我的代理定时干这件事」，这一层回答「我要一个托管运行、按时自跑的代理」——前者是使用者的开关，后者是可以嵌进系统的基础设施。

**其二，触发之后起的是一次完整的新运行，而不是接着上次的环境跑。** 每次调度触发，平台起一个新会话：新沙箱、新的运行循环，跑完即停；上一次运行的任何东西都不在场，除非你显式挂载了记忆存储。在你自己机器上跑 cron 脚本时，磁盘、配置、登录状态都是现成的；这里每次是一张白纸——跨运行的连续性从「环境默认带着」变成「必须声明」。这正是本篇后半失败语义的起点：**没有环境惯性可以依赖，状态全靠自己写。**

**其三，治理是平台执行的资源语义，而不是产品设置或自己的补丁。** 预算：达到上限的运行被暂停并带明确的停止原因，不是失败也不是继续烧钱（同期 Google 的工作代理也上了「实时支出上限、触发即暂停」，说明这类机制正在成为共识）；凭据：真值不进沙箱、在出口替换——这是结构性设计，不是权限开关；网络：白名单默认拒绝；记忆：只读挂载在文件系统层强制。产品自动化里，这几件事通常还是「你自己在脚本、环境变量和 CI 设置里安排」。

一句边界：这不是「有」和「没有」之分，而是一条光谱——产品自动化也在上云、也在补治理。真正的差别可以压成一句：**触发器越来越像，不同的是触发之后，状态、凭据、预算归谁管。**

## 3. 参考实现：一个「定时代理」在这个服务上的完整形状

参考实现（daily-brief）是给这个服务写的最小可用自动化：读两个来源、挑事、发一份简报。README 一句话概括了它的构成——**代理、沙箱、时间表、记忆、花费上限和凭据库，一共六个文件**，交给 `ant apply` 一次应用：代理（模型、工具、八条运行步骤）、环境（沙箱与网络白名单）、部署（时间表、时区、预算、首条消息）、两份记忆存储（偏好只读、状态读写）、凭据库（容器）；外加一份 Slack 应用清单，凭据由安装脚本另行加入（设计上不让密钥经过创建流程）。配置好后，**自动化按时间表跑在 Anthropic 的基础设施上，你机器上不需要留任何常驻进程**。

这个形状里有两点直接决定了后面全部的失败语义：

1. **每次调度触发是一个全新的会话**：新沙箱、没有上一次运行的任何内存。跨运行的连续性不靠平台记忆（平台只保证存储持久），而靠代理自己往记忆存储里写文件——参考实现里就是几个文本文件：`bookmarks.json`（每个来源读到哪）、`ledger.md`（已报过什么）、`notes.md`（对每个来源的笔记）、`proposals.md`（偏好修改建议）、以及每次运行的记录（`runs/<日期>.md`）。
2. **平台管运行，不管语义**：到点把会话拉起来、把记忆挂好、把凭据换好、把预算卡住，这些是平台的事；**读什么、报什么、记什么、什么算发过了，全是代理自己的事**——写在 agent.md 的八条运行步骤里。失败语义没有平台默认值，它是自己设计的。这就是一份「参考实现」值得写专题的原因。

## 4. 游标：为什么不用「最近 24 小时」

最常见的写法是让代理「读最近 24 小时」。文章直接点出它错在哪：一次运行跑晚了，24 小时窗口盖不住空档，中间的内容永远漏掉；跑早了，窗口与前一次重叠，同一批内容再报一遍。定时任务的启动时间本来就会漂移（排队、限流、机器故障），所以固定窗口的漏与重不是偶发，是常态。

参考实现的替代方案是给**每个来源各记一个游标**：运行结束时，把本次读到的最新条目的时间戳写回一个单独的文件（每来源一条，如 `"slack": "2026-09-14T13:02:11Z"`）；下次运行从游标处开始读——实际读取时还会往前放松十分钟，容忍条目排序与时钟的小抖动。这样窗口由「距上次运行多久」推算：上次跑晚了，这次窗口自动变长，什么都不漏；跑早了，窗口自动变短，什么都不重。

状态放在哪也有讲究。整个「状态」是一组文本文件，由平台挂载进每次运行的沙箱（sandbox，一次运行使用完毕即弃的隔离执行环境）的固定目录下，运行之间保留；代理用普通文件工具读写。只读存储的拒绝写在文件系统层——这一点后文还会用到。第一次运行时这些文件还不存在，约定是：读最近 24 小时，同时把文件建起来。

最容易骗过运维的一种失败是**把「读不到」当成「没有新消息」**。文章举了具体场景：某个 MCP 服务器（模型上下文协议连接的外部工具服务）挂掉或 token 过期时，运行照常开始，只是缺了那套工具；会话日志里记了错误，但代理自己什么都看不到，它最自然的输出就是「今天没什么新消息」。参考实现的 agent.md 用三条规则修这个洞：读失败的来源**游标原地不动**（下次运行自然重读，不丢）；简报用其他来源照常写；末尾用一行点名读不到的来源（「本次拉取不到 PR」）。另有一条同源细节：Slack 的调用即使 HTTP 返回 200，body 里没有成功确认也算读失败——「不要把失败读成安静」在协议层面也得贯彻。

## 5. 台账与发布确认：先查、再发、确认才记账

游标解决「读进来」不丢不重，报出去那一步还需要第二层记录：**台账**。参考实现的台账一行一条，记：报告日期、来源、一个不变的 ID（Slack 消息的时间戳或 PR 编号）、最后已知状态。已报过且仍开着的条目下次只带一行标记（「仍在等，第 3 天」），不重复展开；已关闭的静默消失。没有台账，代理要么天天把同一件事再报一遍，要么为了不重而忘记跟。

发布环节则围绕一个不对称：**动作已经发出、结果未知**时，选错哪边都有代价——记成发过而实际没发，游标随之前进，那批内容永远漏掉；不确定就重发，读者收到两份。参考实现在台账和游标上加了三个前置条件：

1. **发前查重。** 先读目的地频道最近的消息，发现今天的刊头已经在频道里，就不发。（细节：机器人 token 用不了搜索，只能按标题读最近历史，所以这个查重以「同日」为界。）
2. **只有平台明确确认才算发出。** Slack 必须返回成功标记和消息时间戳；HTTP 200 不算数。
3. **确认之后才记账。** 台账行、游标、运行记录全部排在确认之后写。

顺序上还有一道防线：发布前先把运行记录写成「正在发布」，确认后改写为「已发布」并附消息 ID。于是任何时刻中断，记录都停在能被人读懂的中间态。两条「永不动」原则贯穿全程：读失败的来源游标不动；发布失败时游标也不动——下次运行这批内容还会被覆盖到，宁可重，不丢。

关于**幂等**（idempotent：同一动作重复执行不产生额外效果）：这里并没有平台级幂等键可用，它是用「查重后再发 + 确认才算数」近似出来的——发布动作被设计成可检查的（刊头、消息 ID），重复发生时可被发现。运行记录还规定：每次运行不管发没发成，都写下读了什么、失败什么、发了什么、砍了什么（各带一词原因）、以及自己单独做过的判断——供人核对。

## 6. 「也许发过」：结果不确定时为什么什么都不改

「也许发过」（maybe posted）是这套设计里最新颖的一格。它的场景是经典的**不确定性窗口**：请求已经发出、结果未知（超时、进程中断）——此时「当成功」会漏发，「当失败」会重发。参考实现显式开出第三种状态：把这次运行标记为「也许发过」，**其余状态一律不动**。下一次运行从旧游标重新读一遍，素材还在，不会丢；代价是有可能重复，而重复靠同日的刊头查重和人大可读的运行记录来兜。

对应的还有第四格「暂存」（held）：发布根本到不了目的地时（机器人不在频道、token 无效、频道不存在），简报文本原样保留在运行记录里，同样别的什么都不动。加上发布前的「正在发布」与终态「已发布」，一次运行在记录里始终停在 `正在发布 → 已发布 / 也许发过 / 暂存` 的某一格上。

这套设计的态度可以概括为：**把不确定性显式化，而不是假装消灭它**。材料里没有给出「也许发过」的跨天自动收敛机制——同日的刊头查重只覆盖当天，`也许发过` 和 `暂存` 的最终判定要靠人看运行记录。另有一个同样「看起来像静默」的来源：达到花费上限的运行是被暂停而不是失败（见第 7 节），README 明确提醒此时要去控制台查看运行列表，而不是把没收到简报当成一切正常。

## 7. 配套与平台层的边界：偏好、凭据、预算，以及调度器自己的丢重

上述机制之外，参考实现还有三样结构性安排，缺一样都会让前面的设计漏气：

- **偏好只读、且每次运行重读。** 读者自己的规则（读哪些频道与仓库、排除什么、长度上限、何时停）放在一个代理只能读、不能改的存储里；代理想改规则只能写一份「建议」文件等人接受。文章点名的典型事故是被烤进提示词里的旧副本继续生效——改了规则，代理还按老规矩跑。另一条纪律是：读不到偏好文件就停下来并说明，而不是按默认值硬跑。
- **凭据不进代理环境。** Slack 和 GitHub 的凭据存在平台凭据库（vault）里：沙箱内只有占位符，请求出沙箱时平台按允许的主机替换成真实值——代理和它的文件系统从头到尾见不到明文。配合最小权限：GitHub token 只读（所有 GitHub 工具无人批准直接放行，安全支点就是「只读」），网络白名单默认拒绝、只放行 Slack 与必要的主机，联网搜索与抓取工具直接关掉（它们运行在沙箱外，不受白名单约束，留着等于给注入文本开了一条外泄通道）。
- **花费封顶、且失败形态不是报错。** 每次运行有独立的花费上限（模板值 5 美元；建议从正常运行成本的 3–5 倍起步、拿到真实数字后收紧）。达到上限的运行被**暂停**而不是失败（停止原因直写「budget_reached」），文案上看起来就是频道安静了。文档说得也直白：上限拦的是「新的工作」，在途的请求会跑完，最终花费可以略微超过上限——这是预期行为，不是计费错误。

还有一层容易被忽略的丢重来源在**调度器自己**：文档写明 cron 按墙上时钟字面匹配，夏令时切换日里，春季被跳过的一小时内的时刻不触发，秋季重复的一小时里的时刻会触发两次；建议是对错过或重复不可接受的场景避开凌晨 1–3 点或改用 UTC。而参考实现的游标加台账恰好能把这些吸收掉——调度层漏一次触发，下次窗口自动变长；重复触发一次，台账和刊头查重接住。这个分层关系本身就是值得带走的结论：**代理层的状态管理要能容忍调度层的丢和重**。

## 尚未解决的问题

- **「也许发过」的自动收敛。** 材料只见同日刊头查重；跨天的 `也许发过`/`暂存` 没有写明自动核对机制，实际收敛依靠人看运行记录与平台控制台。这是参考实现自己的选择（宁重勿丢），不是一个待修的 bug，但在高频自动化里，积压的未决状态需要谁来扫、以什么节奏扫，材料没有回答。
- **Slack 侧的软约束。** 提示规则说「只发简报、只发目的地」，但同一个 token 事实上能发到它所在的任何频道；真正的控制是成员资格。参考实现在安全说明里建议敏感场景拆成两个应用（只读的读来源、只写的发目的地）。
- **注入只被限制「能做什么」，不保证「说什么」。** 文章明确承认：植入的指令仍可能改变简报内容，甚至通过代理自己写的状态笔记跨运行传递；只读权限与网络白名单缩小的是影响范围，不是内容层的可信度。
- **未实测。** 全部结论来自官方文档、官网示例代码与文章自报数字（beta 阶段，行为可能调整）；我们未运行过该参考实现。

## 实践建议（仅在需要时展开）

文章结尾给出的六条规则，可以作为任何「无人值守代理/定时任务」的检查表：

1. 每个来源从游标读，而不是固定时间窗；
2. 读失败的来源报「读不到」，绝不报「今天没什么」；
3. 发布前对每一条内容重新核验；
4. 只有平台确认之后才算发出，然后才更新游标与台账；
5. 每次运行重读偏好，且偏好放在代理改不了的存储里；
6. 只读处只给只读，给每次运行的花费封顶。

配套代码还有两个可复用的用法：把状态存储设为只读即可进入空跑模式（不发布、游标不动，只打印简报），适合上线前校验；参考实现给出了自报的成本量级——繁忙日（两个频道、两个仓库，约 140 条消息与 25 个 PR）一次运行 Opus 5 约 1.5 美元、Sonnet 5 约 1 美元，全部来源都读不到时约 0.15–0.30 美元，来源翻倍约增加三分之一（自报口径，测试时默认模型与现在不同，README 建议以自己运行的实测为准）。

把同一套问题映射回本机：任何自建的定时脚本或 CI 定时任务，如果它「读增量、发结果、记状态」，第 1–4 条几乎原样适用；最容易漏掉的自查是——把「记录的动作」与「实际发生的动作」不一致当作第一类缺陷去找（报出去了但没记录、记录了但没发出、游标动了但内容没读到）。
