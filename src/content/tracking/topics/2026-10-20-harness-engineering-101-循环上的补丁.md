《Harness Engineering 101》开篇给了一个很容易传播的句子：LLM API 是无状态的，每一轮都要把整段对话作为 JSON 数组重新发回去；harness（代理运行框架）就是构建、维护、保护这个数组的程序；业界所说的 agent 能力，大多只是对这个循环打的补丁，而每个补丁都对应一个具体故障。[^book]

这句话的吸引力在于，它把 agent 的词汇表一次性压平了。记忆（memory）是数组，上下文管理（context management）是决定什么进数组，子代理（subagent）是换一个数组，模型上下文协议（MCP）是 dispatch table 多了一跳，检索增强生成（RAG）是决定哪些文本进数组。一门看起来有很多专有名词的学科，被还原成了几个数据结构和一条循环。

但“还原得对”和“解释得够”是两件事。一个成立的还原，也可能把一段历史画成一张静态解剖图。真正有价值的，是它坚持给每个功能配一个故障和一笔代价；“agent 是一个 while 循环”本身并不新，过去两年不少人说过类似的话。它最容易被误读的地方，也在这里：补丁看起来是独立的，实际上被几条不变量绑在一起；补丁的边界看起来是固定的，实际上随模型能力在移动。

下面按三条线读这本书：它怎样把 loop 讲清楚；补丁之间怎样互相约束；这条边界正在怎样移动。最后回到一个它没有回答的问题：loop 健康，是否等于工作做好。

## 1. 数组、循环、闸门

先把最小的机制说清楚。一次模型调用就是一个 HTTP POST：messages 数组进去，下一段 assistant 内容出来；服务端不保存会话，所谓“对话”是 harness 自己持有并每轮重发的数组。会话就是文件，`--resume` 是读文件，`/clear` 本质上就是 `messages = []`。这个事实的推论很硬：模型“忘了”什么，通常是那东西掉出了数组；上下文管理不是玄学，是决定哪些字节进入下一次请求。

在这个数组上，agent 的循环只有一件事：调用模型，如果它请求工具，就执行、把结果追加回数组，再调用；直到 `stop_reason` 不是 `tool_use`。书里把它写成几行：

```python
while True:
    reply = call_llm(messages)
    messages.append(reply)
    if reply.stop_reason != "tool_use":
        break
    messages.append(run_tools(reply.tool_calls))
```

一个“turn”不是一次 API 调用，而是一个用户请求加上它需要的多轮模型/工具往返；一次“修好测试”可能是 40 次 API 调用，用户只看到最后一段回答。

循环里最容易被写错的地方，是工具错误。普通程序把异常当成程序员的问题；agent 应该把失败当成模型的信息。书里列了三种反模式：让循环崩掉、把错误吞成一句“command failed”、或者在 harness 里悄悄“修正”参数再重试。第三种最隐蔽，因为模型看到的世界已经和真实世界不一致，下一步会建立在它不知道的状态上。作者在 WSO2 的 MI Copilot（一个面向集成开发的编码助手）里遇到过一次写文件失败但模型不知道，结果模型在错误的文件上继续编辑，把文件弄坏了。这里的问题出在 loop：失败没有被送回去，模型自然不知道。

再往外一层，是“手”在哪里。模型从不执行任何东西，它只发出请求；真正运行工具的是 harness。所以书里说，能力住在 harness 里，责任也在 harness 里；没有“AI 自己做的”这回事。这个位置感带来了第十三章的那条分层：不暴露工具（没有手）、确定性规则（反射）、人批准（闸门）、小模型分类器（便宜的判断）、沙箱与可恢复状态（爆炸半径）。作者有一句话很准确：系统提示词不是访问控制系统；提示词建议，反射执行，人批准，分类器筛查，沙箱兜底。一个必须在 100% 情况下成立的事情，不能只写在提示词里。

这套位置感最好的例子，是编辑工具的形状。朴素的 `write_file` 让模型重写整个文件，既慢又容易在它“没打算改”的 900 行里引入抄写错误。生产 harness 用精确片段替换：模型给出原文片段和替换文本，harness 只有在片段唯一匹配时才执行；匹配不上或匹配到两处，就拒绝，并把原因作为工具错误返回。这个设计把“模型可能编造一个不存在的片段”变成了一个响亮的、无害的错误。工具的形状本身就是护栏。

另一个例子是子代理。书里说得很直白：与其把子代理当成“团队成员”，不如把它看成一个全新的空数组：只把最后一段报告作为工具结果交回主循环。它存在的理由是保护主循环的上下文预算，不是画组织架构图。把子代理当“人”看，会问错问题；把它当“数组”看，很多设计问题会立刻有答案——为什么子任务描述必须自包含，为什么父代理看不到子代理的中间过程，为什么子代理适合“中间量大、结论短”的工作。

## 2. 缓存把全书串成一条约束链

如果这本书只停在“每个功能对应一个故障”，它仍然是一本不错的教程。真正让它有架构味道的，是第五章那条看起来只关于钱的规则：不要改数组的顶部。

先把账算出来。一个编码任务跑 40 轮，每轮新增约 2,000 token（模型处理文本的计量单位），数组从 10,000 token 开始；第 1 轮发 10,000，第 40 轮发 88,000，整个 turn 的输入 token 是 196 万。模型的输出没有变，账单却按对话长度的平方增长。提示词缓存（prompt caching）把已经处理过的前缀存下来，在 Anthropic 的计价里缓存读大约是按输入价的十分之一，OpenAI 的自动缓存也有折扣；于是同样的对话，成本可以降 80% 到 90%，延迟也降，因为服务端真的跳过了重算。

但缓存只认字节前缀。第 1,000 个字节变了，后面 80,000 个相同字节也要全价重算。书里的规则因此可以概括成一句话：追加便宜，改顶部等于把下面全部作废。这条规则接着解释了全书一半的设计：时间戳不能放在系统提示词（system prompt）顶部，工具列表要排序，MCP 开关不能每轮改工具数组，session 中途“改进”system prompt 会让缓存全灭，从中间删旧消息来省空间反而可能更贵。最反直觉的是最后一条：把数组变小，不一定把账单变小。

于是“补丁”之间的关系变了。压缩（compaction）是一次罕见的、故意的缓存重置，不能当成随时可做的清理：把旧轮次换成摘要，保留最近几轮原文，然后重新开始追加。运行中引导（steering）走的是另一条路：在数组底部追加一条系统提醒（system reminder），理由有三个：缓存、位置（模型对最近的 token 注意力更稳）、时机（事件发生在两轮之间）。延迟加载（deferred tool loading）一旦把某个工具的结构定义（schema）激活，就不能再换掉，因为移除 schema 会破坏前缀；所以它只能是单向的。记忆文件（memory 文件）走的是第一条 user 消息里的上下文注入，system prompt 保持字节稳定，角色上也更诚实。后台任务完成时，通知走的是同一条 reminder 队列，而不是新开一个通道。

这些细节单独看都像实现技巧，连起来是一条不变量：数组的稳定前缀是缓存的前提，缓存是长 loop 的经济前提，而长 loop 是 agent 能做事的前提。书里最后那版 298 行的 toy harness 把这条链收在一个很小的结构里：`drain_reminders_into` 只在两个地方被调用，分别是打包工具结果时和构建下一条用户消息时。这两个地方就是数组仅有的门。门少了，数组才可审计；门多了，很难说清模型到底看到了什么。[^book]

这也是全书最值得带走的部分。具体的补丁清单会过时，这条不变量链不会：任何要进入数组的新东西，都要回答它改的是哪一段前缀、会不会让缓存失效、会不会让某条旧规则从数组里掉出去。书里第十二章把这套东西变成可操作的调试：捕获真正发出去的请求字节，盯 `cache_read_input_tokens`，把捕获的请求重放、只改一个块做实验，用 mock API 在 CI 里断言数组的形状和字节稳定性。作者说得很直白：你修不了一个你看不见的 prompt。这句话比“agent 是一个 while 循环”更接近这本书的实际价值。

## 3. 边界在移动：哪些补丁会被模型吃掉

书里有一个自我修正的线索，作者没有藏起来：harness 的很多机关，正在被模型吃掉。ReAct 式的“Thought/Action/Observation”曾经要靠字符串解析，现在工具调用被强化学习（RL）训练进了权重，循环还在，解析没了。LangChain 时代的 chain 和 graph，很多是为了让一个不够强的模型分步做事；长上下文和更强的 agentic 训练吃掉了一部分，框架转而卖编排、可观测性和企业集成。书里甚至替“只要一个终端”的阵营说了公道话：终端是通用的，模型在预训练里见过海量的 shell 记录，而且这条趋势已经有两次先例。它给出的反驳也很具体：结构化的编辑工具可以被路径级权限、读取追踪和差异（diff）检查；终端里的 `sed -i` 对反射层是一个不透明的字符串；语言服务器协议（LSP）的诊断增量能在编辑后几秒内把新错误推给模型，而终端不会主动推；弱模型需要更多的身体，结构化工具和响亮的错误是它们的地板。

这段争论的意义不在于谁赢，而在于它说明“补丁”不是永久器官。书里附录 A 把这个意思翻成工程语言：能力与脚手架是替代关系。前沿模型可以只拿一个 shell 干活；便宜模型需要更细的工具、更密的提醒、更明确的 schema。同一个 harness 服务多个模型档位时，system prompt、工具集、steering 密度都要分档。路由看后果，不看难度：压缩摘要差 10% 只是少一点上下文，安全分类器差 10% 可能放行 `rm -rf`；所以后者要用小模型加验证和失败时默认拒绝（fail-closed），而不是因为它“看起来简单”就随便换便宜的。

这也解释了 HN 上那串讨论。有人问：模型越强，是不是越不需要 harness？另一位做过 harness 优化的实践者给了一个更完整的答案：一次性任务，强模型加一个强 harness（bash + VM）就够了；重复成千上万次的任务，值得把工作预编译进 harness，然后换最便宜的模型。[^hn] 把它当成“harness 重要/不重要”的二选一，会漏掉真正的变量：任务重复度和验证成本。书里的说法更克制：身体会继续溶解进大脑，但接缝不会消失，因为总得有一个东西把只会说话的函数接到不会说话的世界。[^book]

这里可以再往前推一步，书里只提了一句：OpenAI 的 Responses API 这类接口提供可选的服务器端会话存储，那么“数组由谁保管”也可以移动。无状态的经典 API 让 harness 拥有数组；服务器端存储让 provider 替你保管数组。接缝还在，但“谁构建、谁维护、谁保护”这三个动词的分配变了。所以更准确的说法是：总得有一层东西决定模型看见什么、能做什么，并对结果负责，它不一定非得拥有数组。这层东西可以叫 harness，也可以叫 runtime、agent runtime、orchestration layer；名字会变，位置不会。

## 4. loop 健康，不等于工作做好

这本书的验收标准是内部的：数组里是不是预期的内容，缓存有没有命中，闸门有没有拦住，子代理有没有把错误的报告带回来。它不回答另一个问题：这些做对了，工作是不是就更好。

一个具体的对照来自 Fiona Chen 和 James Stratton 的工作论文。他们用 718 家公司、2021 年 1 月到 2026 年 3 月的数据，利用各公司采纳编码工具的时间差做估计：采纳编码代理后，代码行数约增加 30%，代码变更请求（PR）从提交到合并的时长约增加 49%（基线均值 7.03 天），PR 评论数增加 35%，要求修改的 PR 占比接近翻倍，做代码审查的员工占比增加 14%；而以 Jira 任务和项目完成数衡量的下游产出，没有统计显著的增长，对 Jira 产出的估计还排除了超过 12% 的增长。作者把这解释为代码审查瓶颈。这不是随机实验，样本也只覆盖同意参与研究的 Jellyfish 客户，不能代表所有公司；但它足以说明：代码生成层的指标可以很漂亮，交付层的指标却不动，甚至更慢。[^jellyfish]

这本书的框架能解释这个现象的一半：harness 把“生成代码”这个 loop 调得很顺，但代码审查是另一个 loop，有它自己的瓶颈、队列和人的注意力。书里没有把审查放进 loop；它把 loop 的边界画在 agent 的数组和闸门上，画在“模型能做什么”上，而不是“组织怎么吸收”上。于是出现一种错位：harness 工程的指标（缓存命中、上下文占用、工具成功率、子代理报告质量）都在改善，组织的指标（审查时长、返工比例、交付周期）可能没有。两者不是一回事。

第十二章其实是全书最接近“可验证”的一章，因为捕获、重放、字节断言让 prompt 调试从“再改改措辞”变成实验。但即使观测做到满分，它也只能告诉你“模型为什么这样行动”，不能告诉你“这个行动值不值得做”。后者需要 eval（评估）、任务成功率、回归集、人工审查，甚至是 Jellyfish 论文那种组织层的度量。书把范围限定在接缝上，这属于书的边界，谈不上错误；读者如果把“loop 健康”当成“agent 好”，就会把工程指标当成产品结论。

这也是它与另一篇专题的接口。十月的[《Agent 的改进回路：经验怎样变成能力》](/tracking/2026-10-15-能力内化回路-小模型与垂类的位置)讨论的是经验怎样变成能力：反馈容易取得的任务先跑通，训练、检索、工具和规范都是经验的沉淀位置；小模型和垂类只是另一条成本线。把两篇放在一起看，会发现同一个问题从两头出现：一边是“经验能不能进入模型或 harness”，另一边是“进入之后，工作有没有变好”。前者是这本书的强项，后者是它留给 eval 和组织度量的空白。

## 5. 把补丁史当诊断表

读这本书，可以先记住三个位置：数组、循环、闸门，不必从第一章一路背到尾声。然后每看到一个功能，问它落在哪个位置：它是让什么东西进入数组，还是守住模型的手？如果两者都不是，它大概率是产品层、组织层或营销层的东西，不属于这本书的接缝。

书里最后一章把这一点说得最清楚：所有专有名词，最后都归成两件事：要么有东西进入数组，要么有东西守住手（something enters the array, or something guards the hands）。再往前一步，是第十五章留下的三个问题：什么进入数组？谁决定，大脑还是身体？代价是什么，靠什么执行？还可以再加第四个：它动了哪条不变量？缓存稳定性、权限边界、上下文预算、可审计性，这四条里只要有一条被破坏，补丁就会在别处收费。

这本书的局限也要说清楚。它是一个实践者的教学材料，不是独立评测；作者对 Claude Code 内部机制的描述（文件追踪、压缩提示词 compaction prompt、只读探索子代理 Explore agent、计划模式 plan mode、系统提醒 system reminder）是他对闭源产品的读法，不能当成已核实的内幕；书里的 toy harness 和 One Code 是开源的，可以对照，但生产 harness 的很多细节仍然不可见。作者披露自己起草每章，再用 Claude Code 和 One Code 重排章节、润色英文、生成图表；HN 上的讨论有不少火力集中在“AI 味”上，作者也承认了。这些事影响阅读体验，但不直接决定架构判断的对错。判断的办法仍然是把它的说法拿回自己的 harness 里试：数组里到底有什么，缓存有没有命中，闸门有没有拦住，子代理的报告能不能被父代理验证。

最后回到那句话。Agent 是一个 while 循环，这句话是对的，但它是这本书的起点，不是结论。真正的结论是：循环很小，接缝很长；补丁会过时，位置不会。读完之后，如果只能带走一件事，那就是这两个问题：模型看见了什么，模型能做什么。剩下的名词，可以慢慢往里放。
