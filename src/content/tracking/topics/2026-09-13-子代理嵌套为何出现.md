## 先回答问题

- **时间线纠正**：CC 的子代理嵌套**上线于 2026-06-10**（v2.1.172，"Sub-agents can now spawn their own sub-agents (up to 5 levels deep)"，默认开启）；**7 月 21 日（v2.1.217）的动作是收紧而非上线**——默认改为不嵌套，需设 `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` 才放开，同版本加并发上限 20。你 7 月观察到的应是这两段之一（A；见条目 1）。
- **当前状态与历史不一致**：09-13 官方文档快照表述为「默认可嵌套、主会话以下最多 3 层、到深度收回 Agent 工具」——与 7/21 的「默认关」和 6 月的「5 层」都不同，中间至少经历一次回调，具体版本归属未核清（A/B；见条目 1）。
- **为什么出现（官方动机）**：官方文档明示的场景是「委派出去的任务自身又能拆成并行子任务」——例如审查子代理为每个发现派一个验证器——让**中间输出永不进入主会话**，只有顶层摘要返回（A；见条目 2）。这与 Codex 侧「分级压缩管道、保护根代理上下文」的动机同构。
- **为什么是现在（推断，综合判断）**：三个条件在 2026 年 5–6 月同时成熟：长上下文模型（Sonnet 5 / Opus 5 均为 1M 档）让多层各自持窗的成本可接受；两家多代理框架在同一窗口期上线（Codex multi-agent 机制 5 月初、CC 6/10），属竞争对齐下的能力竞速；Cognition 2026-04 软化「反多代理」立场（承认「单写多读」模式可行）提供了行业叙事背书（B/C；见条目 3、4）。
- **两家都用「默认收紧」约束它**：CC 7/21 默认关 + 并发/预算闸；Codex V1 默认深度 1、V2 靠模型目录授予并记账嵌套用量。放开了能力，但都拒绝无界递归（A；见条目 3）。
- **仍不清楚**：文档与 release note 的环境变量名不一致（`CLAUDE_CODE_MAX_SUBAGENT_DEPTH` vs `..._SPAWN_DEPTH`）；217 到当前文档之间「默认关 → 默认开（3 层）」的回调发生在哪个版本（见条目 1）。

## 详细解释与证据

### 1. CC 嵌套功能的完整时间线：上线、反转、当前状态

|---|---|---|---|
| 2026-06-10 | v2.1.172（commit ca34f27） | "Sub-agents can now spawn their own sub-agents (up to 5 levels deep)"——上线即默认开启 | A（tag 页原文） |
| 2026-07-21 | v2.1.217 | "Changed subagents to no longer spawn nested subagents by default; set `CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH` to allow deeper nesting"；同版本加并发上限（默认 20，`CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`） | A（tag 页原文） |

**判断与边界**：6 月上线时 5 层、7 月反转、9 月文档又写「默认可嵌套但 3 层」——「默认」语义在三个时点不一致（默认开 5 层 → 默认关 → 默认开 3 层？），其中至少 217 → 09-13 之间有一次未定位的回调。本文档节按当前文档理解：嵌套可用但深度/并发/预算三重上限。深度上限从 5 收到 3 的方向，与官方把 `Agent` 工具按深度条件注入（「when the subagent is at the depth limit」）的工程实现一致：**Anthropic 选择结构限制而非事后记账**。

### 2. 官方动机：上下文管理是第一理由

- 文档原句（A）：嵌套适合「a delegated task that itself splits into parallel subtasks, such as a reviewer subagent that dispatches a verifier per finding, **so the intermediate output never reaches your main conversation**. Only the top-level subagent's summary returns to you.」——每层只向上回传摘要，中间探索噪声留在本层。
- Boris Cherny（CC 团队）在上线日（6/9）公开宣布该功能，第三方转述其动机为 context management（C：[ruflo issue 转述](https://github.com/ruvnet/ruflo/issues/2335)，原始帖子未直接核到）。
- 配套设计佐证「保护主会话」是设计中心而非附带：嵌套深度处收回工具、只有顶层摘要上行、树形面板可视化（+N）。

来源：[官方 sub-agents 文档](https://code.claude.com/docs/en/sub-agents)｜Anthropic｜快照 2026-09-13｜A；[Claude Code 2.1.172 变更速报](https://x.com/ClaudeCodeLog/status/2064817348113019239)｜ClaudeCodeLog（第三方追踪号）｜2026-06（具体日期未核）｜C

### 3. 为什么是 2026 年 5–6 月这个窗口（综合判断）

- **竞速对齐**：Codex 的多代理机制（V1/V2）5 月初已进主干（见 [2026-09-07-专题-codex-子代理递归条件](/tracking/2026-09-07-codex-子代理递归条件) 条目 3），CC 6/10 跟进上线——两家在同一窗口交付同一能力，先后差约一个月。
- **理论背书**：Cognition 2026-04-22《Multi-Agents: What's Actually Working》软化 2025-06 立场，承认「写保持单线程、读并行」的多代理模式可行（核查结果沿用旧档，未重新回源）——嵌套恰恰是「单写多读」的树形推广：每一层内仍是单写者，纵向是读/摘要上行。
- **模型前提**：Sonnet 5（7 月初成默认）与 Opus 5 均带 1M 档上下文与更强的自主收尾指令遵循；多一层代理就多一份系统提示词与工具定义开销，弱模型会把嵌套跑成级联退化——Codex 给第三方 Bedrock 模型强制回退 V1 是同款顾虑的佐证（沿用旧档）。
- **管控同步出现**：v2.1.217 同版本加并发上限；同期周报（w30，7/20–24）把 `--max-budget-usd` 预算闸延伸到子代理（到达即停新 spawn 并叫停运行中的后台子代理）——「放开能力」与「锁住爆炸半径」同一批次交付。

来源：[v2.1.217 release](https://github.com/anthropics/claude-code/releases/tag/v2.1.217)｜2026-07-21｜A；[whats-new w30](https://code.claude.com/docs/en/whats-new/2026-w30)｜Anthropic｜快照 2026-09-13｜A；Cognition 续篇核查见 [2026-09-07-专题-codex-子代理递归条件](/tracking/2026-09-07-codex-子代理递归条件) 条目 5｜B

**判断与边界**：本条 1–3 点中，竞速时间线是事实（两家发布日期可查）；「竞争对齐」与「理论背书影响决策」是推断，官方从未如此表述——动机的唯一直接证据只有条目 2 的上下文管理表述。

### 4. 两家设计哲学的分野：结构限制 vs 计量限制

- **CC（结构限制）**：深度硬闸（5 → 3 层）、默认关过一次、到深度直接收回 `Agent` 工具、并发 20、预算闸停机——确定性边界，宁可牺牲能力也不给无界递归。
- **Codex（计量限制）**：V2 无深度硬闸（已核 control/execution.rs 无深度校验），靠 `max_threads` 并发、根预算记账（#41183）与模型目录授予（v2 模型才递归）。
- **共识**：两家都认为嵌套值得做（上下文经济），又都不信任它无界运行——区别只在闸门形态。对使用者的含义：在 CC 里撞深度上限会**工具消失**（结构性失败，可预期）；在 Codex 里超支是**预算报错**（经济性失败，粒度更细但依赖记账准确）。

来源：CC 侧本条目 1；Codex 侧见 [2026-09-07-专题-codex-子代理递归条件](/tracking/2026-09-07-codex-子代理递归条件) 条目 1（沿用旧档，未重新回源）｜A

## 对当前工作流的启示

- **嵌套的适用判据用官方那句**：任务是否「拆出去之后还能自己再拆成并行子任务」（如审查→逐发现验证）。只是单层 fan-out 就够时，不要为省 context 付两层系统提示词的固定开销（见条目 2）。
- **深度与预算要显式设置而非信默认**：CC 默认档在 6–9 月间改了三次，`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`（文档另写 `_DEPTH`，使用前先在当前版本验证哪个生效）+ `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS` + `--max-budget-usd` 三件套配齐再跑无人值守（见条目 1、3）。
- **未决问题**：文档与 release note 的变量名哪个在当前版本真实生效；217 → 9 月文档之间「默认关 → 默认开（3 层）」的回调版本。下轮扫 CC release notes 时顺带核（见条目 1）。
