## 先回答问题

浏览器 agent 在航班页面上要做的，可以被压成两层选择：先选一个操作，再选一个目标（如果这个操作需要目标）。在压缩插件里，上下文压缩（把历史内容缩短以继续任务）也可以被压成一对是非题：这条工具调用还要不要留，它的结果还要不要原文。两件事都叫“让模型做判断”，但模型看到的世界、能选的答案、判断错了之后会发生什么，差别很大。

这里的“决策模型”，指输入任务状态与判据、输出有限选项、评分或概率的模型或服务；TypeSafe 的 Jev 是其中一个具体实现。它不生成文本，也不执行动作，只在一组预先写好的问题上给选项、评分或概率。于是问题就变成了：这套“选择题”里，题干、选项、交卷规则和判分，分别由谁负责？

答案可以先给出来：模型接管的是一组由程序切好的局部判断；程序保留的是问题定义、状态构造、候选发现、动作映射、执行、验证和失败回退。模型的优势是单次判断快、输出受约束、不需要生成；它并不能替代任务理解，也不能保证正确选项已经在候选集里。现有两个公开实现说明，这种分工在“选下一步”上比较成立，在“决定遗忘”上更脆弱；决定成败的往往不是模型分数，而是程序有没有把正确选项和足够证据放进模型的世界。

9-21 的专题已经把 Jev 的 API 形态和压缩用例的价值边界讨论过；10-26 的热点稿记录了讲稿的六种做法和“16 行演示”。这篇不重复那些内容，只沿着讲稿的代码幻灯片和两个公开实现，看看这些判断在程序里到底长什么样。

## 1. 选择题是谁出的：程序先决定什么可见、什么可选

先看浏览器这条线。程序读当前页面，抽出一张元素表：按钮、输入框、下拉框，各自带标签、当前值、角色和可用操作。它把能点的元素和能填的字段分开，给每个操作准备一份兼容的目标列表，再加上等待、完成、受阻三个控制项。模型收到的不是网页截图，也不是整棵页面树，而是这张表、页面可见文本、用户目标，以及最近十步动作。模型要回答的是：下一步用哪个操作；如果这个操作需要目标，选哪个元素。当操作是输入文字时，还有一个小模型只负责生成要填的值；它不选操作，也不选目标，生成结果还要先通过 JSON 校验才会被输入。

这里已经发生了三次程序侧的决定。什么算可见：只送当前可见文本，离屏正文和页脚不进入模型上下文。什么算候选：只送当前观察到的元素，而且每个操作只给兼容的目标；下拉框的选项还带一个观察到的元素/选项索引。什么算可执行：模型可以同时给出操作和几个目标头的概率，但程序只校验被选中的操作对应的那个目标头，其他头即使概率很高也不会被执行。模型的选择空间是程序画出来的。

压缩这条线更明显。程序先按工具调用 ID 把调用和结果配对，固定第一条和最近六条消息，文本消息不参与删除；然后把整段对话压进默认 25k token（模型处理文本的计量单位）的预算：工具结果只剩“ok/error，4213 字符（已省略）”，工具输入按 1000、200、60 字符逐级截断，长文本截头去尾，旧消息折叠成一行说明，旧调用压成一行；如果仍然放不下，直接报错。模型对每个非固定调用回答两个是非题：这条调用还要不要留？它的结果还要不要原文保留？程序再按阈值把两个概率映射成保留、截断或整条删除。

所以“选择题”的题干、选项和交卷规则都是程序写的。模型只负责在有限选项上打分；它不发现候选，不定义问题，不执行动作，也不验证结果。

讲稿的演示把这一点说得很清楚：大模型是默认模型，判断器局部切换到 Jev；剪枝只把当前请求和一条历史交给 Jev，摘要则交给大模型。讲稿里还有工具装载：它把请求和每个工具交给 Jev，问这个工具对当前任务需不需要，再把排名靠前的子集交给 ReAct。它和剪枝是同一种结构：程序枚举候选，模型逐项打分，程序取子集；区别只在候选是工具还是历史。

讲稿甚至说，把 Jev 换成一个小 LLM，整套东西仍然能跑。这句话很重要：它说明这里的关键不是某个模型，而是“把任务切成一连串有限判断”的程序结构。

讲稿的代码幻灯片是教学演示，不是可运行仓库。在四张幻灯片之间，最后一张用两个参数调用摘要函数，前面定义的摘要函数只收一个参数；剪枝的字段说“一个过去的 turn”，实现里遍历的却是单条历史消息。这些不一致不影响理解结构，但足以说明：幻灯片不能当作生产实现，也不能当作效果证据。

## 2. 模型选错，还是选项根本没出现

还有一个更容易被忽略的问题：模型选错，和正确选项根本没进入候选集，是不是一回事？在浏览器这条线，不是。候选集来自当前观察到的元素；快照只支持常见 HTML/ARIA 控件，影子根、内嵌框架、画布、上传控件、新标签页、嵌套滚动和任意键盘控件都不在支持范围。需要点的东西如果在这些结构里，它不会出现在元素表里，模型再准也选不到。此时模型可能选一个看起来合理的可见元素，也可能选“受阻”；程序只能在连续三次动作没有改变页面时判定卡住，它不知道是模型选错，还是世界没被看见。

“完成”也一样。通用循环里，模型说完成，状态就结束；Flights 示例则在跑完后用 URL、单程、出发地、目的地、日期和结果列表做独立检查。作者的性能文档写得很直白：“A valid operation can still be wrong, and DONE is never independent evidence of success.” 一个合法的操作仍然可能是错的，完成也从来不是成功的独立证据。这句话把模型判断和程序验收分开了。

压缩这条线的缺口更隐蔽。程序说把“整段对话”给 Jev，但给的是骨架：工具结果只剩状态和长度，长文本可能被截，旧消息可能被折叠。判断“这条结果还要不要原文”时，模型看不到结果内容本身。它只能从工具名、输入、目标、前后文本、结果长度和是否报错来猜。如果关键约束、错误信息或文件内容正好在被省略的那一段，模型没有证据发现这个缺口；程序也不会因此去补查，它只会按当前状态继续裁。

这不是说这个设计一定错。对可重跑的读操作，“删了再读”是一个合理的兜底；对有副作用、昂贵或结果会变的操作，它不是等价替换。插件自己也承认，概率不是“安全删除”的证明，校准是在请求级别，不是逐条保证。模型说“结果不用原文”，程序仍会保留前 300 个字符和一行说明；真正整条删除的是“调用也不用”的情况。这个三档动作不是模型直接选的，而是程序按两个概率和阈值算出来的。

把两条线对照起来，能看到两种不同的失败：浏览器里，正确动作可能不在候选集；压缩里，正确证据可能在候选集里，但被程序遮住了。前者是覆盖问题，后者是可见性问题。两者都不是模型分数能修的。

## 3. 为什么“选下一步”比“决定忘掉什么”更适合决策模型

9-21 的专题曾把压缩列为 Jev 的坏用例。看到这个插件后，这个判断要收窄：它不是让 Jev 做生成式摘要，而是只让 Jev 对工具调用和结果做保留判断，文本消息不被删除，第一条和最近六条固定，失败时回退到 Claude Code 内置摘要。它比“让 Jev 写摘要”稳妥得多；但它的反馈结构仍然不利。

同一个决策模型，在“选下一步”上看起来更顺，在“决定忘掉什么”上更别扭，关键不在模型，而在反馈结构。

选动作的反馈是即时的。动作执行后页面会变；变了没有、目标还在不在、有没有被遮挡、是不是连续几次没变化，程序和执行器都能看到。选错了，下一步的观察会把它暴露出来；很多错误可以在下一步重新观察、重试或换一个动作。候选集每一步重新构造，模型面对的是当前世界。它主要在当前可见状态里选一个能推进目标的动作，不需要像“决定遗忘”那样，为几步之后才暴露的后果负责。

决定遗忘的反馈是延迟的，而且经常不可见。删掉一条工具结果，当时没有任何信号告诉你“删错了”；要等到后面的任务因为缺少这个错误信息、文件内容或约束而走偏，才可能暴露。即使走偏了，也很难归因到具体哪一条删除。判断时看到的是过去的骨架，要回答的是未来的需要；这两端之间没有即时反馈。

信息要求也不同。选动作需要知道“当前页面有什么、目标是什么、刚刚做了什么”；这些信息在观察里基本都在。决定遗忘需要知道“未来哪一步会用到这条记录”；这需要任务计划、约束、工具的副作用、后续分支，现有状态里没有，模型也无法从一条“ok，4213 字符（已省略）”的说明推出来。

所以可以给出一个比“模型准不准”更有解释力的判据：反馈是否即时，损失是否可枚举，判断所需的知识是否在输入里。三者都满足，局部判断才可能可靠地传递到长程结果；缺一个，模型的概率就只能当参考，不能当保证。这条判据不是从模型能力出发的，而是从程序把什么问题交给模型出发的。

| | 选下一步 | 决定遗忘 |
|---|---|---|
| 模型看到的状态 | 当前页面、元素表、目标、最近动作 | 整段对话的拟合骨架，工具结果只剩一行说明 |
| 反馈 | 页面变化、遮挡、重复，下一步可见 | 删除后果延迟，常无可归因信号 |
| 错误代价 | 局部，常可重试 | 可能影响后续多步；删除本身不可逆，只能靠重跑补救 |
| 候选集 | 每次观察重建 | 非固定工具调用，文本消息受保护 |
| 验收 | 执行器校验；示例有独立检查 | 无端到端验证，失败只回退摘要 |

## 4. 局部指标怎样变成长期结果

浏览器示例的数字很具体：录制的那次航班搜索 7.073 秒完成；六次交替运行，两个版本各 3/3 通过；中位任务时间 9.450 秒降到 7.092 秒，降 25%；TypeSafe 请求从 22 降到 17，浏览器协议调用从 1,092 降到 101。

但这些数字回答的不是“Jev 比 LLM 快多少”。两个对照版本用的是同一个 Jev 1.13.0、同一个 Mercury 2.5、同一个目标、同一个独立检查器、同样的视口和预算；原版是冻结在 68c077b 的代码，差别在快照、点击守卫、等待和文本替换的实现。作者自己说，三对样本太少，符号检验 p=0.25，这不是广泛的 agent 基准。它证明的是：在这个任务上，把动作空间和观察做细，能减少浏览器往返和时间；它没有证明决策模型本身比一个合理配置的 LLM 更好。

压缩插件的数字更少：它报告压缩比例、保留/截断/删除的条数、状态 token 和请求数；当压缩比例低于 25% 或 Jev 失败时，回退到 Claude Code 内置摘要。仓库的测试覆盖状态裁剪、决策映射、请求校验和回退，但没有端到端任务成功率或返工率的对照。它能证明“这套流程可以跑、能在失败时退回去”，不能证明“被删掉的内容不会在后面造成返工”。

讲稿是教学演示，不是评测。10-26 的热点稿说这个演示“没有公开代码”；更准确地说，讲稿有四张代码幻灯片，但没有配套的可运行仓库，而且幻灯片之间的签名和粒度不一致。它可以用来理解结构，不能用来估计漏判率、延迟或成本。

把三份材料放在一起，能支持的结论是有限的：在候选集完整、状态够用、反馈及时、程序能验收的前提下，把局部判断交给决策模型可以把单次判断压缩成有限选择；现有公开材料没有给出“决策模型对合理配置的 LLM”的公平对照，也没有给出长程任务的成功率或返工率。按这套证据标准，举证责任在采用方：先证明候选覆盖、状态可见性和端到端结果，而不是只证明单次调用少、单次延迟低。

## 5. 程序保留了哪些不可外包的判断

把两条线收拢，程序保留的不是一件小事，而是五类判断。

第一类是问题定义：什么算候选，什么受保护，什么算有效答案。浏览器里是“当前观察到的元素 + 兼容的操作/目标”；压缩里是“非固定的工具调用 + 两个是非题”，文本消息不参与删除。

第二类是状态构造：什么可见，什么被省略，什么被固定。浏览器只送可见文本、元素表、目标与最近动作；压缩把整段对话拟合到 25k，工具结果只剩一行说明，第一条和最近六条固定。

第三类是答案空间：哪些选项可执行，概率怎样映射成动作。浏览器只执行被选中操作的目标头；压缩把两个概率按阈值映射成保留、截断、删除。

第四类是执行与校验：动作是否还能执行，输出是否合法，结果由谁验收。浏览器检查页面新鲜度、遮挡和文本 JSON；压缩重建消息、删空消息，失败时回退内置摘要。

第五类是停止与回退：什么时候算卡住，什么时候压缩，压缩不够时怎么办。浏览器有受阻、重复无变化和步数预算；压缩有 60% 触发、25% 最小压缩和内置摘要回退。

模型能做的，是在这些已经写好的问题上报概率。它不能新增候选，不能改写问题，不能要求补查，不能验收自己。文本子模型被允许在缺信息时返回空值，但执行器把空值当无效输出报错，而不是进入追问流程；“受阻”是停止信号，不是求助信号。在这两个实现里，模型也没有“转交”这个动作：压缩失败时是程序回退到 Claude Code 内置摘要，浏览器受阻时是程序结束这次运行。

这也是为什么“16 行”容易让人低估这件事。16 行是调用模型、拼状态、跑循环的表面代码；在本次核对的提交里，真正把压缩做成可用的插件，核心库约 750 行 TypeScript（不含类型与测试），大部分篇幅在状态构造、裁剪、分批、决策映射和消息重建，不在模型调用。浏览器示例也类似：模型调用只是其中一段，快照、元素表、执行和校验占更多。在这两个实现里，模型调用被压得很轻，程序侧的问题定义和验收反而成了主要工作量。

所以，“省掉了什么，又把什么留给了程序”可以收成一句话：模型省掉的是开放式生成，只保留在固定候选集上打分；程序留下的是问题、世界、执行和问责。模型的准确率是必要条件，但不是充分条件；如果程序把错误的世界或错误的选项交给它，准确率越高，错误越自信。

## 尚未解决的问题

- Jev 的内部结构未公开，校准没有独立第三方验证。现有代码能告诉我们它收到什么问题、输出什么概率，但不能告诉我们这些概率在浏览器动作或工具保留任务上是否校准。
- 缺少与合理配置的 LLM 的公平对照。浏览器示例的 25% 是同一运行框架（harness）下的对照；压缩插件没有“让 LLM 输出保留/删除的短标签”的基线。讲稿甚至说可以把 Jev 换成小 LLM，这说明模型不是这套结构的必要条件。
- 缺少端到端成功率与返工率。浏览器示例是一个任务、三对运行；压缩插件只有压缩比、决策条数和请求数。局部指标改善不等于完整任务改善，这一点现有材料没有回答。
- 候选覆盖没有被检测。浏览器不支持影子根、内嵌框架、画布等结构；压缩把工具结果内容换成一行说明。两者都可能让正确选项或证据从未进入模型的世界，而系统没有“候选缺失”的信号。
- 非幂等工具的安全删除没有解决。“删了再读”对读文件成立，对发邮件、写数据库、执行有副作用的命令不成立；插件的候选集不区分工具类型。
- 生产成熟度不同。讲稿是教学演示，压缩插件的 Claude Code 集成依赖早期访问函数钩子（function hook，2.1.274+），浏览器示例是 0.1.0 的公开示例；三者都没有长期使用数据。
