这一期的主线是「怎么把验证做出来」：Claude Code 团队给出三类值得投入的测试，并说清了自己怎么防止验证器骗人；一份 8,300 万 token 的评测说明换模型时该不该顺手换 harness，答案是同一套组合换个模型就能从第一掉到第十六；Simon Willison 给出「agent 在外面、代码在里面」的沙箱结构；还有人做了个代理，让远端 agent 用本机凭据却拿不到密钥。

## 本期值得了解

### 1. Claude Code 团队怎么让 agent 自己验证：三类测试与防作弊

Anthropic 11-16 的工程文给了一个前提：Claude Code 团队约 90% 的代码由 Claude 写与审，所以他们把「让 agent 用证据自证」当成基础设施——有验证回路，你可以同时跑几十上百个 agent，没有就只能跑一两个、自己全查。内部测试里，让一个独立评分者按 rubric 检查文件生成，比标准提示词循环最多提升 10 个点，难题上收益最大。三类值得投入的测试各有分工：端到端测试最难糊弄，要么整个功能好要么不好，还能给出具体坏在哪；属性测试（往返编码、不变量、幂等、等价）用大量输入去反驳「我认为不会失败」的假设，这些输入不带写代码那个 agent 的偏见；差分测试把旧系统当 oracle，适合大规模迁移。文中也点了失败模式：测试不稳定会让 agent 学会重跑而不是修代码，测试太慢会让它少跑批次。

来源：[How the Claude Code team thinks about verification](https://claude.dev/blog/how-the-claude-code-team-thinks-about-verification/)｜Anthropic（Addy Osmani）｜2026-11-16；[HN 讨论](https://news.ycombinator.com/item?id=50529612)（262 分）

### 2. 换了模型就该换 harness：Codex CLI 从第一掉到第十六

RUNTA 与 Baseten 11-17 发布 FrontierHarness v1.1：22 个 harness 配置 × 5 个模型（GLM-5.3、GLM Flash、DeepSeek V4.1 Flash、Muse、Kimi-K3）× 62 个任务 × 4 次尝试，共 2.7 万次运行、8,300 万 token。结论很直接：每个模型的最佳性价比 harness 都不同——Codex CLI 配 GLM-5.3 最好，配 Kimi-K3 掉到第 16；按任务成本排名，中位 harness 在换模型时移动 11 个位次。跨全部模型只有四个落在最优前沿：OpenCode v2（最低 \$0.561/任务）、Pi、Codex CLI、ZCode（最高通过率 61.9%）。他们的「最佳性价比」定义是每通过一个任务的最低成本，除非另一个贵不到 30% 却多通过 5 个点以上。

来源：[Introducing FrontierHarness Eval v1.1](https://runta.com/blog/introducing-frontierharness-eval-v1-1/)｜RUNTA｜2026-11-17；[HN 讨论](https://news.ycombinator.com/item?id=50532191)（335 分）

### 3. 外部沙箱：agent 在外面，它执行的代码在里面

Simon Willison 11-17 与 Prime Radiant 合作提出「外部沙箱」结构：agent 本体跑在沙箱之外，它要执行的代码被送到一台专用沙箱里跑，两者只通过 localhost API 通信。他们放了三份实现——v86 在 WebAssembly 里跑 Alpine Linux、Apple Containers 里跑 Alpine、以及用微软 Quicksand（打包了 QEMU 与 Alpine）的 Python 版；三份实现暴露同一套 API，Pi、Claude Code、Codex 都能把代码执行指向它。沙箱还带可选的 HTTP/HTTPS 白名单代理与凭据替换机制，让 agent 能调用需要认证的 API 却拿不到密钥。

来源：[External sandboxes for coding agents](https://simonwillison.net/2026/Nov/17/external-sandboxes-for-coding-agents/)｜Simon Willison｜2026-11-17；[Prime Radiant 原文](https://blog.primeradiant.com/external-sandboxes-for-coding-agents/)

### 4. 让远端 agent 用本机凭据，却拿不到密钥

11-13 的一篇实践把凭据问题拆开了：作者把 agent 都跑在可丢弃的 VM 上，笔记本只留 SSH 密钥、1Password 与已登录的 gh/云 CLI；他写的 lend 挡在 SSH agent 前面，agent 请求 `gh repo view` 时，命令是在笔记本上以他的登录执行的，token 从不离开本机。每条请求都要过笔记本上的策略并按需 Touch ID 批准，策略默认拒绝、只放行可执行文件与密钥指纹，还能用 `args_prefix` 只允许某些子命令；通过 MCP 暴露成一个 `run_local_command` 工具，理由字段必填但标注为不可信。作者也明说了它防不住什么，思路与外部沙箱互补。

来源：[Running coding agents without handing them my credentials](https://blog.antonio.cx/running-agents-with-lend)｜antonio｜2026-11-13；[HN 讨论](https://news.ycombinator.com/item?id=50526152)（128 分）

### 5. Managed agent 可以自带沙箱：推理在 Google，命令在你的机器

Google 11-16 的开发者月度汇总里提到，Gemini Managed Agents 开始支持自托管环境：模型推理与 agent 循环跑在 Google 侧，bash 命令与文件编辑在用户自己的计算里执行。worker 用受限密钥走出站 HTTPS 连出去，不需要开任何入站端口；生产上可以部署在 Modal、E2B、Cloudflare、Daytona、Fly.io、Vercel 或 Cloud Run。本地模式的说明写得很直白：不额外隔离时，bash 直接在宿主机上跑。

来源：[Gemini 4 Carbon, Hydrogen, Decisions API, self-hosted agent sandboxes and more](https://www.philschmid.de/google-deepmind-roundup-nov-2026)｜Google DeepMind（Philipp Schmid 汇总）｜2026-11-16
