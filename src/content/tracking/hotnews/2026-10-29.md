这期三条各问一个不同层面的事。第一条问成本：Claude Code 为了在面板上显示每个后台子代理做了什么，每 30 秒把该子代理的完整记录重发一次给模型；第三方测出这占子代理密集会话花费的一成多，官方给出的全量数字只有 2%–6%，两种口径都值得看。第二条问护栏：GitHub 把「用自然语言写工作流、让 agent 在 CI 里无人值守地跑」做成正式功能，值得看的是它怎样把意图先编译成可审的 YAML，再把动作拆成只读、校验、施加三段。第三条问能力边界：一份只给客户请求、不给题目的税务基准，最好成绩通过率 10.8%，失败集中在「客户没问但重要」的判断上。

## 本期值得了解

### 1. Claude Code：一条状态行每 30 秒重发一遍子代理的整段记录

Claude Code 的代理面板里，每个后台子代理（background agent，在后台独立跑任务、由主会话派生）带一行 3–5 个词的状态描述，用来说明它正在做什么。这行字不是本地生成的：自 2.1.232（2026-08-13）起默认开启，每个**活跃**的后台子代理大约每 30 秒会被问一次「用 3–5 个词描述你最近做了什么」，问题里带的是该子代理的完整对话记录和完整工具清单。答案只更新面板上那一行，不会回到子代理上下文，也不进你的对话。

第三方把它量了出来。Flamerix AI 在 10-26 发布的一份实测与补丁说明里，用 Claude Code 自己的 OpenTelemetry 事件按请求来源分组：一周内这类摘要请求占其估算花费 **16.4%**（同期主对话 15.7%）、占总 API 请求 **19.7%**，其中 96% 落在 Opus 上，输入输出比约 9,000 : 1。同一现象还有一份更细的独立测量——GitHub 上 8-15 提出、至今未关闭的功能请求（issue #86879）统计了一次 4 小时会话：27 个子代理、1,496 次请求里 339 次是摘要，占 22.7% 的请求、22.2% 的原始 token，按 Opus 价格加权 18.0%；这些调用产出约 2.2 万输出 token，平均每次约 65 个 token 的装饰性文字。

官方口径小得多，而且给了机制边界。10-29 一位自称在 Claude Code 团队工作的工程师在 Hacker News 讨论里回帖确认了机制，并补充：只对**正在干活**的后台子代理触发，空闲的不发；摘要同时供人和 Claude Code 追踪每个子代理在做什么（不必读记录）。他说在开启遥测的用户里，这项约占 API 列表价成本的 **2%**、请求的不到 4%，终端场景约占 6%，并承认「对一条状态行来说这仍然很多」；2.1.311 起修了最贵的那一类（漏掉提示词缓存的摘要），更便宜的模式正在做——把短笔记而不是整段记录发给更小的模型。

两种数字并不互相否定，因为分母不同：16%–18% 那组样本，按官方工程师的说法「像是一个主要跑后台子代理的团队」；2%–6% 是全部开启遥测用户的平均。真正值得注意的是它怎么被藏起来：这些请求带 `skipTranscript`，**不写进会话日志**，只出现在 OpenTelemetry 导出里，所以任何按 transcript 算成本的工具都会系统性低估这部分开销；`/usage` 直到 2.1.311 才开始显示大的缓存未命中。补丁作者还指出，2.1.310 已经带了一个更便宜的 `short` 模式（约 2k token 的笔记，可交给更小的模型），但默认仍是整段记录——与工程师「正在做」的说法并置，说明代码已埋、默认未开。官方没有提供关闭开关；那个补丁的做法是用 Bun 预加载拦截全局定时器，代价是面板状态不再更新。

值得理解的不是「某产品多花了钱」，而是多代理 harness（代理运行框架）在这里做了一个具体取舍：为了让**人和编排层都不读记录就知道每个子代理在干什么**，它维护一份持续刷新的共享状态表示，而这份表示的成本按「子代理数量 × 墙上时间」计费，不按有效工作计费——三个长时子代理并行时，每分钟要付六次这样的调用。这层东西该记在谁头上、要不要暴露给用户，目前没有共识。

### 2. GitHub Agentic Workflows：把 agent 放进 CI，先编译成可审的 Actions

GitHub Next 的开源项目 **GitHub Agentic Workflows** 10-28 转为正式可用。它要解决的场景很具体：议题分诊、CI 失败分析、文档更新、补测试这类「需要推理但每次都要人来点一下」的活，能不能交给 agent 在 Actions 里自己跑。

形态上有一个值得看的决定：工作流用自然语言写在一个 Markdown 文件里，然后**被编译成标准的 Actions YAML**。因为最终产物就是 Actions，它沿用既有的 runner 组与策略约束，而不是另起一套调度和权限模型；每个工作流可以选 Copilot，也可以接别的 coding agent。这一步等于把「意图」先降级成确定性、可审、可纳入代码评审的产物，再让 agent 去执行。

护栏是分层的，顺序也清楚：agent 读 GitHub 内容时受完整性过滤规则约束，**默认只有只读权限**；它在一个沙箱容器里执行，位于 Agent Workflow Firewall 之后；产出经「safe outputs」流程校验，再由一个专门的**威胁检测作业**扫描将要施加的改动。从预览到 GA 加的东西包括：自托管的 Actions Runner Controller（在自己的机器上跑 CI 作业）与 Docker-in-Docker、预算预测（含威胁检测额度与月度区间）、按工作流选模型与模型路由、Cloud Hypervisor 或 NVX 微虚拟机（microVM，比容器多一层内核级隔离）隔离，以及跨仓库工作流用隔离区（enclave）防数据外带。Accenture 一位负责人给的数字是：单个负责人每周省约 29 小时、团队实测速度翻倍、AI 写了 91% 的提交、生产错误从每天约 1.1 万降到 1,000 以下——客户自报，没有对照条件。

为什么值得理解：这是「循环工程」（loop engineering，设计一个代替人工持续触发并验证 agent 的系统）落地时最少被讨论的一半——不是怎么把 agent 叫起来，而是**它无人看着的时候凭什么只能做被允许的事**。这里的两条路可以做对比：一条是把每条命令交给分类模型当场判断（10-26 转正的 Copilot assisted permissions），代价是可测性差；另一条是把 agent 的动作限制在可校验的产出契约里——只读进来、产出先过校验、施加前过威胁检测作业。后者更容易审计，但它把风险都押在「校验规则写得够不够」上。

边界要说清：GitHub 没有披露 safe outputs 与威胁检测作业的误拦、漏拦数据，也没有说威胁检测用的是什么模型、阈值多少；「自然语言编译成 YAML」是否逐条可读可审、编译歧义怎么处理，发布说明也没写。客户数字没有任何对照组。

### 3. DAYJOB: Tax：只给客户请求、不给题目的专业税考，通过率约一成

Surge AI 10-27 发布 **DAYJOB: Tax**，是它那条「能不能顶下一个岗位」基准线的最新一份。与多数税务评测的区别在起点：常见基准给的是一道已经定义好的题（算一张申报表、答一个税法问题、向模拟纳税人追问缺失信息），而这里给的是**客户请求加一堆记录**——报税表、K-1 与 W-2（美国报税表单）、税务局通知、总账、合同、往来邮件，还有手写收据的照片。agent 要自己判断该做什么、哪些记录互相矛盾、哪些问题客户没提但重要，最后交出申报表、工作底稿、技术复核或客户建议。

规模与口径：50 个环境、1,789 个文件（每个任务中位数 30 个、最多 123 个；其中 1,487 个 PDF、117 个 Excel、38 个 Word），覆盖个人与家庭、小企业、合伙、房产与投资、遗产赠与信托、国际税、公司交易、税务复核与争议八个方向。评分是 pass@1（每题只跑一次），一个任务须满足 95% 的评分项才算通过。榜上 Claude Sonnet 5.5 以 10.8% 领先，Fable 5.1 为 9.6%，Opus 5.5 为 9.2%。

两个例子比排名更能说明它在测什么。第一个：客户问 2026 年 10 月还是 2027 年 1 月卖房更省税，两个日期都满足「出售前五年内住满两年」的免税额条件，agent 也都算对了；但客户 2024 年 8 月搬出，资格会在 2027 年 8 月底失效——Astra 五次都没提这个截止日，Opus 五次都提了。第二个方向相反：一对分居的夫妻问怎么分 Roth IRA 与 401(k)（美国的退休账户），Opus 五次都基于「你们没有合法婚姻」给出方案，即便它自己承认不确定；Astra 有四次指出必须先确认婚姻状态（两人曾在得州同居、在科罗拉多办过仪式）。

这就是它想测的东西：不是算得对不对，而是**会不会主动去发现客户不知道自己该问的问题**。两个例子方向相反，说明差距不在「哪个模型判断力强」——Astra 在卖房截止日上五次全漏，却在婚姻状态上比 Opus 更警觉；同一个模型的盲点会换位置。

边界：任务由税务专家三层复核（正确性、完整性、可解性），但基准闭源、需申请，榜单由 Surge 自行运行与汇报；95% 的阈值相当严，10.8% 不等于「只能做一成工作」，两者不能混用。

来源：[DAYJOB: Tax — Benchmarking AI Agents on Professional Tax Work](https://surgehq.ai/blog/dayjob-tax)｜Surge AI｜原文：2026-10-27｜B（基准方自跑自报，任务经专家复核但不可独立复现）；[Hacker News 讨论](https://news.ycombinator.com/item?id=50275626)｜2026-10-28｜248 分、约 162 条评论

### 4. GitHub 把记忆做成常驻层：Memory 转正，Dreaming 在后台改写它

Copilot Memory 转正式可用（付费档）：跨会话、跨客户端记住个人偏好与仓库约定，会话会自主生成和整理记忆。同时公开预览的 **Dreaming** 是一个后台循环，分三类：个人记忆整理（按对话更新个人记忆）、仓库定制（管理仓库级记忆，并对已入库的技能与自定义指令文件提出修改）、评审定制（把反复被接受的评审意见变成代码评审指引）。它可以增、改、删记忆；**对已入库技能与指令的改动以 PR 提议，交人审**，而个人记忆由 agent 自主改。默认关闭，按 AI 额度计费。另有跨仓库代码搜索（精确、正则、语义）与 `/research` 追问，用来在不克隆的情况下追一条跨仓库调用链。

值得看的是「审查强度按对象分叉」这个设计：记忆和技能都是长期指令，但一个允许 agent 自己写，一个必须走 PR。预览期的自报数字（用到记忆的会话里 93% 偏好遵循更好、42% 工作流更高效）没有定义指标也没有对照，只能当能力主张。

### 5. Copilot Fusion 转正式可用：把「路由 + 交叉评审」做成一个模型选项

模型选择器里选 Fusion 不再指某个具体模型，而是选一个按任务挑模型并编排它们的系统，选完只挑努力档（Standard／High／Max）。编排有三种工作流：单模型直解、级联（便宜模型起草，质检决定接受还是升级到更强模型）、批评（一个起草、另一个评审、起草者修订）。管理员可以限制 Fusion 能用哪些模型、是否设为默认；计费按各模型原价结算（对付费档限时给 30% 折扣）。GitHub 称在 Artificial Analysis Coding Agent Index 上 Fusion Max 得 60，与 Claude Code + Opus 5.5 Max 相差 2 分以内，平均每任务 API 成本约为一半、token 约一半、时间少约 40%。

与 10-04、10-15 两期已记的 HydraFusion 研究预览相比，本次增量是转正式可用、给出上面这组量化，并支持选择本地模型；级联与批评的机制本身不是新的。

## 值得继续追问

- 条目 1：官方 2%／6% 与第三方 16%／18% 的差距，究竟来自会话形状还是统计口径（是否含缓存未命中、是否按列表价）？更要紧的是：当这类「旁路调用」不进会话记录、只出现在遥测里，团队怎样自证限额被谁花掉？
- 条目 2：safe outputs 与威胁检测作业的拦截边界没有任何公开数据（误拦、漏拦、模型与阈值都未披露）；自然语言编译出的 Actions YAML 能不能被人逐条审，是这套东西能不能进受监管流程的前提。
- 条目 3：95% 阈值下的 10.8%，更像能力上限还是口径产物？把阈值降到 80% 时排名会不会变——这决定它是「agent 还做不了专业工作」还是「评测太严」。

### 7. OpenAI 称隔离环境里的 agent 用 CPU 缓存时序互相传信

已转述到的内容：The Decoder 10-24 报道 OpenAI 一篇关于训练环境遏制的文章。在一次测试中，agent 被要求在不联网、没有共享可写文件的情况下交换合成的秘密，它们用处理器缓存的时序（一个改动缓存里的数据，另一个测加载时间差来解码）、共享内存的写入模式，以及 OpenAI 自己的离线基础设施来传信；有 agent 在推理记录里写下「可以用持续写入与空闲的差别做一个类似声学调制解调器的信号」。另有一次只给一份通用漏洞清单，让 agent 自己找通道，它们独立发明了编码方案。转述还提到训练暂停期间 agent 红队发现了 Kata Containers 的漏洞（编号称 CVE-2026-24834）并借以逃出虚拟机，以及「每次新训练跑批前都要先做 AI 红队」。
