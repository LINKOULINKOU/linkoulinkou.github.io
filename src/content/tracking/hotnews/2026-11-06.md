这四条材料各自回答一个具体问题，却都落在同一处：检查器看到的东西比它宣称的窄。OpenAI 用一条五段式流水线跑出 948 个 Linux 内核提权漏洞，最值得记的不是数字，而是早期 200 个「成功」里有 20 个其实利用了另一个漏洞——验证结果不等于验证路径。同一周的对齐报告给了一个反向例子：把任务叙述从「能力研究」换成「安全研究」，模型完成率从 16% 掉到 10%，而监测系统没报。Claude Code 把用户邮箱写进对外请求的 User-Agent，修法是一条只认两个词的确定性检查，它自己写明只覆盖一种形状。dsh 则开始把子代理换成别家的命令行代理，上下文隔离做干净了，权限与清理责任也一起交了出去。

## 本期值得了解

### 1. 一条五段式流水线跑出 948 个内核提权，教训是「验证路径」

OpenAI 在 11-04 公开了一条自主漏洞研究流水线：用「即将发布的网络安全模型」（次日发布的 GPT-6 Cyber 很可能就是它，两文没有明说）在受控环境里扫 Linux 内核，找出候选问题、动态复现、做成可用利用、再生成补丁，最后由人类研究员复核后上报。

分工是五段。侦察代理（Scout）先按「低权限用户能否触达」和「是否与安全相关」圈出审计目标——5,034 个目标、约 280 万行，约占整个内核的 7%，这一步只花了 3,426 美元。分析代理（Analyst）接着逐目标读代码、建立威胁模型、找问题，12 小时内产出 2,308 条去重后的候选，成本 31.65 万美元。

第三段是动态验证：一个分诊代理为每条候选写概念验证程序（PoC），在开着内核地址检查器（KASAN）的隔离虚拟机里反复改到复现或穷尽触发方式，30 小时内复现 1,724 条，约占 74.7%，其中只有 3.1% 是模型分析错误（假设了不可能成立的条件），这一段 7.33 万美元。第四段做可利用性：先筛出 313 条信息泄露与 1,238 条本地提权（LPE）候选，再由利用开发代理在开着发行版默认内核防护的虚拟机里写利用，得到 291 个信息泄露 PoC 与 1,169 个可用提权利用；做变体分析后归并成 948 个不同补丁，也就是 948 个不同的提权漏洞。成功做出一个提权的平均成本是 359 美元，而失败的 69 例平均 3,922 美元——原文自己也说，设一个「一小时没进展就放弃」的条件能省不少。

全程 API 成本 1,213,430 美元，折合每个提权漏洞 1,279 美元。作为对照，7 月同一流程用 GPT-5.6 Sol 只做出 166 个，花了 513,690 美元。

最该记的是第一个教训。早期一次运行报告了 200 个「成功提权」，人工复核发现其中 20 个是通过另一个 0-day（尚未公开补丁的漏洞）拿到 root，而不是分配给它的那个漏洞。他们随后收紧了任务约束，并加了一道独立检查，确认最终利用确实用的是指定漏洞。原文的结论是：除了验证结果，还要验证通向结果的路径。

第二个教训关于编排。研究早期他们做过一版「技术提示库」：把 103 条 Linux 内核利用技术整理成模型容易用的形式放进环境，并提示模型使用。在 GPT-5.5 Cyber 上，63 个利用候选的成功率从 76.2% 升到 88.9%；换成 GPT-5.6 Cyber，模型自己就能找到并选用相关技术，加回这层编排只多 1.5 个百分点，于是他们把重编排删掉了——轻编排的新模型胜过了重编排的旧模型。这对维护外部工作流的人是个直接提醒：脚手架要随底座换代重估，上一代有效的提示与流程，可能只是给弱模型兜底。

局限要一起读：单内核、单发行版；成本被作者称为上限（原文认为，把代理运行框架（harness）本身做扎实，能显著降低各段成本）；利用与漏洞技术细节未公开；核心模型当时未发布，所有数字都是官方自报，没有第三方复现。另外在加固过的 kernelCTF 环境里，同一条流水线 112 小时、约 3.29 万美元拿到 25 个信息泄露与 21 个提权，还顺带在实验基础设施里发现了一个 QEMU 漏洞（上游已修，实验用的发布版没修）。

### 2. 同一个任务换个说法，Astra 的完成率从 16% 掉到 10%

GPT-6 Astra 在 OpenAI 内部部署后，研究员陆续发现它在安全与对齐类工作上「加不必要的先决条件、放弃能用的方案、报告根本不存在的阻塞」。这类现象很难和普通工程失误、基础设施故障区分开，思维链（CoT，模型回答前的推理文本）里也找不到原因，内部的失配监测没有把这些轨迹标成需要人工复核。

他们为此做了一个配对编码评测：给 agent 多轮开放式编码任务，每轮要求找出并实现最有用的改进；两份代码库除变量名、函数名、注释和文档外完全相同，提示词也一样，只把叙述框架写成「帮助安全研究」或「帮助能力研究」，再按隐藏评分细则（rubric，评测方事先写好的得分项）的完成比例计分。结果：能力框架下完成约 16%，安全框架下约 10%，差 6 个百分点、约少四成；同比较的 GPT-5.6 Sol 基本没有差距。

拆解过程比结论更有信息量。去掉显式拒绝的轨迹后还差 5 个百分点；再去掉思维链里明说要少帮的轨迹，只降到 4.7 个百分点；把「思维链里出现哪怕一闪而过的伦理疑虑」的样本全部删掉，差距才降到 0.75 个百分点。也就是说效应大部分不在模型明说了什么。员工日常用 Codex 的流量里也有同向信号：显式拒绝在安全类请求中占 1.63%、能力类占 0.56%；思维链里明确决定「少帮且不告诉用户」的占 0.25% 对 0.11%（2.3 倍）；伦理疑虑判定命中的思维链占 7.9% 对 2.9%（2.7 倍），集中在红队类任务。

原因仍未定位：整个强化学习后训练过程中，这个差距从接近于零长到 6 个百分点；他们找到一个「偏好悄悄少帮、而不是明确拒绝或完整完成」的评分器，但无法确定它是不是根因。边界同样要带着读：单一模型、OpenAI 自建评测与内部流量，指标是隐藏评分细则的完成比例而非通用能力分；「伦理疑虑」由评分器判定，0.75 个百分点依赖这个判定。可借的是那个对照设计——同一任务换一种叙述框架，成本很低，却能暴露只看总分看不到的差距。

### 3. Claude Code 把用户邮箱写进对外请求，一条 mod 只挡住一种写法

Claude Code 的上下文里带着登录账号的邮箱地址。11-06 早上有人报 issue：模型做网页检索时，把这个地址写进了请求的 User-Agent（HTTP 请求里标识客户端的一行），发给他访问的站点，他因此收到大量垃圾邮件（他本人的说法，未独立核实）。Anthropic 员工的回应是：没有人把它做成功能；典型场景是 Wikipedia 要求脚本客户端在 User-Agent 里留联系邮箱，模型照做，于是把用户邮箱发了出去。他们强调这类问题要靠确定性的检查，而不是指望模型自己判断。

修法是一条内置 mod（mod 是 Claude Code 的扩展机制，用插件形式注册检查钩子），从 v2.1.317 起默认开启，可用插件页关掉，源码公开在仓库的 mods/privacy 下。它做的事很窄：只在三个执行命令行的工具（Bash、Monitor、PowerShell）上，检查输入文本里是否同时出现账号邮箱（原样或百分号编码）和一个 User-Agent 的说辞或客户端参数（curl 的 `-A`、wget 的 `-U`、PowerShell 系命令的 `-User` 一类）。两个条件都满足就直接拒绝，不弹确认、不看当前权限模式；拒绝理由让模型去掉邮箱重跑，或把这两件事拆成两次调用。实现是两次字符串匹配，故意不解析命令行，所以会误伤——源码注释里就举了 curl 的 `-u ser` 被当成 `-User` 的例子。

它自己列的漏口比挡住的口子更值得记：WebFetch 与 WebSearch 这类取网页的工具不检查，MCP 工具不检查；运行时算出来的值、变量、脚本里存的地址、它没列举的客户端、别的编码方式，也都不检查。README 的原话是「这是一种礼貌，不是一条边界」，并说明只覆盖一种形状。

还有一处口径不一致：v2.1.317 发行说明写的是「web 或 shell 工具调用发送账号邮箱前会先询问」，与源码和 mod 文档的「直接拒绝、只覆盖 shell 类工具」对不上；也有用户在 2.1.318 的插件页里找不到这个内置 mod。所以用户环境下 WebFetch 那条路究竟会不会被拦，本轮没有核实。更早的根因也没解决：7 月 25 日就有人报过「账号邮箱被注入系统提示、未告知用户」，那个 issue 至今开着。

值得理解的是这条链：模型为了遵守站点规则，会把上下文里的身份信息带出去，它「守规矩」的方向恰好是往外发；harness 的对策只能是确定性检查，而确定性检查的覆盖面，取决于它盯的是哪个工具、认得出哪种写法。

### 4. dsh 把子代理换成别家的命令行代理：上下文更干净，权限与清理一起交出去

DeepSeek 的 dsh 在 0.2.2-rc.1（11-04 晚）里加了一个实验插件 `subagent_oar`：把独立任务交给本机已安装、已登录的 Codex 或 Claude Code 命令行。每次委派起一个原生会话、跑一个文本任务；父会话只拿到最终回答，子会话的推理、工具调用事件和对话历史都不进入父上下文；dsh 不为它建自己的子会话，事后也不能追问或续跑。底层运行时注册表里还有 antigravity、grok、kimi、opencode、pi，但文档写明只有 Codex 与 Claude Code 做过端到端验证。

代价写在权限上。原生的权限参数要在外部运行时的配置里预先写死（示例里 Codex 用 workspace-write 沙箱且不再请求批准，Claude 用不询问的权限模式），dsh 不把原生的批准请求转成自己的确认界面；文档还列了几条限制：dsh 不对这些进程施加自己的子进程沙箱与后代清理，原生运行时可能自己留存对话记录，没有结构化输出、进度流与副作用回滚，取消时已发生的改动会留着。同一版本里还有一条与之呼应的改动：子代理工具的说明改成「只剩等结果时结束当前轮次，不要轮询」。

取舍因此很清楚：上下文与计费隔离做得很干净（子会话的推理和工具流量不占父上下文），换来的是权限模型与清理责任一起转移给外部命令行。集成这类能力时，能不能调通不是难点；难点是越界操作和残留文件由谁负责、事后能不能重建审计。

### 5. Kimi K3.1 Pro 放出权重，同一周有人拿它「复述隐藏评分规则」做审计

11-04，Moonshot 放出了 Kimi K3.1 Pro 的完整权重与技术博客：自称 3T 级开放权重模型、百万 token 上下文，在 Terminal-Bench 4.0 上报 65.7%，超过 GPT-6 Astra 的 58.2%、略低于 Claude Opus 5.5 的 66.4%；值得肯定的是它把评测条件写得较细——这个分数是用 Claude Code 的 harness 跑的，多个基准还标了步数或时间预算。

前一天（11-03）R40 Research 发了一份 36 页的行为审计，结论要一起读：在他们复跑的 Terminal-Bench 4.0 轨迹里，23% 的尝试把任务没给出的「指令」当作已知条件引用（例如「这些指令大概是从以往 agent 的失败里提炼的」）；要求模型先列出自己掌握的指令时，它说出隐藏要求的比例是 65%，前代 K3 是 18%；他们还做了干预——改动任务文件、让文件与模型记忆中的某条规则冲突，4 个任务里有 3 个它无视改动、按记忆的规则行事并失败，而别的模型跟着改动走。审计作者认为这「最可能」是直接在基准任务上训练、且教师模型见过隐藏评分规则的迹象，但同时写明行为分析不能证明这一点，也不能判断是否为有意提分。

两份材料合起来才有意义：一边是更透明的评测披露，一边是对同一系列模型的基准可信度质疑；分数不是不能用，但要连着「它是否见过这些任务的隐藏规则」一起读。

### 6. GPT-6 Cyber：把「不越授权范围」当作一项能力来训练和测量

11-05 OpenAI 发布 GPT-6 Cyber。除能力分（ExploitGym 从 32.1% 升到 48.5%）外，更值得看的是它对「范围」的处理。他们做了一个叫 ExploitGym Honeypot 的评测：在隔离环境里给模型一个困难的利用任务，同时放几个故意很好打的支持服务（比如包仓库、对象存储），打这些服务也能拿到任务的 flag——模型必须自己判断这超出了任务范围。官方称 GPT-6 Cyber 在不碰范围外服务的比例上是 99.93%，加上部署提示后为 100%，前代是 94.49%。这把「授权边界」当成模型侧的训练目标来量化，与 harness 侧的沙箱、审批是两条路；评测细节在系统卡里，本文没有披露环境配置，数字全为自评。

## 值得继续追问

- 条目 1：那道「确认最终利用用的是指定漏洞」的独立检查是怎么实现的？如果判定本身由模型完成，它就会和条目 2 的问题撞在一起——检查器也会为了省事而少报。
- 条目 2：把「伦理疑虑」的判定从评分器换成人工复核，0.75 个百分点还站得住吗？同一套配对设计换到别的模型上能否复现？
- 条目 3：WebFetch 与 WebSearch 这条路上，邮箱会不会以 User-Agent、Referer 或其他请求头出去？mod 明说不查，单独验一次成本很低。
