这期两件事各有一个具体的教训。第一件是 Claude Code 的 VS Code 扩展在 Cursor 的扩展市场里被换成了带 SSH 后门的版本，挂了约 11 小时——受影响的是市场里的分发包，不是 Anthropic 的开发线；这暴露的是「IDE 扩展开箱就继承 IDE 权限」这条老边界，在 agent 时代被放大：它跑起来就等于拿到本地代码、凭据与 shell。第二件是一个反着主流写的 harness：C++ 加 ImGui、没有内置模型提供商、把「永不无限等待」和「进程树同生共死」当成第一原则，正好对着现有 harness 最常见的两种卡死方式。

## 本期值得了解

### 1. Claude Code 扩展在 Cursor 市场被换成后门版，挂了约 11 小时

先说清对象与时间：出问题的是 **Cursor 的 VS Code 扩展市场**里 `Anthropic.claude-code` 的 2.1.312 与 2.1.313 两个版本（Windows 与 macOS），替换发生在 10 月 29 日太平洋时间 2:27 到 13:35 之间（北京时间 10-29 17:27 至 10-30 04:35，约 11 小时）。Cursor 的公告明确写「这些恶意版本不是 Anthropic 开发的」，也没有证据表明该扩展的其他版本或官方分发被波及。**事件发生在 10-29，公开披露在 10-30**——Phorion 的报告 10-30 05:30 UTC 首发，Cursor 的公告同日晚些时候更新了受影响版本号。

载荷的设计值得逐层看。被改的是扩展包里的 `extension.js`：一段立即执行函数被拼在压缩后的正常 bundle 前面，Node 加载这个文件时就会跑，**不需要用户点任何东西**，也不用等扩展的 activate 回调。它接着做四件事：把一把攻击者控制的 Ed25519 公钥（注释 `svc-telemetry`）追加进 `~/.ssh/authorized_keys` 并设好权限；尝试打开本机 SSH 服务（macOS 用 `systemsetup`、Windows 装 OpenSSH Server）；用包里另一把私钥向攻击者服务器建反向隧道（`-R *:0:localhost:22`，让远端可以回连本机 22 端口），并放进 60 秒重试的游离循环；最后装持久化（macOS 伪装成 `com.apple.sysmond` 的 LaunchAgent、Windows 计划任务 `SysMon` 加启动目录兜底、Linux 的 `@reboot` cron），再把主机名、用户名、工作目录、Git 邮箱、公网 IP 和「环境变量名里匹配 KEY/TOKEN/SECRET/PASS/AWS/GCP 的那些」打包回传。注意最后一项只回传变量**名**，不回传值——这是侦察，用来挑重点机器，不是直接偷密钥。

两个实现 bug 把影响压小了，但不该当成防线。macOS 上它先用 `systemsetup -getremotelogin` 查 SSH 是否开着，这条命令普通用户跑会打印「需要管理员权限」并以状态 0 退出，脚本的正则只认 `Off`，于是判定「已经开着」，跳过了开启步骤——在本来没开 SSH 的机器上，隧道能出去但回连会撞上关闭的 22 端口。Windows 那条路径把 PowerShell 命令塞进了一个硬编码 `/bin/sh` 的辅助函数。Phorion 的说法是：SSH 服务和入站登录在多数机器上会失败，但公钥、持久化与回传是实打实落地的。**卸载扩展不能清除后门**——持久化脚本是独立落盘的，这是所有处置脚本都要单独清理的原因。

真正值得理解的是这层信任关系的位置。扩展在 IDE 的进程里、以登录用户的权限运行，一旦模块被加载就同时拥有本地文件、源码和开发者工具；因此市场不是「下载站」，而是**供应链的一环**。这次的处置也说明了同一件事：Cursor 下架该版本、把整个市场临时关停、审计确认没有其他扩展被动过、轮换密钥、重建市场，并配合托管商把攻击服务器下线。至于恶意版本是**怎么**被放进市场的——发布者凭据被盗、上传通道被绕，还是签名校验缺失——Cursor 的公告没有说，Phorion 的分析也只覆盖载荷本身。这个缺口决定了所有「IDE 市场 + 扩展」形态的 agent 分发能信到什么程度。

边界：目前只有两家一手材料（市场方公告、独立分析公司的报告），没有 Anthropic 侧的公开说明，也没有第三方统计的实际感染数；HN 上关于受影响范围的说法一度混乱（先被写成 VS Code 官方市场，后更正为 Cursor 市场），Open VSX 是否同样被投毒在讨论里没有定论。这些都不改变载荷行为本身的记录。

### 2. Prospero：把「永不等待」和「进程同生共死」写进第一原则的 harness

Chris Wellons（w64devkit 的作者，博客 nullprogram）10-31 发布了自己的编码 harness **Prospero**：C++ 写成、界面用 Dear ImGui；社区版在 GitHub 免费发布、但没有内置的无头引擎，专业版付费、内置全部引擎。他的出发点很直白——「编码 harness 本质上是 curl 加 popen()，不该占几个 GB 内存」；他批评的是多数 harness 建在 Web 技术栈上，因此常驻内存偏大。这一点在主流产品上确实常见：Claude Code 跑在 Bun 上（打包成字节码的 JS），Gemini CLI、Qwen Code、Kimi Code 是 Node／TypeScript，Cursor 这类 IDE 是 Electron（VS Code 分支）；但并非全部——Codex 是 Rust，Charm 的 Crush 是 Go，Aider 是 Python。「几个 GB」他没有给测量，属作者主张。

真正有信息量的是几条设计原则，它们正好对着现有 harness 最常见的失效方式：

- **永不无限等待**。每个操作都有截止时间；如果你不在场批准某个权限请求，agent 会因为超时拿到拒绝，然后自己想办法绕开。唯一的例外是 Plan 模式（它在等人看计划）。为此所有网络请求带超时，agent 信箱有上界，看门狗防止空等；需要你注意时会弹系统通知。
- **超时不是失败，而是转成后台任务**。命令行超时后变成异步后台命令，agent 可以带超时地继续等，被定期唤醒决定是否继续。作者认为这一步本身就把「agent 卡在一次构建上」解决掉了。
- **进程树同生共死**。命令被停下时，它启动的整棵进程树一起停——这在他眼里是另一类常见事故的根因：agent 并行起了两个构建，超时只杀掉构建系统的一部分，两个构建继续互相踩，机器被拖垮。
- **被动渲染**。没有活干时不重绘、不占 GPU；agent 等构建时界面就是静的。
- **harness 可以整体搬走**。引擎能作为无头实例部署到别的机器（SSH 或 WSL），界面留在本地；配置是 INI，可 include 本地文件或 URL（URL include 被限制，禁止任何可能进入 shell 命令的项）。

其余是常见能力的补齐：子代理与子代理工作树、MCP、网页搜索、会话分叉、技能（它自带一份关于自己的技能，能读文档、改自己的配置并重载）、Windows 上可在会话中途换 shell。它也明确说了权限系统的边界：**权限拦不住恶意 agent**，agent 在运行程序，最终能碰到 harness 能碰到的一切；要真正隔离得把 harness 本身关进容器或另一台机器。

值得理解的地方在于它把「harness 的默认行为」当成一等设计对象：主流 harness 的默认是「一直等、等你批准、等你回来」，Prospero 的默认是「到点就动、没人就放弃、进程不散」。这两种默认直接决定无人值守时能不能跑。判断边界也要说清：资源占用「低两个数量级」是作者自述、没有第三方测量；单人项目、社区版与企业版分层、桌面控制等能力都没有独立复现；这篇的价值在设计取舍的论证，不在性能数字。

## 其他值得关注

### 3. Claude Code 2.1.316：子代理的推理档位可以单独设默认

新增 `CLAUDE_CODE_SUBAGENT_EFFORT`：当没有别的地方指定时，子代理用这个档位跑，而不是继承主会话的档位。同一版还给 Claude apps gateway 加了 `managed.policy_mode: layered`——所有匹配某位开发者的策略都生效，逐条覆盖在下一条之上，而不是只取第一条。前者把「子代理该花多少推理」从隐式继承变成一个可设的默认值；后者改的是策略合并语义，对多策略并存的组织有实际影响。其余条目是权限与兼容性修补。

### 4. Kimi Code 2.4.1：单次文件读取上限从 50 万字符砍到 10 万

agent 单次读文件现在最多返回 10 万字符或约 2.5 万 token（先到者为准），此前上限是 50 万字符；要放宽得在 `config.toml` 的 `[read]` 里显式设 `max_chars`。同一版还缩短了内置工具与子代理的提示词、以及重复出现的 goal 与 plan 模式提醒。把「一次读取能灌进多少上下文」压掉四分之三，属于直接用默认值约束上下文膨胀；发行说明没有给依据，也没说对大文件任务的影响。

## 值得继续追问

- 条目 1：恶意版本是**怎么**进市场的——发布者凭据、上传通道还是签名校验？这个环节没查清之前，「从市场装扩展」和「从官方市场装扩展」的信任差别只能靠平台方自述。
- 条目 1：扩展市场普遍有 12 小时的自动更新延迟，这次它是否起了缓冲作用、又有多少人是手动更新的，两家公告都没给数据；这决定「延迟更新」能不能当作时间窗防线。
- 条目 2：把所有「需要人批准」的操作做成超时即拒绝，会不会把危险但必要的操作变成静默跳过？作者的设计里没有人不在场时的升级路径，这是它和「人工审批 + 分类模型初判」路线的主要分歧。
