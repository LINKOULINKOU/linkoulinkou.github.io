这一窗口的新内容不多，值得展开的只有一件：Y Combinator 与 Olam Labs 把成队的编码 agent 放进 Minecraft 和 Mindustry，同一套游戏 API、同样的沙箱，只换模型与 harness，看多代理系统会长出什么——三组里设置写得最清楚的一组以 6–1 结束，而比胜负更有信息量的是通信方式、记忆写法与领导层怎么被脚手架塑造。另外两条是边界放在哪的决定：Claude Code 给「工作目录外的写入」加了一个不受权限模式影响的开关，GitHub 给 agent 插件定了「企业 > 仓库 > 个人」的优先级链。

## 本期值得了解

### 1. YC 把编码 harness 放进游戏赛场：通信、记忆和领导层都随脚手架变形

Y Combinator 与 Olam Labs 合作跑了三组多代理实验，并开源了场地与运行框架。要让 agent 长期在线地玩，现成的 harness 不够用，他们自己写了一个：agent 在游戏里要观察世界、推理、记事、动手、发消息、写并执行脚本，因此每个 agent 拿到的是一个独立 Linux 沙箱，加上一套通用的编码 harness 和游戏的 API（工具以命令行形式暴露），可以自由写脚本、记笔记；Minecraft 那个 harness 的核心循环跑在 Pi 上，工具走 Mineflayer。Mindustry 那组把设置写得最清楚：**不做 harness 级定制、不做专门的记忆工程**，压缩交给 harness 自带的原生压缩——这一点是整组实验可比较的前提。

三组实验的规模与结果：Minecraft 生存服里 50 个 GPT-6.1 Sol agent 跑 3 小时，同一目标「建一个繁荣的文明」，共享沙箱、可私信、有一份 agent 名册；Bed Wars 打了九局 45 分钟、10 个 Opus 5.5 对 10 个 Sol，指令只有「赢」，GPT 以 6–3 拿下；Mindustry（造工厂 + 塔防的实时对抗）七局、约九个半小时，Sol 跑在 Codex 里、Opus 5.5 跑在 Claude Code 里，两边 API 完全相同、没有任何额外提示，GPT 一方 6–1 获胜，其中一局打了 4 小时 16 分。

比比分更值得看的是四种「脚手架痕迹」：

- **谁排在名册第一个，谁就成了领袖**。两组实验里几乎所有人都去私信名册上的第一个 agent，那个人随即变成事实上的指挥——Ada 在 Minecraft 局里成了领袖，开始审批请求、把殖民地计划写进共享目录；Bed Wars 里红蓝双方各重复了一次。领导层一旦形成就很少更换，Claude 一方连输多局也没换过层级，GPT 一方只在接近输掉时才出现自发的接管。
- **记忆写成文件 vs 记忆当广播**。Claude 玩家把教训写进各自的本机 `memory.md`（例如「别在边缘追人」「别爬上高处拆方块」），下一局照样犯同类错误；GPT 玩家的记忆文件基本是空的，靠私信把警告广播给队友。作者没有给出量化，但配了存档原文可核。
- **故障诊断的传播决定成败**。一次工具 bug 让「破坏方块」失败：GPT 一方有人手动装备镐子试通后，把绕法在频道里讲清楚；Claude 一方有玩家在自己的推理里得出「破坏功能坏了，买剪刀也没用」，于是继续守家——同一条坏消息，一方变成了共享知识，一方变成了个人结论。
- **卡住时去读源码**。Mindustry 对局进入僵局时，GPT 玩家会去网上抓 Mindustry 的开源实现，读单位与机制再写脚本找弱点（沙箱允许联网，没人指示他们这么做）；Claude 一方从未去查游戏代码。通信风格也随之分化：GPT 的消息量是对方的 5–30 倍，并且越打越压缩成不带空格的短代号；Claude 一方发展出「提案 + 回复 +1」的表决式流程。

为什么值得理解：这是一次少见地把「模型 + harness」当成一个整体来对打的实验，两边拿到的是同一个环境的同一套接口，而观察对象是**协作结构本身**——消息频率、语言压缩、记忆载体、领导层来源。名册顺序决定领袖这种小事尤其说明问题：多代理系统里最先被写入结构的那个位置，会自己长成权力中心，而这与模型能力无关，是脚手架的形状。数据与过程也留了痕：对局回放、agent 的命令日志、私有推理片段、记忆文件原文和沙箱存档都放在页面上，可以逐条回看。

边界也要摆清楚。Bed Wars 只有 9 局、Mindustry 只有 7 局，Civ50 只跑了一次 3 小时，胜负差两三局就可能翻过来；模型与 harness 是绑在一起换的（Sol+Codex 对 Opus 5.5+Claude Code），因此无法把差异归给模型或脚手架中的任何一方。游戏奖励的是特定行为（激进、勤发消息、抢中心资源），不能直接推成真实工程任务的协作能力。分析是组织者对自己数据的解读，虽然原始记录可查，但没有第三方复现。

## 其他值得关注

### 2. Claude Code 2.1.314：工作目录外的写入做成模式之上的开关，压缩挪到空闲时

两处都是把决定挪到别处。第一，新增设置项 `permissions.blockWritesOutsideWorkingDirectories`：一旦打开，写入、编辑与 Notebook 编辑在所有权限模式下都拒绝工作目录之外的路径——也就是说这条边界不再能被「允许全部」覆盖，而是提到模式之上。它是可选设置，不是默认值。第二，VS Code 与桌面端 Code 页加了空闲压缩：超过 20 万 token 的会话放着不用时会被摘要，下一次发消息时若提示词缓存已过期，就直接用这份摘要——把压缩从「上下文快满时」挪到「用户不在时」，代价是摘要用的是哪一版上下文、缓存过期怎么判定，都没有公开说明。

### 3. GitHub 给 agent 插件定优先级链：企业 > 仓库 > 个人

仓库维护者可以指定一个插件市场与一批默认插件，贡献者不用每开一个项目就重配；企业管理员可以要求、屏蔽插件，或只允许来自批准市场的安装。被标为「必需」的插件会自动安装并启用，用户不能关闭；托管设置的优先级高于仓库默认与个人选择。值得看的是它把扩展面当成包管理来治理：谁定义默认、谁能否决、谁能强制，三级各有明确归属——这正是各家 harness 里「技能、插件、MCP 服务器由谁装上」问题的一份产品答案。

## 值得继续追问

- 条目 1：名册顺序决定领袖，如果换成真实委派系统（子代理列表、任务队列的派发顺序），会不会同样把第一个被列出的 agent 变成瓶颈？这可以用很小的对照实验验证，但目前没有数据。
- 条目 1：把教训写进本机记忆文件与靠私信广播，哪个在长任务里更有效？这里的证据只有定性观察和几份 memory.md 原文，缺「同一策略、只换记忆载体」的对照。
- 条目 2：空闲压缩把触发条件挂在缓存是否过期上，意味着同一段历史可能在不同时刻被压成不同摘要；这会不会让「同一会话的两次请求」看到不一致的上下文，发行说明没有交代。
