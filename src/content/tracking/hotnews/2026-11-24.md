这一期的主线是「把验证插进流程」：Claude Ship 让 agent 自己评审、修 PR，并按团队写的策略决定哪些能自己批；Hugging Face 的指南用 Terminal-Bench 与 SWE-bench Verified 的返工数据说明基准本身也在出错；Greptile 实测七代模型后得出「怎么看屏幕取决于模型」。模型侧则是 GLM-5.4 用循环层把 750B 撑到 2T–3T 的水平。

## 本期值得了解

### 1. GLM-5.4：28 层跑两遍，750B 达到 2T–3T 水平

Z.ai 11-23 的博客给出架构细节：GLM-5.4 是它第一个基于 Loop Transformer 的旗舰——把 GLM-5 基座的 28 层权重共享地跑两轮，隐藏状态在两轮之间被细化，等于在不加参数的前提下把网络做深。为了在 750B 规模上控制部署成本，做了三处改动：门控渐进更新（直接覆盖隐藏状态会让激活范数在多轮间爆炸，下游层收到超出预期的分布）、混合 KV 缓存（全局共享加独立滑动窗口，多跑一轮只多一份滑动窗口缓存，1M 上下文下成本增幅可控）、稀疏注意力索引复用（第二轮直接复用第一轮索引器产出的索引，零额外开销，实测与每轮重算几乎一致）。在 30B 同架构模型上的等参数对照里，只多约 10% 训练算力，循环版就明确更好，且推理链越长收益越大、思考花的 token 更少；推理速度 200 tok/s，对比 70–80 tok/s。官方也承认它有「马拉松式思考」的毛病，会把循环拖得过长。API 与开放权重都标注为「即将推出」，目前只能经 Coding Plan、ZCode 与 Z.ai Chat 使用。

来源：[Toward Generalized Coding with Our First Loop Transformer](https://z.ai/blog/glm-5.4)｜Z.ai｜2026-11-23；[HN 讨论](https://news.ycombinator.com/item?id=50605103)（1,069 分）

### 2. Claude Ship：agent 评审、修 PR，再按策略自己批

Anthropic 11-23 开测 Claude Ship，由三块组成：已在正式可用的 Code Review（多视角审、对抗式复核发现、分级 Quick/Standard/Deep）、beta 的 PR Steward（专治 CI 失败、合并冲突与评审意见，但被设计成**不得批准或合并**，每次 push 后留言说明改了什么、怎么撤回，开发者可 `@claude stop` 让它停手）、以及 beta 的 Claude Approvals（读仓库里的策略文件，像更聪明的 CODEOWNERS：例行改动可以自己批，特定情形要求人工签核，可用自然语言分类器作为判据）。团队可先用 observe-only 模式跑一段时间，再接分支保护强制要求它批准。开发者侧入口是 Claude Code 的 `/ship`。官方数据：Claude Code 团队 6 到 9 月合并 PR 数翻倍以上、回滚比例下降四成以上。

来源：[Introducing Claude Ship](https://claude.com/resources/articles/introducing-claude-ship)｜Anthropic｜2026-11-23；[HN 讨论](https://news.ycombinator.com/item?id=50618513)（27 分）

### 3. 基准自己在出错：89 个任务返工 28 个，SWE-bench Verified 六成有问题

Hugging Face 11-23 的指南把评测分成三代：问答（MMLU、GPQA）比对答案、agentic（SWE-bench、WebArena）比对 agent 在环境里改了什么、团队/蜂群比对一组 agent 共同产出什么，每代都多一层会改变分数的软件。文中给了几组具体返工：Terminal-Bench 2.1 在用户报告后修了 89 个任务里的 28 个，其中一个任务提示写 PostgreSQL、测试却期望 Spark SQL；CritPt 不公开参考解，物理学家只能自己先解题，在审的 56 道里发现 21 道有错；OpenAI 对 SWE-bench Verified 的审计在 138 道题里发现 59.4% 有实质问题；2026 年 7 月 OpenAI 估计 SWE-bench Pro 约三成任务有问题并撤回推荐。作者引用的一项综述称，任务设置或奖励设计的缺陷可让测得分数相对偏移最多 100%。他们也给了自己的翻车例子：一个只核对缺陷比例的捷径能通过全部八道题，最后靠「拿一个已知不完整的解去攻击评分器」才抓出来。

来源：[How to build and maintain an agentic evaluation](https://huggingface.co/blog/agentic-evals)｜Hugging Face（Avijit Ghosh、Ben Burtenshaw、Irene Solaiman）｜2026-11-23

### 4. agent 该怎么「看」屏幕：取决于模型，不取决于流派

Greptile 11-19 用同一批 172 个 OSWorld 任务测了七代模型在三种观察方式下的表现（纯截图、截图加无障碍树按坐标点、加树按元素 ID 点）。结论分两段：对三个最强模型，加不加树、按不按 ID 都没有差别；四个较弱模型则靠树与 ID 点击提升了 9 到 37 分，其中三个分数翻倍以上。原因是老的「坐标点击」要把像素位置写成文本，差几个像素就点错，而窗口尺寸一变坐标就变；树给出的是可命名的元素。但树自己有盲区：Figma 的画布、Doom 这类游戏完全没有树，文字溢出输入框这类 bug 只在画面上可见。所以他们的 TREX 最终同时用两者：能用 ID 就用 ID，画布与游戏退回坐标，并且每出一个新模型就重跑这套实验。

来源：[How should an LLM see a computer?](https://www.greptile.com/blog/trex-computer-use)｜Greptile｜2026-11-19

### 5. Shirudo：不打补丁也能先挡住漏洞

OpenAI 与 Cisco 11-23 开源 Shirudo（日语「盾」）：一个跑在 Linux 上的 eBPF 运行时，让运维在不重启、不等补丁的情况下，先临时拦住触发漏洞的那一个操作，同时放行合法请求。官方给的验证是：一套由 Codex 生成的 shield 在一次受控测试里挡住了针对运行中 Elasticsearch 的 Java4Shell 攻击尝试，且无需重启。它解决的问题很具体——打补丁要几天到几周，而漏洞利用与正常请求可能走同一个系统调用，整段封掉会把服务打死。

来源：[OpenAI and Cisco introduce Shirudo](https://openai.com/index/introducing-shirudo)｜OpenAI｜2026-11-23
