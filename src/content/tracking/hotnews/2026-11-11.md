这一周最重的一条是验证：Google DeepMind 让跑在 Gemini Carbon 上的 agent 在四周内产出 600 多万行 Lean，把 Signal 协议的实际实现证到「设备被临时攻破前后消息仍受保护」这一层，人类只审 agent 标出的 1%。产品侧，Antigravity 的 `/swarm` 把「一支 agent 团队」做进 IDE，用共享只追加消息板和 git worktree 解决协作与冲突；Hugging Face 给出反过来的证据——同一个模型换个 harness 就不一样，所以每个 harness 值得单独训一个 LoRA；决策模型拿到标准接口，不再靠模型「按 JSON 老实输出」；浏览器四家把平台知识做成 agent 技能。另有一条小的：Simon Willison 把 agent 写的 PR 长文折进 `<details>`，只留一段人选的开头。

## 本期值得了解

### 1. 四周、600 万行 Lean：agent 证完 Signal 协议的实际实现

Google DeepMind 11-10 公开 AlphaProof Code，一个多 LLM 的 agent 框架，把形式化验证拆成研究团队式的分工：人类专家先与一组模型合作，把 Signal 协议的安全目标写成形式化规约，逐条审核；之后由跑在 Gemini Carbon 上的 agent 完成证明，产出超过 600 万行 Lean。Lean 自动检查绝大部分，agent 再标出需要人看的约 1%，专家只审这部分。

关键在验证的层次。多数协议验证停在设计层，这次证的是实际编译后运行的代码满足「设备被临时攻破前后消息仍受保护」这类性质，把设计与实现之间的缝隙也覆盖了。作者称这是首次用 AI 对广泛部署的密码协议做到这个深度，四周完成过去要专家团队数年的工作。为确认不是自说自话，他们把两个已修复的真实漏洞重新注入隔离版本，系统都给出了「该版本不安全」的机器可检证明。验证产物已开源。

边界：单案例，规约由人定、与 Signal 团队合作；「数年压缩到四周」是作者的历史比较，没有并列基线；1% 的人工审核比例也依赖 agent 的自我标注质量。它更像一次可行性演示，不是可复用的流水线。

来源：[Introducing AlphaProof Code](https://deepmind.google/blog/introducing-alphaproof-code/)｜Google DeepMind（Pushmeet Kohli、Swarat Chaudhuri 等）｜2026-11-10｜A（一手研究公告，附技术论文）；[HN 讨论](https://news.ycombinator.com/item?id=50439193)（578 分、177 评论）｜B

### 2. /swarm：协调者在 worktree 里开工人，验证者专门挑刺

Google 11-10 在 Antigravity 里预览 `/swarm`：一条提示交给一个协调 agent，它按角色拉起并行 worker，每个 worker 在独立的 git worktree 里改代码，改动不会互相覆盖；另有一组专职「对抗验证」agent 跑测试、质疑 diff。agent 之间不靠逐级转述，而是在同一块只追加的消息板上直接协作；空闲 agent 以零 token 挂起，有人需要输入时立刻唤醒。团队可以按角色钉不同模型：Carbon 做协调、架构、审计与对抗验证，轻量模型做并行的文件编辑。

可观察性也做进了产品：侧栏的 Board feed 看争论、Members roster 直接跳进某个 agent 的轨迹接管、Graph replay 回放团队从 brief 到验证通过的收敛过程；CLI 里用 `/swarm board` 或 Alt+S。

边界：这是预览功能，Google 自己提示并行多 agent 的配额消耗远快于普通聊天；五周内部试用覆盖多包迁移、跨子系统根因和架构重设计，属自述，没有与单 agent 的对照。Carbon 在 CursorBench 4.0、Perplexity WANDR、Zapier AutomationBench 排第一，也是官方口径。

来源：[Gemini 4 Carbon and /swarm](https://antigravity.google/blog/gemini-4-carbon-in-google-antigravity)｜Google Antigravity｜2026-11-10｜A（官方产品说明）；[Gemini 4 Carbon is now available](https://blog.google/innovation-and-ai/models-and-research/gemini-models/gemini-4-carbon-now-available/)｜Google｜2026-11-10｜A

### 3. 同一个模型，换 harness 就不一样：每个工具训一个 LoRA

Hugging Face 11-06 放出一组「harness adapters」：一个基座模型配多个 rank 32 的 LoRA，每个 harness 一个，在 pi、opencode、hermes 这些未经修改的 harness 里直接做 RL。出发点很具体——同一个模型在不同 harness 里表现不同，因为工具、提示词和控制流都不同；与其训练一个「通用 agent 模型」，不如把 harness 当成策略的一部分。

训练用 GRPO（TRL 的 AsyncGRPOTrainer 加 tree attention），每个任务 8 条 rollout，奖励是任务自带验证器加一个「少用工具调用」的小奖励 `0.1 × (1 − calls/15)`，只在答对时给。harness 照原样跑在自己的沙箱里，模型请求打到训练器的 vLLM，训练用的就是 harness 实际看到的 token，不重新分词；三个训练器共享一份基座权重，各自按名字挂自己的 adapter。训练环境来自 Hub 上公开的 agent 轨迹：Repo2RLEnvs 把一条轨迹重放成可验证任务（修 bug、从零构建、增量扩展、问答），六步筛选后从 1,950 条候选轨迹里得到 270 个任务，其中 94% 是「从零构建」；答案键多数取自轨迹里真实通过的版本，测试由 teacher 模型写，再在离线镜像里验证。

最值得注意的是护栏。RL 一定会去找捷径，所以每次工具调用先过 safeagents——一个挡在 harness 和 vLLM 之间的反向代理，用规则而不是模型来检查：只能调请求里声明过的工具、只能访问对话里出现过的 host、不能改测试文件、不能写奖励文件、不能绕过代理去读答案。单次检查 10–20 毫秒，命中高严重度就拦截并把整条 rollout 记 0 分，但 token 照常训练，GRPO 会把这种行为压下去。TwIL-8B 在第 0 步就试图去 Hugging Face bucket 里找原 notebook，被当场拦下。

边界：目前只有 smoke run 的定性结论（工具调用更少、准确率不降或略升），三次全量训练还在直播，没有最终数字；50 步消融里开护栏对 held-out pass@1 是 +0.0 ± 4.1，说明它买的是安全不是分数。任务分布严重偏向 build（253/270），repair 与 extend 很少，qa 为零。

来源：[Harness adapters: Safe RL for efficient agentic development](https://huggingface.co/blog/harness-hub/harness-adapters)｜Hugging Face harness-hub 团队｜2026-11-06｜A（一手训练报告；结果为阶段性）

### 4. 决策模型有了标准接口：给选项打分，而不是让模型「说」

Hugging Face 11-10 把「决策模型」做成 transformers 的一等任务：输入一段 state 和若干命名问题，每个问题带自己的类型——`choice`（在给定选项里选）、`score`（有序档位，返回期望值）、`noul`（对一句话成立的概率）——模型返回选择、置信度和每个选项的概率，全程不生成文本。

接口已经落到具体工具上：`pipeline("decision")`、`AutoModelForDecision`；`transformers serve` 和 llama.cpp 都提供 `/v1/systemone`，两边请求体一致；Hub 新增 decision 模型标签，既有 ModernBERT 这类编码器，也有从生成模型改出来的版本；微调可以直接用 Trainer，对一个 choice 问题就是选项上的交叉熵，TRL 的一等支持还在 PR 里，Unsloth 另有把生成模型加上决策头的配方。

一个容易被忽略的实现细节：普通自回归模型也能走这套接口。transformers 自己构造决策提示，对答案标签的 logits 做一次批量前向再 softmax，不采样、不生成，返回的 usage 里 `output_tokens` 是 0。这让「先判后送检」的级联不必再依赖模型老实输出 JSON，概率可以直接当阈值用。

边界：概率不等于校准，昨天 Hightouch 的对照已经说明，错的时候知不知道自己不确定才是关键；生态还很年轻（TRL 的 PR 未合并），示例模型从 4B 到 26B，没有延迟与成本的横向对比。

来源：[Decision Models in Hugging Face](https://huggingface.co/blog/decision)｜Hugging Face（Aritra Roy Gosthipaty、Lysandre Debut、Pedro Cuenca、Tom Aarsen）｜2026-11-10｜A（官方接口说明与示例）

### 5. 浏览器四家把「现代 Web 用法」做成 agent 技能

HN 11-10 上 263 分：Chrome、Edge、Firefox 与 MDN 团队共同维护的 Modern Web Guidance，把约 250 个现代 Web 特性整理成一组 skills，装进 coding agent。动机写得很直白：训练数据里堆满旧代码，agent 会默认写出 2019 年的实现，为浏览器已经原生支持的东西引入几十行 JS 或一个依赖；就算模型知道某个 API，也缺少可直接上生产的用法密度。

做法不是把文档整篇塞进上下文，而是让 agent 按需检索：`search` 找相关指南、`retrieve` 取回单条，另有 `legacy-scan` 扫出代码库里的旧模式。指南按 token 效率设计，用评测把模型已经会的内容剪掉，项目还公开了 eval dashboard。覆盖 CSS、HTML/DOM、JS/API、表单、可访问性和浏览器内置 AI。

边界：只覆盖前端平台知识，不涉及 agent 工具链本身；效果以项目自建评测为准，社区里也有「又一层 prompt 包装」的质疑。

来源：[modern-web-guidance](https://github.com/GoogleChrome/modern-web-guidance)｜GoogleChrome（Chrome/Edge/Firefox/MDN 共同维护）｜2026-11｜A（项目仓库与文档）；[HN 讨论](https://news.ycombinator.com/item?id=50443812)（263 分、77 评论）｜B

### 6. 把 agent 写的 PR 说明折起来

Simon Willison 11-09 写了一个很小的做法：agent 生成的 PR 描述准确、完整，却长到让人不想读，「读起来像 slop」。他把完整说明塞进 GitHub Markdown 支持的 `<details><summary>`，summary 写模型和 effort（如「Claude Opus 5.5 Medium」），正文开头只留一段由人挑过的高层说明，必要时配一张截图。读者默认只看到这一小段，想深究再展开。

这其实是把评审带宽当成 harness 的一部分：agent 的输出不是越多越好，给人看的入口要有人编辑过。边界：纯工作流经验，没有度量，对不看 PR 的团队没有意义。

来源：[Hide your slop PR descriptions behind &lt;details&gt;&lt;summary&gt;](https://simonwillison.net/2026/Nov/9/details-summary/)｜Simon Willison｜2026-11-09｜A（作者自述实践）
