本期三条主要材料都在处理同一个问题：agent 从一次性演示变成持续运行时，成本、能力和运行状态怎样被维持和验证。OpenAI 把提示词缓存的最短寿命做成 12 小时选项，但写入价提高到 2.5 倍；SlopCodeBench 把编码任务拆成逐步追加需求的检查点，前沿模型的严格通过率只有 12–16%；一位基础设施工程师则记录了监控场景的 harness 取舍：让 agent 写监控计划，交给确定性 runner 执行，比纯 agent 循环更省 token、信号更干净。最后是 Qwen Code 预览版和发行线简讯。

## 本期值得了解

### 1. OpenAI 12 小时提示词缓存：写入 2.5 倍，换跨小时的稳定前缀

提示词缓存（prompt caching，复用已处理过的输入前缀）对 GPT-5.6 及之后的模型默认按 30 分钟的最短寿命计费。OpenAI 10-20 在开发者账号宣布，Responses API 里可以选 12 小时的最短寿命，也可以在同一请求里混用 30 分钟和 12 小时：共享的指令、工具定义和参考资料放前面走 12 小时，会话中新追加的内容走 30 分钟。官方文档把两档写入价写得很清楚：30 分钟按未缓存输入价的 1.25 倍计，12 小时按 2.5 倍计；之后的缓存读取两档同价，都是 0.1 倍（GPT-6.1 Sol 是 0.05 倍）。这里的 12 小时是“最短寿命”，不是删除期限；缓存仍可能保留更久，也不改变数据保留政策。

这条改动真正影响的是成本结构，而不是“缓存更久就一定更便宜”。按文档倍率做一个粗略估算：一个 10 万 token 的稳定前缀，10 次请求，如果都在 30 分钟内完成，30 分钟档是 1.25 + 9×0.1 = 2.15 倍未缓存输入价，12 小时档是 2.5 + 9×0.1 = 3.4 倍，反而更贵；如果 10 次请求分散在一整天、间隔超过 30 分钟且缓存已经过期，30 分钟档每次都要重写，合计约 12.5 倍，12 小时档在缓存不被驱逐的前提下仍是 3.4 倍，这时才划算。

所以它适合的是“跨小时复用同一段稳定前缀”的长期代理：例如每天多次启动、共享同一套系统指令和工具定义的任务；不适合高频循环里的每一步。文档还给了一个容易忽略的限制：12 小时档只在 Responses API 提供，且只对 GPT-5.6 及之后的模型生效；缓存条目存在单台机器上，请求要被路由到持有该条目的机器才能命中，12 小时只是计费寿命，不保证每次都能复用。

### 2. SlopCodeBench 10/2026：严格通过率 12–16%，提高推理档位不是可靠的提分手段

SlopCodeBench 是一个把编码任务分阶段给出的基准：代理先写出一版程序，随后收到新需求，必须在不破坏旧行为的前提下改现有代码；后面的检查点同时测新功能和回归。它和一次性跑完的基准不同，考的是“需求变化后还能不能守住已经测过的行为”。这次更新覆盖 36 个问题、每个设置 196 个检查点，作者把“严格通过”定义为所有测试类别（包括回归）都通过；“核心通过”只要求核心类别通过，允许之前的检查点仍然失败。

结果不乐观：10 个完整设置的严格通过数是 24–32/196，严格通过率 12.24–16.33%；核心通过率 65.82–73.98%。两条线的差距说明，模型通常能把主要功能做对，但在需求追加后保住全部已测行为很难。更严格地看最终代码：每个设置只有 0–3 个问题的最后一个检查点严格通过，最终失败测试用例在 1,435–2,831 之间。Astra XHigh 的严格通过数最高（32/196），Opus 5.5 Medium 的核心通过数最高（145/196），但严格只有 28/196。

作者还比较了同一模型的 Medium 与 XHigh 档：Opus 5.5 从 28 降到 25，成本约 4.22 倍；GPT-6 SOL 从 30 降到 26，成本约 2.11 倍；只有 Astra 从 29 升到 32，成本约 2.91 倍。单次运行不能证明“更高推理档位有害”，但至少在这组运行里，它没有稳定换来更多严格通过，成本却明显上升。文章标题里的“xhigh considered harmful”是作者自己的概括，不是受控实验结论。

边界也要说清：这是基准维护者自己的十月更新，每个设置只跑一次，成本是按运行记录估算的，不是独立复现；严格通过率低不等于模型在真实项目里同样差，检查点的权重和测试设计都会影响结果。它值得看的地方是评测设计——“逐步追加需求 + 回归检查”把“能写”与“能改”分开了，这正是编码 agent 长期运行时的核心难点。这条是补收：10-15 发布，落在本轮窗口内，上一轮漏收。

### 3. Agentic Monitoring：持续监控不适合纯 agent 循环，先让 agent 写监控计划

Ben Congdon 的这篇记录从 Anthropic 的一个做法说起：让 Claude 盯着单个组件的健康状态，像“超级粉丝”一样反复看图表和日志。作者的判断是，这种持续监控不适合纯 agent 循环——每次都让模型自由地查日志、跑查询，token 贵、信号也容易噪声化。他试的原型把监控拆成两段：agent 先读服务代码，写出一份“监控计划”（要查哪些指标、日志、阈值和查询），再由一个确定性 runner 按计划执行；触发后再由另一个 agent 调查，必要时升级给人。

这样做的直接好处是，重复执行的部分不经过模型，token 消耗和结果波动都降下来；作者说，纯循环和“计划 + 确定性执行”相比，后者的信号更干净、token 少得多。他还给了一个成本量级：一个中等规模的科技公司，全部服务按这个方式监控大约每天 100 美元；在一个热路径库上，几轮调查发现了 50% 的堆节省和 30% 的延迟下降。前者是作者按模型价格做的估算，后者是他的单次观察，都没有独立复现。

这条的价值不在“又有一个自动运维代理产品”，而在 harness 的分工：模型负责提出监控什么、为什么；确定性系统负责按同一份计划反复执行；模型只在触发后做调查。作者也承认，真正的难点是噪声抑制、让模型写出好计划的提示词，以及一套足够大的标注评测集；这些都没有公开。HN 评论里有人进一步指出，真实规模下的日志和指标基数、跨服务关联才是硬问题，单靠把 agent 指向可观测性栈并不能解决。

边界：这是一位基础设施工程师的原型记录，不是对照实验；成本、节省比例和“信号更干净”都是作者自述；监控目前以只读为主，写入和自动修复需要额外的护栏。它值得继续追问的是：监控计划怎样表示、确定性 runner 如何做去噪和关联、以及这套东西在数千服务规模下是否仍然省 token。这条同样是补收：10-19 发布，上一轮观察时讨论度不足，本轮讨论已到 118 分/23 评论。

### 4. Qwen Code 0.25.4 预览：托管会话的隔离、恢复与预检

Qwen Code 在 10-20 晚间（UTC）连发 0.25.4-preview.0 与 preview.1，稳定版仍是 0.25.3。发行说明列出的改动集中在“托管运行”一侧：工作区隔离的会话预热、托管 harness（发行说明里称 Hosted Harness）处理私有文件轮次、把本地与 SSH 工作区文件引用接进来、给托管配置加只读的 `--check` 预检、把附件输入上限提高到 8 MiB，以及为会话状态的有界保留写文档。它们指向的是一套把会话、工作区、文件和预检分开管理的托管 agent 运行时，而不只是单个 CLI 功能。
