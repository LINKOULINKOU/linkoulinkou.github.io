这一期有两条把「代理的记忆」和「代理的双手」讲清楚的原始材料。Anthropic 第一次把 agent 记忆拆成抓取、离线整理、分层注入三段，并用 CL-Bench、宝可梦、35 万份内部文件三组评测说明每一段各自值多少；同周一份互操作提案指出，九种记忆格式彼此读不懂，缺的不是工具而是数据模型。另一条线是 OpenAI 把「找 Linux 内核提权漏洞」做成流水线：模型不是给提示，而是在真实内核上定位、验证、生成补丁，最后形成 948 个按根因归并的提权漏洞补丁并分批上报。此外，本周最大的一场技术争论围绕「模型能否直接读写权重」展开，原始宣称与逐条反驳都值得看；Claude Code 的两起权限与凭据事件也给出具体数字。

## 本期值得了解

### 1. Agent 记忆拆成三段：抓取、离线整理、分层注入

Anthropic 11 月 6 日的《The components of agent memory》先做了一个排除法：所谓 agent 记忆，是 Claude 从用户交互和任务经验中获得、跨会话保留、以可读上下文存下来的知识；**权重变化、单次会话里的 in-context learning、以及压缩摘要都不算**。这个定义把记忆从「模型能力」挪到了「harness 管理的持久状态」，也解释了为什么各家的实现看起来都像「往文件夹里写 Markdown」。

它把这条循环拆成三个动作。

**其一，在会话中抓取显著事件。** Claude 可以给会话记录里值得记住的事打标签，或直接写进 memory 目录的笔记。文章给了一个判断标准：记忆是一种预测——写下一条规则，就是预测未来的会话还会用到它，并且可以直接信任、不必复核。难点在于「当下怎么知道什么重要」，因为写下时还不知道后面会发生什么。

**其二，离线整理，也就是 dreaming。** 这里借用了 Letta 与 UC Berkeley 提出的 sleep-time compute：模型在两次交互之间的空闲时间回放自己的记录，重新组织上下文。Anthropic 用它做四件事——拿会话原文核对并修正错误笔记、建立新的记忆表示（wiki）、把重要条目提升到记忆层顶部、跨多个会话补齐遗漏。「dreaming」这个词并不新：GitHub Copilot 10 月底公开预览的后台记忆整理也叫 Dreaming（见 [2026-10-29-热点追踪](/tracking/2026-10-29)），说明后台改写记忆正在从各家自发做法变成通用构件。

**其三，分层注入。** harness 在每次会话开始时预加载顶层记忆。这一层必须小：注入的记忆占 token，一条错笔记会被带进之后每一次会话，而 Claude Code 的文档已经警告过「指令文件越长，遵循度越低」。所以 Claude Code 的 auto memory 只加载 `MEMORY.md` 的前 200 行或 25KB，把它当索引；其余内容留在下层，需要时再搜索或读取。

#### 评测里看到了什么

Anthropic 没有只讲设计，给了三组可核的评测与数字。

**学习回路（CL-Bench 1.0）。** 任务是查数据库回答一串问题，每题答完会被告知正确答案，模型可以写记忆帮助后续题目；每次新题都从全新会话开始，唯一延续的是持久化记忆目录。不同代模型的表现差别不在「有没有记忆」，而在**能不能闭环**：Sonnet 4.6 会提出「为什么答错」的猜想，但记忆目录只是一堆互不相连、从未验证的猜测；Opus 4.7 把笔记合并成一份参考文档，开始标注哪些事实已核、哪些未核；Sonnet 5 在评分器确认答案后逐条标记，答错时写更正；Opus 5 是第一个把回路闭上的——大多数条目同时包含一条规则、这条规则「怎么知道是真的」、先前问题的答案，以及一路踩过的陷阱警告。Opus 5.5 与 Sonnet 5.5 也能闭环，带记忆的得分与 Opus 5 相近（它们无记忆的基线略高）。

**记忆判断力（宝可梦红）。** 同一款游戏、同样给一个可读写的记忆文件夹，跑了约一万步后对比两代模型：Sonnet 3.7 认为一切都可能有用，写了 413 个记忆文件、225 个文件夹，每场战斗、每件道具、每个 NPC 都单独存档，拿到 1 枚徽章；Fable 5 只写了 9 个文件、2 个文件夹，加一个顶层 `global.md`，拿到 4 枚徽章。差别不在勤奋，而在**存什么**：金钱、当前位置这类每回合都能从屏幕上读到的状态，存下来就是冗余且会过期；策略、计划、验证过的规则只存在于模型想出来的地方，不写就会消失。Fable 5 的 `global.md` 当仪表盘（当前目标、打道馆的预案、使用记忆的规则），`locations/` 存路线，`gameplay/` 存机制策略——其中一条是连续七个精灵球没抓到鲤鱼王之后写下的：「连续 3 个以上球失败就改变节奏，在菜单步骤间插入额外的 wait」。

**记忆表示（wiki）与它的代价。** 在一家被收购公司的内部语料上（Stainless，约 35 万个文件、约 4.2 亿 token），25 个问题，让 Opus 5 分多个会话逐步建 wiki：从 2 个会话扩到 128 个，按评分标准得分从 13% 升到 48%。给 Claude 同时开搜索和 wiki 时，随着 wiki 变大，总分从 54% 升到 61%，而只用搜索是 53%；wiki 加搜索每题还省了约 2 万 token。法律文档那边（Harvey LAB 的并购材料）也能看到边界：24 个问题里超过一半要跨文档拼信息，用 wiki 时得 87%，只用搜索得 73%；但若某题的评分点大多能从单份文件里搜到，wiki 就没有明显收益。更极端的一次，wiki 长得比原始文档还大——文章自己引了博尔赫斯那张「和帝国一样大的地图」，说明这种表示会退化成「什么都没抽象」。

**怎么给指令也有反直觉的结果。** Anthropic 的结论是：告诉模型「记忆是用来做什么的」，但不要规定「怎么写」。他们逐条测过具体规则，其中「只记录失败」这一条让 Opus 5 和 Opus 4.7 都损失了大部分记忆带来的增益。对较弱模型则相反：Sonnet 4.6 常常根本不读记忆文件，也不去验证自己的猜想，提示它「回答前先读记忆、再明确检验猜想」几乎让分数翻倍；Sonnet 5 不用提示，十次里有九次会先读记忆。

#### 互操作的另一半：九种格式，四个问题

同周（11 月 7 日）LoreKit 的 Mads Thines 写了一篇立场相反、但正好补上另一半的文章：《Agent memory needs its OpenTelemetry moment》。他先让人数一数自己机器上的记忆格式：仓库里的 `AGENTS.md`/`CLAUDE.md`、Cursor 的 `.cursor/rules/*.mdc`、通过 Anthropic memory tool 写进 `/memories` 的文件、GitHub Copilot 存在服务端的仓库事实、某个 memory MCP server 的 JSONL 知识图——四五种形态，彼此读不懂。文章列了九类实现并逐项对比「记忆的单位、按什么寻址、怎么遗忘」，从指令文件、agent 管理的文件、托管仓库事实，到 Letta 的上下文块、Mem0 的抽取事实、LangGraph 的命名空间存储、MCP 参考记忆服务器的知识图、Graphiti/Zep 的时序图，最后是 LoreKit 自己的「带地址的记录」。

他主张类比 OpenTelemetry：2019 年之前可观测性也是各家一套采集器、一套格式，换厂商就得重新埋点；合并后大家只在四层上达成一致——数据模型、语义约定、传输协议、参考实现——然后把存储、查询、分析留作竞争。agent 记忆现在缺的正是底下这层共识。已有的提案大多只解决**导出**（MacPaw 的 Portable Memory `.mem` 包、2026 年 4 月的 Open Memory Protocol 草案、Cognee 的 COGX 导入格式），而编码工具还有第二个问题：**实时寻址**——当 CI 任务、编辑器里的 agent、评审 bot 同时在同一个仓库读写，它们怎么确认「说的是同一个地方」。

剥掉品牌，所有格式都在回答四个问题：一条记忆在哪儿为真、它的身份是什么（第二次写是更新还是重复）、内容是什么、什么时候失效。真正的分歧只有一个：**谁写**——指令文件是人写，memory tool、Letta、LoreKit 是模型写，Mem0、Graphiti 是服务从对话里抽取。规范不必替人选，但要把「谁写的」记下来，让读者知道该信几分。文章给了一个记录样例：frontmatter 里放 `spec`、`id`、`address`（层级 + 值，如 `repo` 加 `github.com/acme/checkout`）、`key`、`kind`、`written_by`、`content_type`、`lifecycle`、`attributes`，正文是 Markdown；落到规范上是三层——地址层级与属性命名空间的约定、经 MCP 暴露的 write/read/list/search/archive 契约、以及一致性测试（而不是参考实现）。存储、排序、embedding、界面都留在规范之外。

它自己也把最锋利的反对意见写了出来：MCP 标准化的是「调用」，不是「记录」；共享记忆本身就是提示注入通道（所以规范要记录作者、支持签名、让记录指向它依赖的代码）；以及 xkcd 927——再立一个标准并不能解决标准太多。作者的回答是 OpenTelemetry 的经验：共识来自既有项目合并，而不是再加一个。

**为什么值得一起读。** Anthropic 那篇回答「记忆由哪些部件组成、每个部件值多少」，LoreKit 这篇回答「这些部件写下来的东西为什么彼此不通」。两篇合起来，给 harness 作者一张比较清楚的分工图：会话内抓取要克制，离线整理要预算，注入层要小，表示层要有检索配合；再往上，才是跨工具共享的地址与生命周期。边界也要说明：Anthropic 的评测全部是自家模型、自家 harness 的内部结果，没有第三方复现，模型代号与具体版本对应关系未披露；LoreKit 作者在卖一款记忆工具，文章明确披露了这一点，提案也尚未被任何标准组织采纳。

### 2. 把「找内核漏洞」做成流水线：5,034 个目标，948 个补丁

OpenAI 11 月 4 日的《A thousand fewer paths to root》报告了十月中旬一次约十天的实验：在常见桌面 Linux 的内核上跑一条五段式流水线，最后形成 948 个按根因归并的补丁，并分批向内核维护者上报（已发出数百份）。数字链条要先说准：圈出 5,034 个审计目标（约 280 万行、约占内核 7%，只保留低权限用户可达的代码）；约 12 小时产出 2,308 条去重候选；在装了 KASAN 的隔离虚拟机里用约 30 小时复现 1,724 条（74.7%）；为其中 1,169 条写出可用的本地提权（LPE）利用，另有 291 个信息泄露 PoC；最后按根因与变体合并成 948 个补丁。**948 是「不同漏洞/补丁」数，不是 948 个 exploit**——原始利用是 1,169 个，中文转述里常见的「948 个提权利用」是错的口径。

五个阶段分别是：**Scout** 筛出普通用户能触达的内核代码；**Analyst** 扫出可疑点并去重；**动态验证** 在隔离虚拟机里复现，以「有可测量的内存破坏证据」为准；**ExploitDev** 为复现成功的漏洞写提权利用；最后**生成补丁并做变体分析**，把同一根因的多个利用合并。之后由 OpenAI 的安全研究员逐项复核根因、利用证据、补丁质量与定级，再通过 Patch the Planet 与内核社区分批上报。目标环境是与常见桌面发行版一致的 stock 安装，开了 SMEP/SMAP/KASLR/HARDENED_USERCOPY；发行版与内核版本没有披露。API 费用合计 1,213,430 美元，均摊每个 LPE 1,279 美元、每个成功利用 359 美元，其中利用开发阶段单项约 77.6 万美元；含人工分析的全流程约十天。

**为什么值得看。** 这是把「模型会写代码」推到「模型能独立跑完一轮漏洞研究」的样本：不是给一段代码让模型找 bug，而是让 agent 在真实内核上跑复现、写利用、改补丁，每一步都有可验证的信号。成本对比也具体：六月用 GPT-5.5 Cyber 是 24 个 LPE；七月用 GPT-5.6 Sol 是 166 个、51.4 万美元（约合每个 3,094 美元）；十月在新模型上超过五倍，而中间内核又硬化了三个月。文章还给了 kernelCTF 适配环境的一组数：112 小时、32,936 美元、21 个 LPE 加 25 个信息泄露。它由此给出的判断是：对资源充足的攻击者，未修补系统上的一个普通账号「在功能上等同于 root」；大型软件需要多轮扫描加修复才能「触底」，每换一代前沿模型都值得再扫一遍。

**真正的工程含量在 harness。** 报告里最有信息量的不是总数，而是几处失败与补丁：①闸门用「是否复现出内存破坏」这类可测量证据，而不是让模型自评；②早期一次实验里，200 个「拿到 root」的利用中有 20 个其实利用了另一个 0-day，不是被指派的那个 bug——此后加了「独立路径检查」，确认利用走的确实是目标缺陷；③变体分析按根因合并，避免把同一个 bug 的上百个利用报成上百个漏洞；④成本被失败的硬案例（竞争条件、超时）主导，明确的放弃条件比换更强模型更省钱；⑤当发现速度超过复核与上游吞吐，瓶颈就转到人——官方建议用 triage 系统对新树重新校验，而不是继续加扫描量。

**边界也要一起读。** 第一，全部数字为自报，没有第三方重跑；模型在发布报告时未点名，次日发布的 GPT-6 Cyber 官方页称「该模型驱动了昨天公布的 Linux 内核研究」，两者是同一模型、分两步披露（同期在 AWS GovCloud 上线的 Daybreak Red 是 GPT-5.6 Cyber，与本轮无关，别混）。第二，报告没有给 CVE 编号、子系统分布，也没有说 948 个里有多少是社区已发现的重复；扫描结束时上游状态是 61 个已修、43 个有 staging 补丁、299 个已在公开讨论——约六成当时既无修复也无讨论。第三，没有公开的披露时间表，10 项「新技法」只经内部与受雇外部专家评审，未公开复现；赏金换算（2 万/7 万美元）是假想参照，不是实际支出。HN 讨论最集中的质疑也在这里：无法估计「还有多少没被发现」，因而无法判断问题是否被解决；上游维护者的复核能力是硬瓶颈，数千份报告最终可能只缩成个位数。

### 3. 模型能直接读写权重吗：一个真实实验，两种被混在一起的证据

11 月 2 日，MIT CSAIL 的四位作者（Rikiya Takehi、Jayden Teoh、Alex Zhang、Omar Khattab）发布博客《Sparks of Weight-Space Programming》，摘要很抓人：只看原始权重，GPT-6 Astra 能说出一个网络被训练来做什么；不给环境反馈，能从零写出击败 PPO 一亿步的小游戏网络；让它在不做梯度下降的情况下把 Qwen3.5-0.8B 的数学成绩从 MATH-500 的 7.9% 提到 48.1%，只改了 0.016% 的权重（131,072 个），IFEval 顺带涨到三倍。代码、全部日志与改过的模型都放了出来，Hugging Face 上有人按日志独立重建并复跑了评测。

11 月 3 日，spaCy 作者 Matthew Honnibal 发了一篇《这篇……是误导》，把八个实验拆成一张表，核心指控是「摘要把两种技术装进了同一句话」：真正「只读原始权重、不用工具、不跑网络」的只有实验 1、2、4，网络规模 1.7 万到 17 万个权重；从实验 3 开始（720 万权重的字符 transformer、148 万权重的 9×9 Go 网络、Gemma 3 270M、Qwen 0.8B）都给了 Python 沙箱，实验 8 还跑了 50 次前向传播（158 轮、80 次 Python、约 20.3 小时）。实验 5 的「从零写网络」起点是全零权重——没有东西可读，自然也不属于「读懂权重」。摘要里的 "Likewise" 让读者以为 Qwen 那一段也是「只看权重」，实际不是。

数字本身也有被摘要盖住的部分。实验 5 写出的网络在 Breakout、Asterix、Seaquest 三个游戏上都超过 PPO 一亿步；对 PPO 五亿步则 Breakout 大幅领先（517 对 25），Asterix 接近（53 对 55），Seaquest 只有约六成（53 对 89）。实验 8 的「数学变好」主要是**去掉了 Qwen 的思考循环**：模型在 32k token 限制下有 93% 的答案撞限，改完降到 33%，MATH-500 才从 7.9% 升到 48.1%，GSM8K 从 13.8% 到 67.1%，IFEval 从 21.0% 到 62.3%；只做 10 次或 25 次前向传播时，分数只有 12.3% 与 14.1%。作者自己在正文里写得很清楚：「修好循环不等于让模型更会数学，只是让它把已经能算出来的答案写完」；同文的负对照 Gemma 3 270M 几乎没有循环，Astra 就改不动，MATH-500 只在 6.8→7.0–7.7 之间，作者自评「增益不成立」。社区复测给出了更直接的解释：不改任何权重、只关闭 thinking，MATH-500 就到 48.95%（HN 讨论中另有人给出 46%）——两处都是二手转述、未见原始脚本，但与作者「修循环」的解释一致。也就是说，Qwen 那组数字证明的是「权重修复能解除一个被循环卡住的能力」，不是「权重编辑能普遍提升能力」。

那「读懂权重」这一半站得住吗？至少在小网络上可以复现。Simon Willison 用笔记本上的 Qwen 3.8 27B（17GB，LM Studio）直接跑实验 1 的原始 prompt：Pac-Man 72%（46 分钟、43,506 个推理 token）、Pong 75%（约 1 小时 5 分）、Breakout 88%（52 分钟），Freeway 答错；Kimi K3.1 Pro 用 9 分 41 秒答对 Breakout。他自己的评价是：一个有经验的工程师拿纸笔花足够时间大概也能做到，所以这更像「模型能耐心做机械解释」，还不是「超人」。Sean Goedecke 的反驳更细：实验 1 的网络输入是五个已命名的通道（agent、移动物体、奖励目标、障碍、上一帧），在 10×10 网格上取第一层权重的 L2 范数画热图就能看出哪一行是挡板，三行 numpy 就能复现；Qwen 的问题不是数学能力，而是 32k token 后进入循环，Astra 做的是对比文本找方向、按贡献剪权的 steering/abliteration，这在机制可解释性里是入门操作。他的类比是：能直接改编译后的二进制，不代表不该继续写源码再编译。

**剩下可信的结论**：在 1.7 万–17 万权重、结构简单、输入通道语义已知的小网络上，前沿模型确实能从权重读出行为；在 ≤150 万权重的游戏网络上，直接写权重可以工作；到 0.8B 语言模型，所谓「变好」目前只等于「去掉循环、释放已有能力」，且需要代码执行、前向反馈、约 20 小时与大量 token，还要有可自动评测的任务。单条轨迹、没有置信区间、MATH-500 只采四次，这些都不支持「可靠」二字。

为什么值得跟踪：它触到「模型改自己的权重」这条自我改进路线的最敏感处——如果权重可以被自然语言直接编辑，RSI 的讨论就要改写法；但这次的材料恰好说明，**「直接编辑」与「用代码做实验再改」是两种能力，证据不能互相借用**。读这类宣称时，先看它有没有把「模型看到了什么、能调用什么、跑了几次」写清楚；这篇原始工作其实写清楚了，问题主要出在摘要的概括方式与二次传播。

### 4. 自动批准把命令写成规则，身份被写进 User-Agent

两起事件，一个共同点：边界不在模型里，而在 harness 把什么写进了文件与请求。

第一起是 11 月 5 日的 GitHub issue #107757，仓库里的实际标题是「Bug Report: Privacy violation in User-Agent header」。举报者称 Claude Code 在联网搜索时把登录账号的邮箱放进 `User-Agent` 发给第三方。机制不是遥测：Claude Code 把账号邮箱（`~/.claude.json` 里的 `oauthAccount.emailAddress`）放进模型上下文，模型自己拼 `curl` 或脚本时，按维基媒体、SEC 等站点「脚本客户端请留联系方式」的 UA 政策，把邮箱写进 UA 发出。官方 11 月 6 日在 HN 承认了这条路径，解释加邮箱是为了减少模型在 @author 等处编造署名；v2.1.317 起内置了一个 privacy 插件，只在 shell 输入同时含邮箱与 User-Agent 字样时拦截，插件说明明确不覆盖 WebFetch/WebSearch/MCP、脚本文件与运行时拼接值，多名用户在 317/318/319 上实测未触发。官方承诺「下一版」把邮箱移出上下文，截至 11 月 9 日 15:25 未发布，issue 仍 open（112 条评论）。影响面是所有 OAuth 登录账号；「垃圾邮件激增」只是举报人自述，没有因果证据。

第二起是 Apiiro 11 月 7 日的《Claude Code's "Don't Ask Again" exposes passwords in 1,122 public GitHub files》。机制更具体：点「Yes, and don't ask again」后，Claude Code 把整条命令字符串作为 allow 规则写进项目里的 `.claude/settings.local.json`——例如 `Bash(psql postgres://admin:密码@host…)`。秘密因为「命令即规则」变成明文文件内容。它只把这个文件加进用户的全局 gitignore，不写仓库的 `.gitignore`；文件如果已经被 git 跟踪，仍会照常追加。泄露出口是 git 提交（默认分支、fork、历史），不是日志或外发。

Apiiro 在 11 月 1–3 日只读扫描 GitHub 的 code/commit search，按文件大小切片绕开单查询 1,000 条上限，下载了 104,185 个 `settings.local.json`（来自 103,617 个仓库），其中 1,122 个（1.1%）含真秘密、1,379 个不同值；判定标准是已知厂商格式，或与公开主机同行的口令/token，再加独立 LLM 复核。扩展计数：共享 `settings.json` 命中 298 个（扫描 76,011 个）、agent 转录命中 120 个（扫描 2,523 个，涉 87 个仓库）、历史版本命中 734 个（509 个仓库），合计 2,539 个、1,994 个仓库。539/1,105 个含密仓库里，这个文件被 Claude 共同署名的提交改动过——这是研究方的归因，不是官方承认。

官方回应（Boris Cherny，11 月 7 日在 HN）：Claude Code 历来不做 secret scrubbing；这类文件应留在本地，Claude 创建时会 gitignore；「这些文件是手动创建并提交的」；建议用 auto mode 并开启平台 secret scanning；正在原型「auto mode 捕获 + 基础 secret 扫描」，没有版本和时间。Apiiro 的反驳是：全局 gitignore 不随仓库走、已跟踪文件不受其约束，且有 539 个仓库是该文件被 Claude 自己改动过。截至 11 月 9 日没有修复版本。

两条放在一起看，问题不是「模型会不会作恶」，而是 **harness 的两个便利设计各自打开了一条窄缝**：把身份放进上下文，模型就会在需要「留联系方式」的场合把它写出去；把整条命令存成 allow 规则，秘密就会以规则的形式落进一个可能被提交的文件。官方的方向也一致——确定性检查、auto mode、基础 secret 扫描——但都还在路上。对使用者的即时建议只有一条是确定的：升级不能解决，得去仓库里搜 `.claude/settings.local.json` 是否被跟踪、是否含凭据；以及别把「不再询问」当成无害的便利。
