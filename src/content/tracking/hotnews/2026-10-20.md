本期两件主要材料都在回答同一个问题：什么样的证据能说明 agent 真能干活。MiniMax 用一组 agent 基准和低价发布 M3.1 Flash，但它在匿名试用阶段就以另一个名字跑在 OpenCode 的订阅里，用户的反馈和官方数字对不上；RuneBench 把 MMO 做成可复现的长程任务环境，用峰值经验率而不是总经验值计分。后面还有一本把 harness 拆成 16 章的书、一个只读的个人 WhatsApp MCP，以及发行线简讯。

## 本期值得了解

### 1. MiniMax M3.1 Flash：低价 agent 模型的发布，与匿名试用期的另一种评价

MiniMax 10-19 发布 M3.1 Flash，定位很明确：不是通用聊天模型，而是给 agent 用的——官方把 agentic 任务、编码、Computer Use 和网络安全上的提升放在标题里，同时给出一个很有攻击性的价格：每百万 token 输入 \$0.15、输出 \$0.60、缓存命中输入 \$0.015；官方称 agent 任务整体成本比上一代低 70%，在线推理快近 3 倍。已通过 API、M Plan 订阅和 MiniMax Code 桌面端提供；权重稍后发布，Pro 版也在后面。

规格上，MiniMax 的开发者页列出混合专家（MoE）结构：总参数 428B、每 token 约激活 23B，上下文 1M token，支持文本、图像、视频输入，推理始终开启，只有五档 effort（Low、Medium、High、Xhigh、Max）可调。速度口径有两处：正式发布博客说峰值 200+ token/s、P50 170+；预览版开发者指南写约 150 token/s——前者是正式版口径，后者是预览指南的数值，实际取决于负载。

官方给出的 agent 基准：AutomationBench-AA 进入前列（未给具体分）、BankerToolBench 76.2、DeepSWE v1.1 73.7%、OSWorld V2 61.7（官方称中国模型中第一）、Agents' Last Exam 29.6（同称第一）、CyberGym 82%。这些数字都来自 MiniMax 自己，未见独立复现。

更有意思的是发布方式：博客自己说，M3.1 Flash 的早期版本曾以「Space Bunny」的名字匿名跑在 OpenCode Go 里，处理了 200 万亿 token 才公开身份。匿名大规模试用本来可以成为比基准更接近真实使用的证据；但 HN 讨论（400 分/172 评论）里，最高赞的评论给的是相反结论——它认为这个模型是「为基准而优化」（benchmaxed），Space Bunny 在免费提供时也没让人印象深刻，GLM 5.3 Flash 和 DeepSeek V4.1 Flash 更受偏好。另一位评论者则用自己搭的对抗性编程语言基准测得它与 DeepSeek V4 Pro 相当。两边都是个人体验或单一基准，不能互相取消；可以确定的是，厂商基准与匿名试用期的口碑没有对齐。

对做 agent 选型的人，这条的实用部分不是排名，而是价格与规格：\$0.15/\$0.60/\$0.015、1M 上下文、推理常开。是否真的便宜，要看具体任务的输出与思考 token；是否真的强，需要独立评测——目前公开的只有一个对抗性语言基准的正面结果。

### 2. RuneBench：把 MMO 做成可复现的长程 agent 评测环境

RuneBench 是一个把大型多人在线角色扮演游戏（MMO）当成 agent 长程任务环境的评测项目（作者 Max Bittker 等，仓库 2 月建）。它用 LostCity 的模拟服务器跑 RuneScape，把服务器加速到 8 倍；代理不是直接操作键鼠，而是写 TypeScript 片段调用 SDK 读游戏状态、执行动作，每个任务还配一份从游戏 wiki 抽出的 markdown（技能指南、物品数值、NPC 位置、任务攻略）。任务分三类：16 个单技能经验值（XP）任务（15 分钟）、16 个延长到 30 分钟的版本、8 个金币积累任务（4 种起始条件 × 15/30 分钟）。每个任务跑在 Docker 容器里，SDK 通过 MCP 服务器暴露游戏工具，最后由 verifier 检查游戏状态计分。

计分指标是这条最值得看的地方：最初的设计是固定时间内最大化经验值，但作者发现这会惩罚探索——赢家往往是不停手的简单刷；于是改成「任意 15 秒窗口内的最高 XP/分钟」（峰值经验率），奖励发现更高级策略的运行。作者说获胜运行会用多个地点、技巧和方法，并感叹「模型是惊人的优化器」。

RuneBench 的 SDK 也不是先设计好再评测：作者用自动化错误分析迭代——批量跑 agent、归类失败和缺失功能，再据此改 harness，等于把代理与游戏服务器之间的 API 层「养」出来。局限由作者自己写明：任务运行时间长；缩短时间会惩罚前置规划（花几分钟读文档）和推理慢的模型；环境复杂、样本少，会给模型比较带来噪声和假阴性，影响数值准确性。未来工作列了多代理协作（一个采集、一个加工）和知识转移（一个代理给另一个写指南）。

这条是补收：基准 2 月建仓，10-18 早晨提交的 Recurse Center 讲座视频与 HN 讨论（167 分/64 评论）落在上一轮窗口内但此前未收；视频上传日期未取，按 HN 提交时间记。它不是本期新发布，值得看的也不是排行榜，而是「环境、计分、噪声」这三件事如何一起决定评测结论。

## 其他值得关注

### 3. Harness Engineering 101：把 agent 拆成循环上的补丁

Harness Engineering 101 是一本 16 章的书（v1.1，2026-10），作者 Isuru Maduranga 做过 WSO2 的两个 Copilot 和一个开源编码代理 One Code。它的中心句很简单：LLM API 是无状态的，每一轮都要把整段对话作为 JSON 数组重新发回去；harness（代理运行框架）就是构建、维护、保护这个数组的程序。作者进一步主张，业界所说的 agent 能力，大多只是对这个循环打的补丁，而每个补丁都对应一个具体故障。

书的组织方式也照这个主张来：每章先给失败，再给最小补丁，最后算补丁的代价；一条约 300 行的 Python 玩具代理贯穿全书。作者在开头披露了写作方式：自己起草每章，用 Claude Code 和 One Code 重排章节（先给答案）、润色英文、生成图表和画图代码。

它值得看的不是「又一个 agent 教程」，而是把功能清单还原成故障驱动的循环补丁——如果要判断某个 harness 功能为什么存在、代价是什么，这个框架比按产品对照有用。局限也清楚：作者视角的教学材料，不是独立评测。

### 4. WhatsApp MCP：只读、跑在自己 Cloudflare 账户里的消息接入

WhatsApp MCP 是一个 Show HN 项目：把一个小服务部署在你自己的 Cloudflare 账户里，让任何支持模型上下文协议（MCP，用统一接口连接外部工具与数据）的客户端读取你的 WhatsApp 消息。它的设计取舍很明确：手机仍是事实源，服务只是像 WhatsApp Web 一样被链接的一台设备；代理要消息时（以及每天一次）才连上去，收取 WhatsApp 排队给它的内容，写进自己账户里的 SQLite，然后断开。

能力边界：只能读和搜，不能发；媒体不下载，只留 `[image]`、`[voice note 12s]` 这类标签；一次部署对应一个账号、一个所有者；联系人名字可以借助代理已有的通讯录或 Gmail 工具补全，服务本身不连通讯录。它需要 Cloudflare Workers 的付费计划（首次导入历史会触碰 CPU 上限），消息留在自己的 Cloudflare 账户里。

边界也要写清：这不是官方接口——WhatsApp 没有读取个人消息的 API，项目用的是 WhatsApp Web 的协议库 Baileys，违反 WhatsApp 条款；作者认为只读链接设备的实际风险低，但不是零。它提供的是一种个人数据接入形态：桥接器跑在自己控制的云账户里，默认只读。HN 讨论 146 分/78 评论；项目属上一轮窗口的覆盖缺口，本轮补收。
