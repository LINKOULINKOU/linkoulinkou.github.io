## 本期主线：可编程扩展层同周成型——Mods 发布、编排即代码、第三方跟进兼容

三条独立动态指向同一变化：编码 harness 正在把「代理运行时的可编程控制面」做成产品接口——插件可以改写事件（Claude Code Mods），编排本身变成可提交的代码（Copilot Dynamic workflows），且这套接口两天内就被第三方 harness 当作兼容目标（DeepSeek Harness）。综合判断：前几周各家在比「代理能做什么」，这一周开始比「别人能在代理上编排什么」；接口的互认程度，会直接决定插件与技能生态往哪走。

### 1. Claude Code 正式发布 Mods：插件可改写代理运行时事件

Claude Code（Anthropic 的编码代理）10/1 发布 **Mods**：装进插件分发的一类扩展，通过订阅运行时事件来观测、改写或接管代理行为——能改写发给模型的提示词，阻止、改写或重试工具调用，批准或拒绝权限请求，在工具输出进入模型前做脱敏，也能替换界面元素；多个 mod 按加载顺序形成中间件链，先加载者先见到事件。此前该能力以「灰度泄漏」形态被社区从源码里读出（09-24 期条目 1），官方当时称数周内发布，这次连同整套文档上线，并明确 **Mods 与 Claude Code 同权限、不做沙箱**，只应安装可信来源。两个信号说明它是正式产品线：内置功能开始外迁——`/diff` 已改为 mod、官方称还会继续把内置功能下沉、把内核缩小；企业侧默认先加载内置 **sec-default** 压制用户安装 mod 的越权（例如覆盖权限拒绝规则），v2.1.288、v2.1.289 连续两版修的正是「托管机器上拒绝规则要能压过 mod 的审批」这类对抗。边界：npm stable 通道仍停在 2.1.285（latest 为 2.1.289），引用「稳定版行为」先看渠道；官方称设计曾在 issue 中公开征求意见。

### 2. GitHub Copilot 把编排写成代码：Dynamic workflows

GitHub 10/1 为 Copilot CLI、Copilot 桌面应用与 Copilot SDK 发布 **Dynamic workflows**：工作流把若干自动步骤与一个或多个代理组合成可执行流程——步骤可串行或并行，能把目标拆成并行任务、传递结构化结果、让子代理互验、必要时向用户要输入，并支持检查点暂停与恢复；工作流程序跑在 Copilot 的扩展机制里，可以复用扩展接口，也可以让 Copilot 自己写。官方把它与既有的并行子代理能力作对比：后者是「派一批子代理干活」，前者是「用代码定义怎么派」。为什么值得关注：编排从提示词与对话变成可版本化、可复用的程序，与本工作区持续跟踪的 loop engineering 方向直接对应；另一面是权限与审批将被要求覆盖「工作流生成的步骤」这一新形态。

## 对当前工作流的启示

- **跟 Mods 生态的接口化**：扩展接口一旦被第三方当兼容目标（dsh 已跟进），插件与技能的可迁移性随之提高；值得跟踪第三方 mod 的实际用法（如会话监控类）与 sec-default 的压制案例，再评估哪些模式能迁移（见条目 1、3）。
- **决策模型先校准再接入**：已有至少两项独立证据质疑「自报置信度」可直接做门限（≥99% 对 68%；守卫场景无优势），若要把决策原语放进路由或分类环节，先用自己的数据做校准与对照（见条目 7、8）。
- **成本与信息边界前移**：硬预算上限、「代理读到停机线索」类事件与桌面操作进入上下文，都指向把成本与信息边界做成系统默认，而非事后发现（见条目 4、11、17）。
