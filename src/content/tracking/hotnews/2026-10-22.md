### 1. Claude Duet：主动助手把“先问你”做成产品边界

Claude Duet 是 Anthropic 10-21 开放研究预览的独立应用（iOS、Android、claude.ai），面向 Pro/Max 用户，先在美国以候补名单（waitlist）开放。它和普通聊天最大的差别是主动性：它读取你连接的邮件、日历和其他应用，每天早上给一份简短简报，白天只在“需要你注意”时发消息；你也可以把排会、做仪表盘、财务或销售预测、原型和网页应用之类的任务交给它，离开后它继续做。官方把“判断什么需要你、什么可以等、什么时候先问你”称为产品的核心，但没有公开这套判断的具体策略。

它的控制模型比“主动”更值得看：发送消息、付款、签文件、删除之前，Duet 会把将要做的动作展示出来并等你批准；即使批准，证券交易和账户间转账之类也被列为不可做；你可以随时断开某个应用的访问。凭据沿用 Claude Managed Agents 的设计，Duet 不直接看到密码或登录 token；支付走 Link/Stripe 的虚拟卡，1Password 登录是“coming soon”。此外还有一个专门的安全分类器和系统提示，拦截信用卡号、政府证件等最敏感信息的对外发送。

这套设计把“主动代理”的风险落到了可检查的动作上：不是问模型会不会越权，而是问每一次外发、支付、删除有没有经过展示与批准，哪些动作即使批准也不做，凭据是否经过代理而不进入模型上下文。边界也要说清：这是研究预览，官方没有给出主动判断的准确率、误报率，也没有公开外部渗透测试的结果细节；HN 的 279 条评论里，最具体的担忧是给它 1Password 访问权限，另一些人把它和 ChatGPT Dot 等个人助手比较。产品能力是官方自述，不能当成已独立验证的“可靠主动”。

### 2. Qwen Code 0.26.0：托管运行时开始区分“失败”和“不知道”

Qwen Code 在 10-22 早上把 0.26.0 转稳定（10-21 23:20 UTC，北京 10-22 07:20），上一轮看到的 0.25.4 预览里的托管运行改动已进入稳定版。发行说明没有把它写成“新功能清单”，重点在托管 agent 的状态机：工作区隔离的会话预热、按会话刷新 Skill/Extension、接任的托管运行所有者（Hosted owner）凭已有的持久回执（durable receipt）完成私有文件轮次、运行时（Runtime）结果无法证明时标为未知（unknown）而不是瞬时故障（transient fault）、未知的轮次先挂起等待复查而不是反复重试取消。

这些改动的共同点是“谁拥有这一轮、做完没有、失败了还是不知道”。长会话恢复最怕两件事：同一轮被两个 owner 同时执行，或者结果未知就当成失败重跑，导致重复写文件、重复调用工具。Qwen 的做法是把执行证据（execution evidence）和持久回执（durable receipt）作为恢复依据：能证明完成就接着完成；不能证明就标 unknown、挂起复查；接任者只接已经留下回执的私有文件轮次。这比“失败就重试”更接近可恢复的语义。

发行说明还列了：托管 agent 在一轮进行中修改审批、会话创建时导入已启用 skills、8 MiB 附件、凭据 bootstrap、后台守护进程（daemon）的 start/status/restart、每模型首 token 延迟（TTFT）和输出速度，以及一个实验性的生成式界面（Generated UI，模型生成 HTML/CSS 卡片，在受限本地 JS 里调整输入，不再多跑一轮模型）。这些不是同一个功能，但都指向“托管运行时要能被启动、观察、恢复和审计”，而不是只把 CLI 包一层。

边界：这些是发行说明和 PR 标题，官方没有给出故障注入或恢复测试的结果；0.26.0 虽标稳定，但托管部署的默认行为仍要以文档和实际配置为准。上一轮只看到预览版的标题，这一轮补的是稳定版和更多恢复语义，不是重复收录。

### 3. Claude Code 2.1.307：把“为什么拦住这次工具调用”写进 OTel

2.1.307（北京 10-22 06:17）新增 `claude_code.safety_event` OpenTelemetry 事件：每次工具调用被权限规则、auto mode、安全检查、hook 或沙箱拦住、询问、退回时，都会发一条事件。它本身不是新的权限规则，而是把“哪一层、因为什么介入”变成可采集的观测数据；对需要审计 agent 行为的团队，这是比只看最终拒绝更有用的信号。

同版还修了一个工具执行语义：HTTP MCP 调用在连接中途断开时会被发送两次；现在只对只读或幂等工具重试。这个修复值得注意，因为它把“重试”与“是否有副作用”绑定，而不是所有工具都自动重试。其余修复包括 MCP 在 macOS 锁屏或睡眠后的认证与超时状态、subagent transcript 的 token 与 stop reason、Autocompact 抖动等，属于维护线，不展开。

### 4. GitHub 把 Git 存储迁到 Azure：agent 流量把 Tier 0 服务推到架构迁移

GitHub 10-21 的工程文章给出了一个不常见的基础设施视角：Git 流量在 agentic shift 下快速增长，GitHub 把 99.99999% 的仓库复制到 Azure，但最忙的仓库卡在 25ms 的跨区往返上。文章的核心改动是把写入仲裁组（quorum）的范围从“整个仓库”缩到“单个引用”，并把对象存储作为一个虚拟副本加入 quorum：写先在对象存储持久化，读副本可以从 Blob Storage 预热、按需扩容，不再都挤在写 quorum 上。

这条不是 agent 产品，但它说明 agent 带来的不是只多几个请求，而是 Git 这种最高优先级（Tier 0）服务的写入、读取比例和并发结构变化；当编码 agent 大量 clone、fetch、push、开分支时，仓库级锁和跨区复制会成为瓶颈。文章给的是 GitHub 自己的迁移方案和自报数据，没有第三方复现；它值得看的是“按单个引用的仲裁组（per-reference quorum）+ 对象存储虚拟副本”这个拆分思路，而不是把它当成所有 Git 托管的通用配方。

### 5. LiteLLM 1.107.0 供应链事件：模型网关的凭据面

10-21 的 LiteLLM 事件值得 agent 部署团队单独看一眼：PyPI 上的 `litellm==1.107.0` 七个 wheel 包都带有凭据窃取器和后门，`cook.pth` 在 Python 启动时自动 import `cook`，`sitecustomize.py` 负责加载；窃取目标包括 SSH key、云凭证、CI/CD secret、AI 工具 token、浏览器密码，以及 LiteLLM proxy 数据库里的模型服务商密钥（provider key）。PyPI 已移除该版本，Docker 的 `latest`、`main-latest`、`main-stable` 也已撤下（yank）；维护者的 issue 说根因是构建自仿冒仓库（lookalike）`Berri-AI/litellm`，payload 不在 `v1.107.0` 的 git tag 里。

这不是 agent 能力更新，而是 agent 网关的供应链风险：LiteLLM 常被用来把多个模型和工具接到同一层，一旦安装被污染的版本，provider key 和工具凭据会直接暴露。当前可核的处置是 pin 1.106.2、轮换 PyPI 发布凭据、检查 Docker 镜像；初始入侵路径和完整影响仍要以维护者后续说明为准。HN 的 442 分/147 条评论主要在为包管理器冷却期（cooldown）、权限弹窗疲劳和“又一次”争论，技术细节反而不多。

### 6. NVIDIA OpenShell 参考架构：把 agent harness 放进可监管的执行边界

NVIDIA 10-21 发布 OpenShell 参考架构，把 9-28 发布的 OpenShell 安全运行时扩展成一套全栈部署：推理放在 Vera Rubin，agent harness 与工具调用放在 Vera CPU，BlueField-4 DPU 上的 Sentry 做带外监控和芯片内策略执行；支持 Canonical 与 Red Hat 的企业 Linux、Microsoft Windows 和 Microsoft Execution Containers；合作方包括 Anthropic、AWS、Cisco、CrowdStrike、Google Cloud、IBM、Meta、Microsoft、OpenAI、Palo Alto Networks、SAP、ServiceNow、Siemens、SpaceX Super Intelligence 等。

这条和 Qwen 的托管运行时是两种所有权模型：Qwen 管的是会话与轮次状态，NVIDIA 管的是执行环境与带外强制。官方没有给出拦截率、性能数据或独立攻击测试，当前只是参考架构和伙伴名单，不能当成已验证的防护效果；它值得看的是“模型推理、harness、DPU 看门狗分开部署”这个边界划分，而不是伙伴名单本身。
