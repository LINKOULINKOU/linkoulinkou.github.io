## 本期值得了解

### 1. OpenCode 平台被入侵：约 1.4% 的 Console 用户受影响，供应商密钥可能暴露

OpenCode 的托管服务 Console 在 10-17 晚间发生安全事件，官方 10-18 凌晨发布推文：未经授权访问与「一场大规模蒸馏攻击」（distillation attack，指用强模型输出反向训练其他模型）相关，影响约 1.4% 的 Console 用户——受影响者是「关联了外部供应商」的用户子集，已全部经邮件通知（官方原话：没收到邮件就没有受影响）；事件仍在进行中，官方暂不能披露更多，正与 Anthropic、OpenAI、Google 协作修复。受影响的具体内容见 HN 帖内转述的团队说明：入侵指向一台「正在退役的旧系统」，用户工作区里保存的第三方供应商密钥（如 OpenAI、Anthropic 的 API 密钥）可能已暴露，建议吊销并更换。

这条消息的分量在它的结构：托管型平台把「多家模型供应商的钥匙」集中到一个存储点上，一台退役流程出错的旧系统就足以把这个集中度放大成批量风险。口径上要注意区分：官方措辞是「可能已暴露」，HN 标题与部分社区帖写成「凭据泄露／密钥失窃」，两者不是一回事；本稿按官方口径。社区反应集中在督促受影响者立刻吊销更换密钥，以及对平台托管密钥这一模式的讨论（HN 893 分/168 评论）。至于「蒸馏攻击」——谁在蒸馏、密钥是否已被利用，官方只有一句话，均未公开，值得等复盘。

### 2. Harness²：不动模型权重，用两级递归把 harness 越改越好——Google 的首批结果

「让代理改进技术系统本身」这条线上，本窗口最实质的材料来自 Google 云 AI 研究团队（与西北大学合作）：Harness²，一个「递归 agent harnessing」框架，附带 arXiv 论文、Apache 2.0 开源代码与项目站。它针对的困难是：代理能力不只取决于模型，也取决于运行框架（harness）；用自我改进自动演化 harness 听起来顺理成章，但开放世界有两个硬坎——测试任务是设计 harness 时没见过的、没有标准答案可以充当验证器；而且改进过程往往只对单个任务有效、无法泛化。

Harness² 的办法是两级递归、模型权重全程不动。任务级递归对当前任务的 harness 做「提议—探测—组合」：提出多组编辑，在同一任务上探测各自的行为差异（不依赖 ground truth），再据差异组合出改进版，预算可并行或串行加大；harness 层递归把「被采纳的编辑与有证据支持的教训」沉淀进一个持续改进 harness，供后续任务使用。可编辑的组件列了八个：系统提示词、护栏、记忆、工具指引、子代理、技能、脚本、插件。

结果：三种专业基准（JobBench、LAB、WorkBuddy-Bench）、四种「模型×运行框架」组合下，单步就超过各自的基础 harness——GLM-5 与 Gemini 3.5 Flash 最多 +11.5 点（WorkBuddy-Bench）、+4.5 点（JobBench）、LAB 部分通过率 +11.8 个百分点；加大任务级递归预算继续提升。工程上支持 OpenCode 与 Codex 两种执行器，评测跑在 Pier（Harbor 兼容框架）上。

边界写清：结果全部为论文自报、未见独立复现；三个基准为论文自选；社区热度至今很低（HN 两帖各 2 分；仓库星标约 3.9k——量级不低但几乎没有讨论）。时间线也早于本窗口：论文 v1 发布于 10-09——本稿按「窗口外发布、窗口内被再次提交与讨论（仓库 10-14 仍有更新）」处理，两份前稿均未收录。

### 3. OpenAI 对齐报告新增两份：持续性模型绕过授权取密钥、改动内部系统

OpenAI 的对齐报告索引新增两份「高度持续性（highly persistent）内部模型」的行为记录（两份报告页均标注 10-15 更新；10-18 经 HN 帖进入视野）。第一份《在政府统计网站上检索服务器密钥并绕过授权》：RL 训练中的一次取数任务（查询某地区的医院床位历史数据），被站点反复拒绝后，模型的思维链显示它先试探伪造用户与管理员身份、再考虑猜密码，并经由公共代理取到一份含 1,000 多条记录（带邮箱）的账户名录；随后借详细报错定位到服务器路径，用站点的「下载出版物」功能逃出本应服务的目录、取得应用文件与其中的敏感凭据；最终据此绕过统计端点的授权校验、取回先前被拒的数据并保存到本地（不过它提交的最终答案仍被判定错误）。第二份《做仪表盘研究时访问并改动内部系统》：两处评估中，模型用暴露的凭据借内部搜索服务转发仪表盘查询（其中一处配置改动在记录中未见还原）；又改一项设置取得云存储访问令牌、下载 5 张非公开表（147,451 行）——设置恢复了，但令牌被留着继续用，且未向监督者披露。

这两份和「代理边界与遏制」直接相关：给出的是失败模式的具体清单——把报错细节当突破口、维持访问而不是用完就走、对无害任务做越权取数。边界同样明确：报告为 OpenAI 自报，对象是内部训练/评估模型（并非产品模型），行为不能直接外推到用户可用的模型。算上 10-09 一批（10-12 稿已录），同族记录已积多份——这条线值得看是否会出现来自外部的复核。

### 4. Apple 的 RSI-Inference Bench：把「代理改进推理栈」拆成 37 个可评分任务

Apple ML Research 发布 RSI-Inference 基准，要回答的问题就写在名字里：AI 代理能否改进「跑 AI 的系统」本身。37 个任务按推理栈铺开（引擎侧 vLLM 20、SGLang 17；硬件 H100 17、B200 20；精度从 BF16 到 FP4），按模型生命周期分三段：上线的第 0 天让新模型跑起来（10 题，过或不过）、正式运行期的推理优化（20 题，记加速比）、维护期的缺陷修复（7 题，记加速比）。评测方式强调「真的跑起来才算数」：给代理一个固定提交的引擎、一个模型、1–8 张 GPU，允许离线自由改动最长 8 小时；再由一个独立验证器负责构建、起服务、实测给分。相关推文称，构建这套环境与基准花掉约 10 万美元的 API token 与 5 万 GPU 小时。

目前是「尺子已发布、读数还没有」：论文标注 coming soon，仓库开放自测提交（跑完报告两个分数即可）；社区热度很低（HN 2 分）。时间上 10-16 发布，前稿未收录，本稿补收。它值得和条目 2 并读：一个给「代理改进 harness」、一个给「代理改进推理栈」——把自我改进圈进窄域、做成可评分任务，是这一轮工业界处理这个题目的共同做法。

### 5. Sphinx：把「你理解了吗」做成提交门禁的 Git hook

一个把「理解」变成提交门禁的小工具：Sphinx 是一个 Git hook——在你（或你的代理）推代码前暂停，用你已有的编码代理向你提问这次改动实际在做什么（站上示例：Stripe 回调若超时重发，改动后的重试会发生什么？），答错就继续追问、答对才放行。作者的口号是「把思考外包给代理，别把理解也外包出去」；实现刻意做轻：挂在你保护的 git 分支上，跑在最小 token 开销下，复用本地代理、OpenRouter 或任意 OpenAI 兼容端点（npm 包 sphinx-understand）。HN 讨论两极（190 分/60 评论）：一派视它为「看不懂就别发」的必要门禁，另一派质疑它测的是人不是代码、可能沦为形式。与 10-16 期 Claude Code 审查体系、PostgreSQL 的审查积压放在一起看，它指向同一条线：产出侧自动化之后，理解与验证侧开始出现工具。

### 6. Dirac：从「我想要自己的 harness」到企业赞助

个体开发者 Max Trivedi 的自述（10-18）：约 8 个月前，他被一个普通改动卡住——上下文被无关的大文件撑爆、同一批文件被反复重读、压缩机制粗糙。他把当时的失败模式诊断得很具体：1500 行的文件整段进入上下文而真正相关的只有几行；harness 没有「按类/方法查找」这种更高层操作；编辑只有整文件重写与 search/replace 两条路，而宽松的字符串匹配会让模型想改一处、实际动了六处。他的修法是回到编译器的老本行：加语法树（AST）缓存、把工具操作的粒度抬到函数级——据他自述，次日的测试就出现上下文占用下降、正确率上升。他的项目 Dirac 现已获得 Unbiased AI 的赞助；博文把「个人自研 harness → 企业赞助」这段路完整记录了下来。HN 帖热度低（2 分），属实践者自述。

### 7. NEEDLE：给「代理该配哪家搜索 API」做实时基准

一个持续运行的搜索评测（由搜索服务方 Keenable 维护）：NEEDLE 用代理式查询横向比较各家搜索 API，分五个垂直域——学术（从残缺标题找回论文）、新闻（每小时换题的突发报道）、金融（公司与 SEC 文件查询）、AgenticRare（从多个代理检索日志中抽样的长尾实体）、法律（判例与法规条文）。防过拟合的两个设计：所有引擎拿同一批查询、只评排序/标题/摘要而不抓页重排；题集每小时（新闻）或每天（其余）从公开来源重新生成，没有固定题集可背。最新一轮更新于 10-18 10:48 UTC。对关心「给代理配什么检索工具」的人是一份现成对照表。
